### board

The **shared work board**: a durable record of what every session has in flight, who is driving it, what it waits on, and what was decided. Coding sessions (`car claude`, `car codex`), CAR agents and people read and keep it; design in [shared-work-board.md](../proposals/shared-work-board.md).

**Awareness, not exclusion.** Nothing on the board locks or refuses work. Two items that share a ticket, branch or PR are *related*: the write that creates the overlap reports it in its result (`overlaps`) and sends the other item's last-writing session a `handoff` peer message, through the same admission as `agents.message`. That includes two sessions of the same account. Neither write is refused. Exclusion stays with resources that cannot be shared (worktree slots, test locks); `lattice.claim` is unchanged.

**One writer per item.** An item's `owner` is the account the daemon bound the writing session to: the work context's `account_id`, or `personal` for unbound personal work. It is set by the daemon and refused as a client field. Any session of the owning account may change the item; every change records the session that made it (`updated_by`, and `node` in the history) and the device it was made on (`device`: this CAR's host label, the name the owner's other devices know it by). Two devices on one account write under one `owner`, so `device` is what tells their items apart. It is set by the daemon, never by a client, and absent on an item last written before CAR recorded it. Any session that can see the item may append a comment, which never changes it.

**One board per work context.** A session bound to an organization uses that organization's board (every account of the org on this CAR shares it); a personal account, and unbound personal work, each have their own. A session never names another board. An agent this CAR supervises whose registration has no work context (CAR Link, any CarHost-supervised agent), calling from its own connection, is one of the owner's sessions: it uses the board of the organization it names with `org`, or, when it names none, of the person's default organization (`car auth default-org`), else of the organization the owner's active Parslee login is signed in to (the one `car auth orgs` marks active, which `auth.switch_org` changes), else of the only one this CAR holds a login for: the same rule as `collab.*`. When it holds several and none of those settles one, a call with no `org` is refused with a sentence telling the person to choose a default organization. It uses the personal board while this CAR holds no organization login. Its items are owned by the owner's account in that organization and record the agent as `updated_by`. It can't name `account`. The operator's host client uses the personal board, names an organization this CAR holds a login for with `org`, or names a personal account context with `account` (and `api_base`, default Parslee's): the board a session bound to that account writes.

**An organization's sealed board.** An organization can move its board onto Parslee's sealed org board, where the backend stores every item sealed with a key only the org's verified devices hold. CAR never moves an organization by itself: a person in the org takes one explicit step from their own CAR, `car board setup --org <org>` (`board.setup`, host credential only), which makes the board's first key and copies it to the org's verified devices. It can't be undone, so no agent and no Claude Code or Codex session can run it.
- **Which board an organization uses** is the organization's state on the backend, the same for every CAR in it: the sealed board once the backend holds a key history for it, otherwise the file board below. Each CAR asks the backend with its certificate for the org and remembers the answer in `<state root>/lattice/org_board_route/`. The sealed answer never goes back. The check never holds a call up: an organization found without a sealed board is asked again at most once a minute (so a board set up by another CAR is found within a minute), one check at a time, waiting at most 2 seconds with no retries, and a call with a remembered answer never waits for a check another call is making. When the backend cannot be asked (no usable certificate for the organization, certificate logins not listed yet, or Parslee slow or unreachable), the remembered answer stands. With nothing remembered, the CAR uses the file board and remembers nothing, so a later check can still find a sealed board; until a check answers, every reply from `board.list`, `board.upsert`, `board.transition`, `board.comment` and `board.history` carries `notice`: "This CAR couldn't check whether this organization has a sealed board, so it's showing the board stored on this device." CarHost shows it as a line above the board's rows, and the `car board` commands print it to stderr (`--json` keeps it in the reply). Such an organization still serves and accepts writes on the file board; the notice is what tells a person which board they are looking at.
- **What changes once it is set up.** Every board method on that organization reads and writes the sealed board, on every member's CAR. Items on the org's file board stay in that file and are no longer shown; the org moves what it still needs. A sealed board needs Parslee: offline, its calls fail with the reason. Not yet on the sealed board: overlap reports (`overlaps` is always empty), sending an `ask` to the person, `related` rows, other CARs' items and the code-host reconciler, which keeps writing to the file board. A row is `stale` only when the backend says so. Personal and account boards, and every organization that has not been set up, are unchanged.
- **People hear about changes to their items.** Anyone in the org may claim, close, reopen, release or take over an item someone else created, or comment on it, so the sealed board tells the people an item is about. The account that created the item is told of every change someone else makes to its state or its holder (a claim, a takeover, a close as `done` or `abandoned`, a reopen, a release, any other status move) and of every comment someone else adds. Whoever held the claim before is told when the item leaves their hands to someone else (a takeover of a stale item, an accepted handoff). The ownership verbs tell the same people whenever they change who holds the item: `board.claim` (a claim, or a takeover of a stale item), `board.release`, and `board.accept` of a handoff or assignment, whose notice says it was accepted. `board.check_in`, a `board.handoff` or `board.assign` asked, and `board.decline` leave the holder as it was and tell nobody; the person a handoff or assignment names sees it through the item's `pending`. The account that made the change is never told, and an edit that changes only the item's words tells nobody. Each notice is a private message from the person who made the change, queued on the same collaboration outbox as `collab.message`: sealed on this device, sent by the collaboration pump, and read in the told person's sessions bound to the org (`collab.read`) and in CarHost. It passes the same body scan and delivery guards as any message, and carries only the item's id, title, project, new state and the backend version it was left at (a comment's notice quotes the comment), which the person can already read on the board. The write's (or verb's) `notified` lists each person told, as `{ item, to, role: "creator" | "previous_owner", queued: true, message_id }`, or `queued: false` with the `reason` it was not queued (no certificate for the org, the body scan or a delivery guard refused it, or the person has left the org). Someone who has left the org is never told: when the relay sends the org's roster, a creator or previous holder the org's directory no longer lists gets a `queued: false` row and nothing is queued for them. Without a roster the directory names only who holds a certificate now, so the signed membership this CAR has verified decides instead: a creator or previous holder this CAR's pair with them no longer has as a member, or whose departure from the org a history this CAR holds records while no history it holds has them as a member and they hold no certificate now, also gets a `queued: false` row and nothing is queued for them. The notice is still queued when nothing this CAR has verified speaks to that account (before the first collaboration pass after a restart, for someone who shares no conversation with this CAR and appears in no departure it holds, or for someone who left within their last certificate's life); the sealer, which reads the signed membership before every send, then refuses to send it to someone who left. `queued: true` means it is on the outbox, not that it arrived.
- **When someone leaves.** Once a person is removed from the organization, the backend refuses sealed writes until the board has its next key. The next write from a member's CAR makes it: a fresh key for the next epoch, recorded by a signed statement and copied only to the devices the org's directory lists at that moment (read fresh, so the person who left gets no copy), then writes. Of two CARs doing this at once, one key is stored and the other CAR opens its copy.
- **Claims and Ready.** On a sealed board an item is held by whoever claimed it (`holder`), apart from its `owner` (who created it). `board.claim`, `board.check_in`, `board.release`, `board.handoff`, `board.assign`, `board.accept` and `board.decline` are the backend's ownership actions; the backend referees each, and a refusal says why with nothing written. A holder promises to check in (every 24 hours unless the claim names another `check_in_ms`); every write the holder makes to the item checks in too, and a holder who misses one leaves the item stale and free to take. **Ready** is the backend's answer, from the board's structure alone: open and held by nobody, not waiting on an assignment's answer, and blocked by nothing unfinished; or stale. `board.list` marks each row `ready`, and `ready: true` lists only those. The rows and Ready are two reads of the backend, and a claim, release, handoff or assignment can land between them, so a row is marked `ready` only when Ready named the item at the same `version` the row carries, and never while the row names a holder who has not missed a check-in: a row's `holder` and its `ready` never contradict. An item freed between the reads reads free but not ready until the next list. A blocker finished or reopened between the reads changes Ready without changing the blocked item's `version`, so that item's `ready` is as of the Ready read. An item is blocked by another when `board.upsert` names it in `blocked_by`: the backend keeps the link, refuses one that would make a loop, and frees the blocked item from Ready once each item blocking it is `done` or `dropped`. An open item that is still blocked may be claimed all the same; it was just never in Ready. `in_progress` and `abandoned` are spelled `claimed` and `dropped` there; either spelling is accepted.
- **Where an item came up.** `board.upsert` with `collaboration` (the id of a collaboration this CAR's owner is in) links the item to that collaboration as a place it came up. A card may be linked to several collaborations, one link each. The board itself never records a link: the creator's CAR posts one line to the collaboration's members, sealed end to end like any `collab.message` post, reading `Raised on the board: "<title>"` (the title and nothing else: no id is ever in the words a person reads), and that post is the link. The item's id rides in the post's sealed `board_item` member, which `collab.read` and `collab.conversation` give as `board_item` on the post (CarHost links the title to the card with it). Posts made before 2026-11-23 carry `[board item <id>]` at the end of their text instead and are still read as links. A link is added to an item that exists by `board.upsert` with only its `id` and `collaboration`: no field of the card changes, so its content is not written again and nobody is notified (a holder's write still checks in, as every write by the holder does), and linking a collaboration it is already linked to posts nothing more. Each member's CAR reads its own copies of the collaborations it is in and lists the item's `came_up_in` as `[{ collaboration, title }]`, one entry per linked collaboration the reader is in, in the order they were linked (`title` is `null` until the collaboration's title opens there); a reader in none of them gets `[]`. Only a post by the account that created the item counts, so only that account links it. An org member outside a collaboration reads the item, its description and its log as usual, and nothing on the board, in its history or in what the backend stores names that collaboration. A `collaboration` the caller is not in is refused before anything is written.
- **Viewers only read.** An organization's Viewers, and agents a Viewer registered, may list, read Ready and read logs. Every write they try is refused: "Viewers can only read this organization's board, not change it; nothing was written". `board.list` names the caller's `role` so a screen can hide what would be refused.
- An item's sealed content is at most 49,000 bytes; a larger one is refused before anything is sent, naming its size. An item whose sealed content does not open is left out of `board.list` and counted in `unreadable`.

**Storage.** Each board is an append-only JSONL event log, `<state root>/lattice/board/<board>.jsonl` (0600, fsynced per event), folded to the current record on read.
- **Torn and unreadable files.** A torn line, even one cut inside a multi-byte character, is skipped, and the next write starts a fresh line. A board file that exists but cannot be read is an error for every method. It is never treated as empty.
- **Compaction.** Past 4 MiB, and after that only once the file has doubled since the last rewrite, the board is rewritten from the snapshot just written (temp file, fsync, rename, directory fsync). Items closed more than 90 days ago are dropped. Every other item keeps its first record, its newest 50 changes and its newest 200 comments. A leading `mark` event carries the highest sequence number, so numbers never repeat.
- **Other CARs.** A board also shows the items of the CARs this one reaches directly. They are read-only here: an item is changed, commented on and read in full on the CAR that holds it, and a write naming one is refused with that CAR's name. Each daemon pulls them every 15 seconds beside the Lattice listings, over the peer-authenticated A2A method `car/latticeBoard`, and checks each item as it would a local write; an item that fails is dropped.
  - **Your own devices** see every board. The same work context has the same board name on every device, and a device's items show only on that board. They count as `mine`. A daemon knows its own devices only from the host endpoints published on the encrypted sync oplog, so this needs Parslee sync: a Parslee login and the same sync passphrase on each device (`car keys set PARSLEE_SYNC_PASSPHRASE`, then restart the daemon). Without it, another of your Macs is reachable only as a Lattice connection, and is treated as one: only shared projects, never `mine`. One device's answer carries at most 64 boards (500 items each): those with something to share, most recently changed first. When more are in use, the answer counts the rest in `omitted_boards`, and the receiving daemon logs a warning naming the device whenever that number changes.
  - **Another owner's CAR over a Lattice connection** sees only items in projects shared on that connection as `agents:<project>` (`lattice.connect.share`), from the board the connection serves: its verifying organization's, or the unbound personal board for a personal connection. The batch is sealed with the connection's key, and an item that looks like it contains a credential is withheld. These are never `mine`, even when both owners are `personal`.
  - **Never shadowing.** An id this board holds is always its own: another CAR's item with the same id is dropped. A pull that fails, times out or does not open clears what that CAR showed until its next good answer.
  - **Notices across a connection** name only items in projects this owner shares on that connection. A project name is just a string: the other owner's shared `web` is not consent to show them this owner's `web`, so that overlap shows as related here only.
  - **Over the Parslee relay** (a connection neither CAR can dial), items are not pulled: each side mails its batch, sealed, as relay method `latticeBoard` when it changes (checked on every relay pump, and again after a restart; an empty batch is sent only to clear items sent before), and the other keeps it until the next one or until the connection ends. Which batch the relay last took is kept per connection in `<state root>/lattice/board/relay-sent.json`, so a project unshared while the daemon was down is cleared after a restart. Same scope as a direct connection; one batch is at most 500 items and 160 KiB.
  - **Not covered yet.** A connection over the org stream is not covered. Nothing rides the encrypted sync oplog.
  - **Overlap found by a sync.** When a pull or a relay batch brings in another CAR's item that overlaps an open item here (both written before either CAR saw the other's), no write reports it. The daemon tells that item's live last writer instead, as the reserved node `car-board` (`no_reply`, kind `handoff`, through ordinary admission in that session's own context): once per pair, only when one of the two changed in the last 10 minutes, and never for a pair the write already reported. `car-board` cannot be an agent id.
  - Own devices are sent every board on every pull, with no check for an unchanged board.

**The code host.** A project can opt in to follow its repository (`car board reconcile add --project <p> --repo <checkout>`, which writes `<state root>/lattice/board/reconcile.json`). The daemon reads that repository's forge every 5 minutes, and within 30 seconds of the config changing. It uses the coder's PR seam: `az repos pr` for Azure DevOps or `gh` for GitHub, chosen from the checkout's `origin`, with the credential the checkout already uses.
- **What it changes.** For each open item in that project with `refs.branch`, it looks at the branch's newest pull request:
  - open: `review`, with `refs.pr` set;
  - merged: `done`;
  - abandoned: `abandoned`.
  - With no pull request, a branch that reconcile has seen on `origin` and that is now deleted makes the item `abandoned`; a branch not yet pushed leaves the item alone.
- **Main pipelines.** For each pipeline on the main branch (`--main-branch`, default `main`), the newest completed run decides: a failed run opens an `incident` titled `main is red: <pipeline>`, and a later successful run closes it. Cancelled, skipped and in-progress runs are ignored. Pipelines are Azure DevOps pipelines or GitHub Actions workflows (a timed-out or startup-failed workflow counts as failed). A repository on another forge is skipped with a log line.
- **It reports, never guesses.**
  - A merged pull request wins over a deleted branch, because Azure DevOps deletes the source branch on merge.
  - A forge or `git` error defers the item instead of reading as "no PR".
  - It acts only when what it observes changes, so an owner's own later edit is not overridden.
  - It changes an item only if it is still in the state it was read in.
- **How its writes look.** These are the one write that bypasses the owner rule. They are daemon-internal (no RPC can make them), and each appears in the history as `node: "code-host"`, `event: "code-host"`. Incidents it opens are owned by `code-host`: anyone may comment, and it closes them.

**The record**: `{ id, project, kind, title, owner, state, waiting_on?, refs?, note?, created_at_ms, created_by, updated_at_ms, updated_by, device? }`.
- `kind`: `work`, `incident` (main or a shared gate is red), `policy` (a standing rule), `ask` (a named person must act; requires `waiting_on`), `finding` (a defect nobody owns).
- `state`: `open`, `in_progress`, `waiting`, `review`, `done`, `abandoned`. `stale` is never stored or set: a listing reports `stale: true` for an open item untouched for 24 hours whose last writer is no longer live (never for one the operator or the code host last wrote).
- `refs`: `{ tickets?: [string], branch?: string, pr?: string, commits?: [string], runs?: [string], urls?: [string] }`, at most 32 entries per list of at most 512 characters. Tickets, branch and PR decide overlap, after normalizing (`#9875` = `9875`, case-insensitive; `refs/heads/` and `origin/` stripped from branches). A default branch (`main`, `master`) is never an overlap key. Only open items in the same project overlap.
- `title` is one line of at most 200 characters; `note` is the item's current state in at most 1,024 bytes, replaced on each change.

Claude Code and Codex reach these through `car-mcp --collaboration` as `board_list`, `board_upsert`, `board_transition`, `board_comment`, `board_history`, `board_claim`, `board_check_in`, `board_release`, `board_handoff`, `board_assign`, `board_accept` and `board_decline`, and the daemon's `/mcp` endpoint serves the same tools keyed on the session's `mcp:<peer-id>`. Setting a board up is not a tool. People use `car board items`, `car board history`, `car board setup` and `car board claim|check-in|release|handoff|assign|accept|decline`. The plugin's session-start hook (`car board-hook`) briefs each Claude Code session from `board.list`. `agents.session_brief` returns the same briefing as `board`, and `car codex` puts it in Codex's developer instructions.

#### `board.list`
- **Params**: `{ project?: string, state?: string, kind?: string, mine?: boolean, related_to?: string, include_closed?: boolean, ready?: boolean, limit?: integer, org?: string, account?: string, api_base?: string, unless_changed_since?: integer }`.
  - `unless_changed_since` is a `change_seq` an earlier reply for the same organization's sealed board returned. While the board's sequence still equals it, the reply is `{ self, org, sealed: true, unchanged: true, change_seq }` and no item is read: one request to the backend instead of every item page. A poller keeps what it last read. The sequence moves with every structural change (an item made, claimed, moved, handed off, assigned or commented on, an edge, a new key), but not with the clock: a held item going stale or turning ready by time, or a key reaching this device later, moves nothing, so a poller should read in full now and then, and should not keep a sequence from a reply that counted `unreadable` items. On an account board the parameter is accepted and changes nothing, and the reply carries no `change_seq`. A value that is not a non-negative integer is refused.
  - `ready: true` lists only the items ready to pick up (an organization's sealed board only; elsewhere it is refused, since nothing there is claimed).
  - `related_to` is a ticket, branch or PR — bare, or prefixed `ticket:`, `branch:` or `pr:` — or an item id (its tickets, branch and PR). It matches items sharing any of them.
  - Done and abandoned items older than 14 days are left out unless `state` names one or `include_closed` is true. `mine` keeps the items the row marks `mine`. `limit` is 1–500 (default 100).
  - `org`, `account` and `api_base` are for the operator's host client only, here and on every board method.
- **Returns**: `{ self, owner, count, total, items: [record + { mine, written_by_you, last_writer_is_you, stale, remote?, related?: [{ id, title, owner, state, updated_by, device?, shared, remote? }] }], not_in_view: [{ device, reason }], unreadable? }`, newest change first. Every row carries `lane`, the Board's lane for it, so each item is in exactly one: `settled` (done or abandoned), `waiting_on_person` (`waiting`, or a handoff or assignment pending on the person it names), `coming_up` (an open item on an organization's board that nobody holds: work nobody has started), or `under_way` (every other item: in progress, in review, stale ones included, and every open item on an account board). A row's `owner` is who has the item now: the account holding its claim, else its creator while nobody holds it, and empty while it is `stale` on an organization's board (nobody is named for a stale item); the record's own creator still decides who may change it. On an account board nobody holds an item, so it is the account that wrote it. Another CAR's row never carries a holder. `mine` is an item the caller's account changes: the one holding it, or its creator while nobody holds it (on an account board nobody holds an item, so these are the account's items). `written_by_you` says every word in the item is the caller's account's: only such a `policy` relays the owner's rule, and the briefing marks it "your account". A row without `written_by_you` (an older daemon) is read by `mine`. `not_in_view` names each own device whose items this board may not show: "no board fetched from it" (no direct answer and no fresh relayed one), "this board may be among the N boards it left out", or "only the newest of this board's items came from it" (cut to fit one relay mail). With no roster known it is one entry with `device: null` and the reason (`no_session`, `no_passphrase`, `pending` or `local_journal`, as `fleet.composite`'s `roster`). The session briefing names them before its item list. `remote` is this CAR's name for the CAR that holds the item; another CAR's item is `stale` when it has not changed for a day, since its sessions are not visible here. `owner` is the account the caller writes as; `total` counts matches before `limit`; `shared` names the overlapping refs (`ticket:8292`, `branch:fix/x`). On an organization's sealed board a row's `created_by` and `updated_by` name a session only where the content's signature vouches for it: `updated_by` when the content opened verified, and `created_by` when, in addition, the content was written only by the account that created it: once another account has written it, `created_by` stays `device:<id>` from then on, even after the creator writes again. Otherwise each is `device:<id>`, the device of the latest content write, which after another account's write is not the creator's (the backend records no creating device for an item; `board.history`'s `created` row still names the creating account in `by`). When the item's newest change is a claim, status move, check-in or other ownership action after its latest content write, `updated_by` instead names whoever made that change, as on the file board: the session its signed action record names (the `node` of that row in `board.history`), else `device:<id>` of the device that made it. A holder's check-in counts as such a change. Reading such an item costs one item-log read, so a list reads one log per claimed or checked-in item, up to 8 at once; when that read fails the row is still listed and `updated_by` names the content writer as above.
  - **On an organization's sealed board** the reply also carries `change_seq` (the board's change sequence, read before its items, so a write landing during the read shows as a higher sequence on the next one), `sealed: true` and `role`: `admin` (an org Owner or Admin), `member`, `viewer`, or the issuer's own word lowercased, as the sign-in reported it (`null` when it named none; the backend still decides every write from the live membership). Each row also carries `ready`, `holder` (absent while nobody holds it or it is stale), `free_to_take`, `labels`, `description?`, `pending` (`{ kind: "handoff" | "assignment", from, to, at_ms }` or `null`), `check_in_ms` and `last_check_in_ms` (while someone holds it), `version`, and `came_up_in`: `[{ collaboration, title }]`, one entry per collaboration the item came up in that the caller's account is in, `[]` when there is none (it was a single object before CAR-984).
  - An organization's sealed board is read from this CAR's copy of it, one per account, kept current from the board's change feed: a read whose board has not changed costs one request to the backend, and one that has reads only the items that changed. When the backend refuses or rate-limits the read, the reply is the last copy read, with `stale: true` and `stale_reason` (one sentence), never an empty board; with no copy yet, the read fails as before. The same holds for the `unchanged` reply.

#### `board.upsert`
- **Params**: `{ id?: string, project?: string, title?: string, kind?: string, state?: string, waiting_on?: string | null, refs?: object, note?: string | null, description?: string | null, labels?: [string] | null, blocked_by?: [string], collaboration?: string, org?: string }`.
  - Without `id` it creates an item: `project` and `title` are required, `kind` defaults to `work` and `state` to `open`.
  - On an organization's sealed board, an `id` no item has yet, given with `project` and `title`, creates the item under that id (1–128 of `[A-Za-z0-9._-]`), and the result returns it. An `id` without them is the usual "no such item".
  - `description` says what the work is (at most 2,048 bytes; `null` or `""` clears it). `labels` are free-form, one line each, at most 32, replaced whole (`null` or `[]` clears them; a repeat is kept once).
  - `blocked_by` (an organization's sealed board only) names up to 20 items that block this one; each is linked after the write, keeping the links it already has. An item the board does not have, or a link that would make a loop, is refused naming the link, with the item and any earlier links written.
  - `collaboration` (an organization's sealed board only) is the id of a collaboration this CAR's owner is in where the item came up: see "Where an item came up" above. With only `id` it links an item that exists without changing it. Only the item's creator's post counts; for anyone else allowed to write the item the write still lands and the reply carries `came_up_in_error`.
  - With `id` it changes an item the caller's account owns, replacing only the fields given. `refs` is replaced whole. `null` or `""` clears `waiting_on` or `note`.
  - An `owner` field, an unknown field, or `state: "stale"` is refused. Changing another account's item is refused with a message naming its owner and last writer.
  - An open `ask` must name `waiting_on`; one being closed may clear it.
  - **An ask reaches the person.** When a write leaves an open `ask` waiting on `human:<name>` that has not been sent yet, the daemon sends the person a `question` peer message from the writing session, with the item's title and note. It uses the human-request ledger, approval mirroring and admission any message to a person goes through, so it reaches them in `lattice.requests`, CarHost, iMessage or Slack. The request id is recorded on the item (`asked`, set by CAR only). The result's `asked` is the send's result (`request_id`, `outcome: "awaiting_human"`, and `answer_token` for the asker alone), or `{ to, queued: false, reason }`: the operator wrote it (no peer address), the person is not a Lattice node here, or the writing session is bound to an organization, which cannot reach a person yet. An organization's sealed board sends and records an ask the same way. Editing the ask does not send it again; changing `waiting_on` to someone else clears `asked` and asks them. The answer goes to the asking session (`lattice_wait` with the request id). The board item gets a comment saying who answered and where the answer went, never the answer itself.
  - A board holds at most 5,000 open items, counting reopened ones.
- **Returns**: `{ item, overlaps: [{ id, title, owner, state, updated_by, device?, shared, remote? }], notified: [{ item, node, to?, remote?, queued, reason? }], asked?, hint?, blocked_by?, came_up_in_error? }`. On a sealed board `item.came_up_in` lists every linked collaboration the caller is in, the new link included once its post is queued, and `blocked_by` lists the links made. Overlap includes the other CARs' items this board shows; the notice for one goes to `<its last writer>@<that CAR>`, under ordinary cross-CAR message admission (a connection's shares included).
  - `overlaps` lists only items that became related with this write; a later change that keeps an overlap does not report it again.
  - For each, `notified` says where the `handoff` went: the other item's last writer when it is live, else the person's `inbox:<org>` on an organization's board. Otherwise it is `queued: false` with the reason: the caller is that item's last writer too, the operator wrote (no peer address), the last writer is not live, or the per-write cap was reached.
  - At most 5 notices go out per write; the remaining overlaps show as `related` only.
  - A notice sent when an item is written names that item's last writer and the device it was written on (`by <session> on <device>`; `an unrecorded device` for an item from before devices were recorded), so a session on one of the owner's devices can tell that the overlapping work is on another. A notice sent when another CAR's item is pulled in names the CAR that holds it instead (`<title> on <CAR> (…, by <session>)`).
  - Delivery runs in the background: `queued: true` means the send started, not that it arrived. A refused delivery is logged by the daemon.

#### `board.transition`
- **Params**: `{ id: string, state: string, note?: string | null, waiting_on?: string | null, org?: string }`.
- Moves an item the caller's account owns to `state`, replacing `note` and `waiting_on` in the same event when given. Any other field is refused (use `board.upsert`).
- **Returns**: as `board.upsert`.

#### `board.claim`, `board.check_in`, `board.release`, `board.handoff`, `board.assign`, `board.accept`, `board.decline`
- **Params**: `{ id: string, org?: string }`, plus `check_in_ms?: integer` (1 to 604,800,000) on `board.claim` and `board.check_in`, `to: string` on `board.handoff`, and `to: string | null` on `board.assign`. Any other field is refused.
- An organization's sealed board only: on any other board each is refused, naming `board.transition`.
  - `board.claim` takes an open item, a stale one, or one still blocked (which simply is not in Ready). It becomes the caller's (`holder`, state `in_progress`) and leaves everyone else's Ready. A claim that loses to another is refused naming who holds the item; one on an item assigned to someone else names them.
  - `board.check_in` moves the holder's `last_check_in_ms` forward.
  - `board.release` leaves the item open with no holder: back in Ready unless something unfinished blocks it.
  - `board.handoff` offers the holder's item to the account `to`. The sender keeps it, with `pending: { kind: "handoff" }`, until `to` accepts.
  - `board.assign` asks the account `to` to take an unowned item. It stays unowned and out of Ready, with `pending: { kind: "assignment" }`, until they answer; `to: null` clears a pending assignment.
  - `board.accept` and `board.decline` answer a handoff or assignment naming the caller; anyone else's answer is refused. Accepting makes the caller the holder. Declining a handoff leaves it with its sender; declining an assignment puts it back in Ready unless something unfinished blocks it.
  - Done and dropped are `board.transition` to `done` or `abandoned` (`dropped`): either takes the item out of Ready and frees what it blocked.
- **Returns**: `{ item, notified }`: the item's row as `board.list` shows it, and the people told, as for a write (see "People hear about changes to their items" above). `board.claim`, `board.release` and `board.accept` tell the item's creator and its previous holder when they change who holds it and someone else made the change; `board.check_in`, `board.handoff`, `board.assign` and `board.decline` tell nobody, and `notified` is `[]`.

#### `board.comment`
- **Params**: `{ id: string, body: string, org?: string }`. `body` is at most 2,048 bytes.
- Appends a remark to any item on the caller's board, whoever owns it. It never changes the item. An item closed more than 90 days ago (which compaction drops) refuses new comments.
- **Returns**: `{ id, commented: true, seq }`. On an organization's sealed board it also carries `notified`, as for a write (see "People hear about changes to their items" above), and `checked_in` when the commenter holds the item.

#### `board.history`
- **Params**: `{ id: string, org?: string }`, or `{ ids: string[], org?: string }` for several items at once (never both).
  - `ids` names 1 to 50 items. On an organization's sealed board they are read from one open of the board (the open's key and directory reads are made once, not once per item), at most 4 logs at a time, and nothing is retried: a refusal, the backend's rate limit included, comes back at once in that item's row. A screen showing many cards reads their trails this way rather than one call per card, which spends the device's budget with the backend. It returns `{ self, trails: [{ id, count, truncated, events } | { id, error }] }`, one row per id in the order given; `events` is as below, and one item that cannot be read leaves the others read. The item's own record is not included; `board.list` has it.
- **Returns**: `{ self, item: record + { mine }, count, truncated, events: [...] }`, oldest first, at most the newest 500 events (`truncated` counts the older ones left out; compaction may already have dropped more). A change is `{ seq, at_ms, node, event: "created" | "updated" | "transition" | "code-host", from_state?, state, note, waiting_on, refs, title, device? }` (`code-host`: written by the code-host reconciler, `node: "code-host"`); a comment is `{ seq, at_ms, node, event: "comment", author, body, device? }`. `node` is the session that wrote the event, `author` the commenter's account, `device` the CAR it was written on.
  - On an organization's sealed board every entry of the item's log is a row, oldest first: each change also names its `action` (`created`, `updated`, `claimed`, `takeover`, `checked_in`, `released`, `handoff`, `assigned`, `assignment_cleared`, `accepted`, `declined`, `status_changed`), the account `by`, and where they apply `to` (who a handoff or assignment named), `previous_owner` (who a takeover took it from) and `status`. A comment's row has `action: "noted"`. A change row's `title`, `note`, `waiting_on` and `refs` come from the sealed record its writer added to the log: the first record whose note was added after the change, by the same account and device the backend recorded for it. A record always follows its change, so one added before the change is never its record, and a record another member adds never fills or relabels a change while both members are on the board. Erasing a member gives every change and note of theirs the same account and device (`former_member`), so once two writers are erased their records are no longer told apart by who added them: an erased writer's change with more than one such record after it is shown with none, as `writer: "former_member:ambiguous"`, `node: "device:former_member"` and null fields, because CAR adds exactly one record per change. What remains: a member who is later erased too can still blank an erased writer's change this way, and where the erased writer left no record of their own (an older CAR, or a record that failed to post), a record the other added after the change still fills it. `writer` carries that record's open code, as a comment row's does: `verified`, `unverified:<why>` (for example `unverified:revocation_stale` while no fresh revocation list is held) or `former_member:verified` / `former_member:unverified` for an erased member's, whose changes stay readable, or `former_member:ambiguous` for an erased writer's change with more than one candidate record. `node` names the record's session only when `writer` is `verified`, and is otherwise `device:<id>`, the device the backend recorded. A change with no record from its writer (an older CAR wrote none) has `writer: "unverified:no_record"`, that device, and null fields on a create or update row. A comment's row carries `writer` as its note opened, and names its session only when that is `verified`.

#### `board.setup`
- **Params**: `{ org: string, confirm: string }`. Host credential only: the person's own CAR (`car board setup --org <org>`, which asks them to type the org). `confirm` repeats `org`; anything else is refused with nothing changed. Any other caller, a supervised agent or a Claude Code or Codex session included, is refused: "A person sets up an organization's shared board, from their own CAR: `car board setup --org <org>`. An agent or a Claude Code or Codex session can't, because it can't be undone; nothing was changed."
- Sets up the organization's sealed board (see above): a fresh key whose id is recorded, signed by this device, in the backend's key history, then a copy for each device in the org's verified device directory, this device first. From then on every CAR in the org uses the sealed board. Of two CARs setting it up at once, one makes the key and the other reports it as already set up. The new key and its signed statement are kept on this device (owner-only) until every copy is stored. A setup cut off before it hears back keeps both: the next call on that board finishes the copies when the statement landed, and the next `board.setup` sends the same statement again when it did not. The kept key is dropped only when the backend's history shows another key for that epoch. One setup runs at a time per organization on a CAR. Nothing else ever does this, so reading a board never sets one up.
- A board already set up is reported and left unchanged. A CAR that signs in as an organization's agent account cannot set one up: the refusal says a person's CAR must. An organization this CAR holds no login for is refused.
- **Returns**: `{ org, created, epoch, message }`. `created` is true when this call made the key. `message` says this CAR uses the sealed board at once, and that other members' CARs may still write to the file board until their check with Parslee succeeds (the once-a-minute check above). That bound holds only while the backend answers: a CAR that can't reach it keeps its remembered answer, and keeps writing to the file board, until a check does.
