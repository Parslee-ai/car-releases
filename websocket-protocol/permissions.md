### permissions

#### `permissions.status`
- **Params**: `{ domain: string, target_bundle_id?: string }`
- **Returns**: `{ domain, status, target_bundle_id }`. `domain` is one of `browser` | `contacts` | `calendar` | `mail` | `accessibility` | `screen_capture` | `automation` | `camera` | `microphone` | `health_read` | `photos` | `reminders` | `full_disk_access`; any other name is refused with `invalid_domain`. `status` is one of `granted` | `denied` | `not_determined` | `restricted` | `not_applicable` | `restart_required` | `signature_changed` | `unsupported` | `not_responding` | `unknown`. `unsupported` means the state could not be read without prompting — "can't tell" — and is distinct from `not_determined`, which is the OS saying the user was never asked, so only `not_determined` means a request-access prompt is the next step. On macOS every check answers within 2 s; one that has not answered by then reports `not_responding` — distinct from `denied` and `unknown`. For `automation`, `photos` and `reminders` (all three Apple Events checks) it means the target app — Photos.app or Reminders.app for the latter two — is running but not answering Apple Events, and its access may already be granted (the fix is to quit and reopen that app); for other domains the check itself did not answer, for example while a macOS privacy prompt is pending. A check that never returns gives way to one fresh check after 30 s, so checking again works without restarting the daemon; at most three checks per target (bundle IDs compared case-insensitively) can be stuck at once, and once eight checks in all are stuck past their deadline no new check starts until one returns: a call that would start one answers `not_responding` at once. Checks that start together before any of them is overdue are not refused, so a burst of concurrent checks for different apps can briefly leave more than eight stuck. On macOS every domain is a real, non-prompting query: `calendar` (EventKit, which can additionally return `write_only`, the macOS-14 write-only calendar grant) and `contacts` (Contacts framework, which can additionally return `limited`, access to only the contacts the user picked) are read by the helpers that read calendars and contacts, and report `unsupported` when that helper cannot answer (it is built on first use, which needs the Xcode Command Line Tools, and may not run from a sandboxed process) or answers with a status this version does not know; `camera` and `microphone` read `AVCaptureDevice` authorization in the daemon's process; `full_disk_access` opens, and immediately closes, a file only Full Disk Access can open (Safari's `Bookmarks.plist` or the Messages `chat.db`, the files the integrations read, falling back to the system TCC database only when neither exists), reporting `denied` when macOS refuses it (it never prompts for this grant). The `automation` domain uses `target_bundle_id` for a non-prompting, target-specific Apple Events readiness check; with no target it reports `unsupported`, because Automation grants are per app, and macOS answers the check only while the target app is running, so a target that is not running reports `unsupported` too. `photos` and `reminders` are that same check for `com.apple.Photos` and `com.apple.reminders`, because the photos and reminders integrations drive Photos.app and Reminders.app over Apple Events: `unsupported` while the app is closed, the real grant once it runs (the integration launches it and its first use asks). `health_read` reports `unsupported` on macOS: HealthKit has no non-prompting status query. `mail` reports `not_applicable` on macOS even though `mail.*` drives Mail.app over Apple Events: to check Mail's grant, query `automation` with `target_bundle_id: "com.apple.mail"`. Off macOS, `photos`, `reminders` and `full_disk_access` are `not_applicable`.

#### `permissions.request`
- **Params**: `{ domain: string, target_bundle_id?: string }`
- **Returns**: `{ domain, status, target_bundle_id }`, with `status` from the same set as `permissions.status`. On macOS this does not prompt: it runs the same check as `permissions.status` (for `calendar` and `contacts` too), answers within 2 s, and can report `not_responding` the same way.

#### `permissions.explain`
- **Params**: `{ domain: string, target_bundle_id?: string }`
- **Returns**: `{ domain, status, message, fix, target_bundle_id }`, with `status` from the same set as `permissions.status` (for `calendar` and `contacts`, the same helper answer) and `fix` `null` when there is nothing to do. On macOS it answers within 2 s; a check that has not answered reports `not_responding`, and for `automation`, `photos` and `reminders` its `message` and `fix` say the target app (Photos or Reminders when no target is given) is not answering Apple Events and to quit and reopen it, while for any other domain they say the check itself did not answer and to check again.

#### `permissions.domains`
- **Params**: `{}`
- **Returns**: `string[]` — all known permission domain names
