### declagents

**In-daemon declarative agents.** A declarative agent is pure data — an identity (system prompt), a tool **allowlist** (names of tools the daemon already exposes), an optional deny list, a standing goal, an optional deterministic `goal { check, max_iterations }`, and scenarios (test cases). The daemon runs it with a generic model→tool loop: there is no command to spawn, so a non-developer installs nothing. Built by the coder→agent loop (an `agent`-kind project: `coder.start { project }` synthesizes a "scenarios pass" contract, the build loop generates the spec and drives its scenarios green in-daemon, and `coder.approve_merge` registers it). The project's committed `agent.json` and `scenarios.json` are versioned build output; the daemon runs the separately registered spec in `declagents.json`, so editing only the project file does not update the active agent. Rebuilding and approving registers the updated spec. This is a **parallel registry** to the supervised `agents.*` — a declarative agent has no command, so it never travels through the supervisor's absolute-path validation. `agents.list` read-merges declarative entries tagged `kind:"declarative"` (carrying `enabled` instead of process status), `capabilities:["chat"]`, and `description` (the trimmed standing goal when nonblank, otherwise the trimmed identity); hosts can call `agents.chat` with the declarative agent id and receive the normal `agents.chat.event` stream from the in-daemon runner. `agents.chat.cancel` is honored in-daemon via a local cancellation flag; the runner stops at the next model/tool/goal-check boundary and late frames are suppressed once routing is dropped.

**Security**: the tool allowlist is strict — an empty/typo'd allowlist exposes ZERO tools, never the full set — and the daemon's inspector chain hard-enforces beneath it. A declarative agent can only call tools it was granted, gated by the same policy as the coder.

- `declagents.list` — **Params** `{}`. **Returns** `{ agents: [{ id, name, description, kind:"declarative", enabled, capabilities:["chat"], tools, goal?, inference?, scenarios }] }`; `description` is the trimmed standing goal when nonblank, otherwise the trimmed identity. A missing `declagents.json` is an empty list. A file that exists but cannot be read or parsed is an error naming the file, never an empty list: `declagents.list`, `declagents.get`, `declagents.invoke`, `declagents.run_scenarios`, `declagents.route`, `declagents.route_split` and `coder.projects.create` with `existing_agent_id` return that error, and every `declagents.*` mutation and `coder.approve_merge` registration refuses rather than write over the damaged file, which stays as it was for the operator to repair. `agents.list` still answers with every supervised agent and leaves out only the declarative rows, logging the error, so call `declagents.list` to tell "no built agents" from "could not read them". `discovery.resolve` drops declarative agents from its candidates and logs the error, the same way it skips a provider that times out. `agents.chat` to an id that is not attached keeps its "agent `<id>` is not attached to this daemon — …" refusal with the registry error appended.
- `declagents.get` — **Params** `{ id: string }`. **Returns** the full `DeclarativeAgentSpec` plus `registry_path`, the exact daemon-resolved file that supplied it. `registry_path` is response metadata and is never written into `declagents.json`. Builder-created specs may include `builder_draft: { template_id, name, responsibility, example, access, cadence, delivery, privacy, mail_access?, working_folder? }`; `mail_access` (default `false`) records that the person allowed read-only Mail, and `working_folder` (default empty, meaning `~/CAR Agents/<agent name>`) the folder they chose. Both are omitted when unset, so older drafts keep their exact JSON and fingerprint. A spec may carry `working_folder: string`, an absolute path: the folder the agent keeps between runs (see `declagents.invoke`). It is optional; a spec without it runs in a scratch folder as before. A Build an Agent build (one with a `builder_draft`) always records one, and refuses a folder that is the disk root, the home folder or above it, or inside CAR's state root; edited specs additionally include `previous`, the immediately preceding full spec with its own `previous` cleared. Both fields default absent, so legacy and hand-authored specs keep loading. A spec may also carry `inference: { model: string, provider: string, reasoning_effort: "low" | "medium" | "high" }`. The whole block defaults absent for adaptive routing; when present, a bare model is qualified as `<provider>/<model>`, an already-qualified model must agree with `provider`, the route is strict, and the effort maps to the provider's native coarse reasoning control. On Claude and OpenAI reasoning models the runner adds the reasoning budget to `max_tokens`, capped at the catalog output limit (car#1989). The spec also includes `context: "car" | "self"` — who manages the agent's conversation context (see `declagents.invoke`). It is optional on disk and defaults to `"car"`, so a spec registered before the field loads unchanged, but the response always carries it. The optional structured `cadence` is `{ trigger: "interval"|"cron"|"manual", schedule, timezone?, phrase }`; `phrase` preserves what the user entered, while `trigger` and `schedule` are the result from `schedule.suggest`. Its absence means no cadence was requested.
- `declagents.remove` — **Params** `{ id: string }`. **Returns** `{ removed: bool }`.
- `declagents.set_enabled` — **Params** `{ id: string, enabled: bool }`. **Returns** `{ ok: true }`. A disabled agent stays registered but refuses to run.
- **An unparseable registry file is never overwritten.** `declagents.remove`, `declagents.set_enabled` and `declagents.revert` error, and leave the file untouched, when the registry file exists but does not parse ("`<path>` is not a valid declarative-agent registry (…); refusing to overwrite it — fix or move the file"); reads still return an empty list.
- `declagents.revert` — **Params** `{ id: string }`. **Returns** `{ reverted: true, agent: DeclarativeAgentSpec }`. Restores the spec's one retained `previous` version atomically under the same id, without model generation or another build. The outgoing version becomes the new one-level `previous`, so another revert toggles back while history stays bounded. Errors without retained history. This is a host-lifecycle mutation and uses the same host-authority gate as remove and enable/disable.
- `declagents.run_scenarios` — **Params** `{ id: string }`. **Returns** `{ id: string, passed: integer, total: integer, all_passed: bool, can_revert: bool, results: [{ index: integer, input: string, expect: string, output: string, passed: bool, turns: integer, tool_calls: integer, error?: string }], run_error: string | null }`. Top-level `passed` is the count of passing cases; each row's `passed` is that case's boolean verdict. `index` counts from 1; `run_error` is `null` when the suite ran. Runs every scenario currently stored on the registered spec through the same declarative runner and case-insensitive expected-substring evaluator used before registration. For a spec with `working_folder`, each scenario runs in its own fresh throwaway copy of that folder's files (hidden files included; a link that leads inside the folder is copied as a link to the same place in the copy, so tools treat it as in a real run, and one that leads outside or nowhere is left out), so they see the person's inputs and never change the real folder; a folder with more than 1,000 files, more than 64 MB, folders more than 16 levels deep, or anything unreadable is refused with an error naming the problem rather than copied in part. `run_error` reports suite-level infrastructure failure; completed per-case evidence remains in `results`. It does not modify the agent.
- **Admission on `declagents.invoke` / `.run_scenarios` / `.route` / `.route_split`.** All four reach the same in-daemon declarative executor, so all four pass the admission `agents.chat` and `agents.message` apply when the caller is an *agent* rather than the host: the per-recipient channel guard (dedupe inside 10s, 20 per sender per minute) and the `AgentPermissionPolicy` decision at the `read_only` tier. Gating chat while leaving these open would just make them the way around it. For `route` and `route_split` the check is applied to the **chosen** agent, not the requested need, so a routed run is graded against the agent that actually ran. The host is exempt.
- `declagents.invoke` — **Params** `{ id: string, input: string }`. **Returns** `{ output, turns, tool_calls, model_served?, model?, error?, goal? }`; `model_served` is the serving catalog id and `model` is its temporary compatibility alias for older CarHost Work clients. A saved `inference` selection is applied to Work, direct, routed, and chat invocations and cannot be replaced by a per-call model parameter; host availability and policy may still refuse or narrow it. Without the block, routing remains adaptive. Runs the agent on `input` entirely in-daemon (no process), bounded by a turn cap, with file tools rooted in an ephemeral scratch workspace — or, when the spec has `working_folder`, in that folder, created if missing and kept after the run. A folder agent may read and write only inside its folder: file tools (reads as well as writes) refuse a `path` that is not text and paths outside it, a listing or search with no `path` covers the folder, judged by where a path really leads, so a link already inside the folder that points out is refused, left out of `list_dir`, never walked by `find_files` or `grep_files`, and any hit that resolves outside is dropped; `write_file` and `edit_file` refuse a `.csv`, `.xlsx`, `.xlsm` or `.docx` file (any letter case; reading one is fine) with "Use append_spreadsheet_row / fill_word_template to change this file."; a write or edit to a file hard-linked from somewhere else is refused ("This file is linked from somewhere else, so the agent won't change it."), and the spreadsheet and Word tools replace a file rather than write through it, so a hard-linked file elsewhere keeps its contents; and it runs no commands — a build never gives it `shell` or a goal check, and a spec edited to add either is refused with an error — because a command could read files anywhere the person can. Its executor still write-confines any child to the folder and denies it Apple Events. A folder agent is not given the Parslee platform tools. The folder is resolved (symlinks followed) and refused if it is, or holds, the home folder or the disk, or lies inside CAR's state root. A folder agent is also offered `append_spreadsheet_row` (adds one row to an `.xlsx` first visible sheet or a `.csv`, creating it with `headers` when missing; `values` is a list in column order or an object keyed by header; the row goes after the last row holding a value, writing into an existing row below it that holds only formatting or formulas, keeping each cell's style and never writing over a formula, and refusing when that row is hidden or zero height, when a column it writes is hidden or zero width (including by a `sheetFormatPr` `defaultColWidth` or `baseColWidth` of 0 or less without its own visible width), when an empty cell it reuses has a number format (read from the workbook's styles) that would hide the value, can't be read, or picks its section by a condition such as `[>100]` (a numeric 0 also needs a `0` placeholder, a literal or `@` in its section: `#` alone shows it blank), when it would write a numeric 0 into a sheet that shows zeros as blank (`sheetView showZeros="0"`), when a conditional-formatting rule covering a written cell applies a number format (its `dxf` in the styles) that would hide the value or can't be read, or names an unknown `dxfId` (rules that only change colours, fonts or fills are fine), or when the sheet hides rows by default (`sheetFormatPr zeroHeight`, or a `defaultRowHeight` of 0 or less); text starting with `=`, `+`, `-` or `@` is an inline string in `.xlsx` and gets a leading `'` in `.csv`; a `.csv` field holding a comma, quote, line break, `;` or tab is quoted, and a row is appended with the file's own line ending (`\n`, `\r\n` or `\r`); a number with more than 15 significant digits is refused, asking for it as text (Excel would round it); a row whose values are all empty or null is refused with "There's nothing to add: every value is empty.") and `fill_word_template` (copies a `.docx` template to `output`, replaces its `{{name}}` placeholders including ones Word split across runs (text is found by the WordprocessingML namespace, whatever prefix the file uses; every `{{…}}` counts, whatever its name, and names match ignoring case, surrounding and repeated spaces, and typographic apostrophes, quotes and non-breaking spaces), never overwrites the template, refuses an existing `output` unless `overwrite: true`, saves nothing and names them when any placeholder has no value, refuses a value containing `{{` or `}}`, reads the filled document back before saving and saves nothing if any `{{…}}` remains, and returns `{ output, filled, unfilled, unused_values }`); both take paths relative to the folder, used exactly as given (a path that starts or ends with a space is refused, never trimmed), and refuse a spreadsheet, template or output that is a link ("This file is a link. Point the agent at the file itself."), run one at a time in the daemon (so concurrent appends each get their own row), ignore cell references past Excel's last column, refuse to append past Excel's last row (1,048,576), refuse a template with more than 5,000 placeholders (counted after split runs are joined), and refuse — changing nothing — a spreadsheet or template outside the shape real producers write, read with a namespace-aware XML reader and matched by namespace (XML comments, CDATA, processing instructions, a rebound namespace prefix, an element named like the edited ones in another namespace or position, a `dimension` with children, rows, cells or cell contents other than SpreadsheetML `row`/`c`/`v`/`f`/`is`, a `{{` outside paragraph text, or a placeholder split by anything but run formatting), asking the person to open and re-save it in Excel, Numbers, Word or Pages, also refuse, changing nothing, a sheet with merged cells, an Excel table, a PivotTable (linked from the sheet's relationships) or a filter (a sheet `autoFilter`, or the workbook's `_xlnm._FilterDatabase` name for that sheet), asking the person to unmerge the cells, convert the table to a normal range or turn off the filter, a CSV whose quotes don't balance or whose header line has a `;` or a tab outside quotes, a value or header holding a control character other than tab, line feed and carriage return or any other character a spreadsheet or Word document can't hold (rather than dropping it), a value named by a header that appears more than once in the sheet or two named values that land in one column, a sheet with a repeated row number, any part with more than one root element, and a `.docx` without its `[Content_Types].xml` or a package relationship naming `word/document.xml` as the main document. A line break or tab in a Word value is written as a Word line break or tab in the same run. Both tools are `sandbox_edit` tier. When the spec allowlists `mail_inbox`, `mail_search` or `mail_message_body`, it gets those three local Mail.app reads and nothing else (the spec's tools decide this, not `builder_draft.mail_access`, so a spec registered over RPC with those tools reads Mail): a saved agent is never offered `mail_draft` or `mail_send`, and calling any other Mail name is refused before Mail is reached. For a spec with `working_folder`, a run in which `append_spreadsheet_row` or `fill_word_template` returned an error on a file (its `path`, or `output` for a template) that no later call of the same tool on the same file cleared ends with `error: "The agent stopped without finishing: <the tool's error>"` whatever the final answer says, and a scenario with that error fails; other tools, and specs without a folder, are unchanged. The run's system prompt names the folder and, for Mail, says the agent can never write drafts, send, reply or forward. When the spec has a `goal`, CAR runs `goal.check` in that same workspace after each pass, re-drives the agent with the verifier reason until the check exits 0, and returns `goal: { check, max_iterations, iterations, met, grounded, last_exit_code, last_reason }`; if the check never passes, `error` is `goal_not_met ...`. **Context policy.** With the spec's `context` at its default `"car"`, the run's growing history is compacted before each model call to fit the context window of the model that ran the turn (three quarters of it, measured on the provider's reported prompt size once there is one), pinning the identity and the original input and leaving the `[history compacted: ...]` system notice — the same compaction the assistant and coder loops use. With `context: "self"` CAR never compacts and the spec owns the transcript. The window is re-read after every call from the model that served it, so a mid-run fallback to a smaller model is compacted against the smaller window. A model absent from the catalog (or a catalog row whose `context_length` is `0`) has no known window. If the run never knew one, compaction is disabled for it and the daemon logs `compaction disabled: unknown context window for model <id>` once per invocation; if an earlier turn did know one, that budget is kept — losing it would leave the run unbounded over a routing detail — and the daemon logs `model <id> has no known context window; keeping the last known budget of N tokens` once instead. An unrecognized `context` value is not a parse error — it warns and falls back to `"car"`, so a hand-edited typo can never unregister the agent.
- `declagents.route` — **Params** `{ need: string, invoke?: bool, from?: string, visited?: string[] }`. **Returns** `{ chosen, candidates: [{ id, name, score, similarity, success_rate, edge_weight }], next_visited, invoked, result? }`. Capability-similarity routing: embeds `need` (query-side) and each eligible agent's capability surface (name + identity + standing goal + tools), then ranks by `score = 0.7·similarity + 0.3·success_rate + 0.2·edge_weight` (the AgentNet milestone, see `docs/proposals/agentnet-self-organization.md`). `success_rate` is the agent's learned success prior: the Beta(success+1, fail+1) posterior UCB (the `car-memgine::utility` substrate) over the raw success/failure counts persisted in `~/.car/routing.json` — folded across BOTH the agent-id key (outcomes recorded by `declagents.route`/`invoke`) and the agent's `agentdns://local/agent/<id>` identifier key (outcomes recorded by `discovery.report`), so `declagents.route` and `discovery.resolve` score the same agent identically (one agent, one score — H2 Part 2, `docs/proposals/h2-builder-discovery-acceptance.md`). The cold-start posterior mean is exactly the neutral `0.5`; the persisted EMA field remains in `declagents.routing_stats` for display but no longer drives ranking. Similarity dominates so cold-start ranking is correct, the prior nudges toward agents that actually finish work. `similarity` itself blends cold-start similarity (need vs the agent's static capability text) with learned similarity (need vs the agent's reinforced capability centroid, `0.6·cold + 0.4·learned`) once the agent has succeeded at least once — so an agent's effective profile drifts toward the needs it actually handles well. **Forward op:** when `from` (the delegating agent) is set, it is excluded from candidates and a learned directed edge `from → candidate` adds `edge_weight` to the score — so a proven delegation path re-ranks peers. `visited` is the set of agents already on the routing path (DAG/cycle guard): all are excluded, and routing refuses the next hop once 4 agents are already on the path (a chain runs at most 4 agents before terminating). To walk a Forward chain, the next hop passes `from = chosen` and `visited = next_visited` (the response echoes `next_visited = visited + [chosen]`, so each hop strictly grows the path and the hop cap always terminates it). `score` is an unbounded ranking score (a fully-forwarded agent can exceed 1.0), not a probability — only the order across candidates is meaningful. `candidates` are the top 3 ranked descending. With `invoke: true`, the top-ranked agent is run on `need` via the same governed path as `declagents.invoke`; its outcome is recorded, the `from → chosen` edge is reinforced/weakened by that outcome, and its `{ output, turns, tool_calls, error?, goal? }` lands in `result`. Errors if no eligible declarative agents exist.
- `declagents.route_split` — **Params** `{ need: string, invoke?: bool, max_subtasks?: number, decomposition_mode?: "vanilla"|"sad", sad_hints?: number, sad_iterations?: number, sad_convergence_jaccard?: number }`. **Returns** `{ subtasks: [{ subtask, chosen, score, result? }], count, invoked, decomposition_mode, rounds, initial_subtasks, final_subtasks, hints, hint_jaccard? }`. AgentNet's **Split** op as a fan-out: a planner model decomposes `need` into independent subtasks (`max_subtasks` clamped to [1, 10], default 5), then each subtask is routed to its best-matching agent by the same capability-similarity ranking as `declagents.route`. `decomposition_mode` defaults to `"vanilla"` for compatibility. `"sad"` enables Skill-Aware Decomposition: CAR decomposes once, retrieves candidate agent hints, re-decomposes with those hints, and stops early when hint-set Jaccard reaches `sad_convergence_jaccard` (default 0.6; hints clamp [1, 50], iterations [1, 3]). Any decomposition failure falls back to the last valid subtasks or the whole `need`. A per-subtask infra failure is captured into that subtask's `result.error` and the fan-out continues. **Cost:** `invoke: true` runs up to `max_subtasks` full agent loops sequentially; SAD adds extra decomposition/embedding work.
- `declagents.routing_stats` — **Params** `{}`. **Returns** `{ agents: { <id>: { successes, failures, ema_success_rate, learned } }, edges: { <from>: { <to>: weight } } }`. Read-only view of the learned routing topology — the success priors, the `learned` flag (whether the agent has a reinforced capability centroid), and directed agent→agent forward-edge weights that `declagents.route` ranks with. The centroid vector itself is omitted (large embedding, noise for observability). Empty when nothing has been routed yet.
- `discovery.resolve` — **Params** `{ need: string, limit?: number }`. **Returns** `{ services: [{ identifier, name, kind, protocol, score, similarity }], count }`. AgentDNS-style service discovery ([arXiv:2505.22368](https://arxiv.org/abs/2505.22368), design in `docs/proposals/agentdns-discovery-layer.md`): resolves `need` into ranked CAR services across providers, each named under the `agentdns://organization/category/name` scheme. Providers: **declarative agents** (`kind:"declarative"`, `protocol:"in-daemon"`, `agentdns://local/agent/<id>`), **observe-only registry services** (the dashboard-registered local services under `~/.car/registry/`, written by `registry.register` / `register_agent` / the supervisor — `kind:"registry"`, `protocol:"http"`, `agentdns://local/service/<name>`; only running/idle entries are surfaced, ranked by the entry's `capability` text and reachable at its `dashboard_url`), **connected MCP connector tools** (`kind:"connector"`, `protocol:"mcp"`, `agentdns://<connector-slug>/tool/<tool>`, `name` = the canonical `mcp_<slug>_<tool>` handle), **installed external agent CLIs** (Claude Code / Codex / Gemini — `kind:"external"`, `protocol:"cli"`, `agentdns://external/agent/<id>`; detection is cached ~60s to avoid per-call `--version` probes), and **registered remote A2A peers' skills** (`kind:"a2a"`, `protocol:"a2a"`, `agentdns://<peer-slug>/skill/<skill-id>`; each peer's agent card is fetched concurrently with a per-peer timeout and cached ~60s — register peers via `a2a.peers.add`). Ranking is uniform — cosine similarity of `need` vs each service's capability text blended with a learned success prior for **every** provider kind: the Beta(success+1, fail+1) posterior UCB (the `car-memgine::utility` substrate, shared with `declagents.route` — one agent, one score, both surfaces) over the routing-store history keyed by the service's `agentdns://` identifier (fed by `discovery.report`; a never-reported service's cold posterior mean is exactly the neutral 0.5). Declarative agents additionally fold in their agent-id-keyed history (the `declagents.route`/`invoke` learning) and blend their learned capability centroid. `limit` clamps to [1, 50] (default 5). Pure resolution — it does **not** invoke; the caller selects an `identifier`/`name` and invokes via the matching surface (`declagents.invoke`, or the connector's canonical tool name). Empty `services` (not an error) when nothing matches. A fifth provider, the **remote AgentDNS root server** (cross-vendor registry), is included when `CAR_AGENTDNS_ROOT_URL` is set — CAR POSTs the need to the root and folds its records into the same ranking via their description (signed-in users send the Parslee token as bearer). The root contract is `docs/agentdns-root-contract.md`; the provider is inactive until the backend is deployed and the URL configured. Provider gathering is best-effort and each probing provider is time-bounded (5s): a flaky connector, slow detection, unreachable A2A peer, or unreachable root is skipped, never failing discovery of everything else.
- `discovery.report` — **Params** `{ identifier: string, outcome: "success"|"failure" }`. **Returns** `{ identifier, outcome, successes, failures }` (the updated raw counts). Records a discovery-routed run's outcome into the routing learning store (`~/.car/routing.json`), keyed by the service's `agentdns://` identifier — for **every** provider kind (connector, registry, external, a2a, declarative), not just declarative agents. This is the feedback loop `discovery.resolve`'s success prior learns from (H2 Part 2): a service that keeps failing is demoted below a healthy sibling on the next resolve — e.g. a broken MCP-connector tool sinks under its backup provider — while a never-reported service stays at the neutral cold-start prior. The identifier is validated against the `agentdns://` scheme and must be passed **verbatim** from `discovery.resolve` (the parser validates, it does not normalize — a re-spelled identifier records feedback that ranking never reads; charset-valid identifiers for nonexistent services are persisted but never rank); `outcome` is strict (anything else errors). **`agentdns://local/agent/*` identifiers are rejected**: in-daemon declarative runs are recorded automatically by `declagents.invoke`/`route`, and their agent-id and identifier keys fold together at ranking time — reporting them here too would teach the same run twice. Recording is caller-attested — CAR doesn't verify the run happened; the caller that invoked the service reports what it observed.
- `discovery.route_compose` — **Params** `{ need: string, max_subtasks?: number, decomposition_mode?: "vanilla"|"sad", sad_hints?: number, sad_iterations?: number, sad_convergence_jaccard?: number, candidates_per_step?: number, rerank?: bool }`. **Returns** `{ plan: { steps: [{ id, subtask, service, invoke_kind, invoke_target }], edges }, decomposition, candidates, metadata }`. This is SkillWeaver-style decompose → retrieve → compose over the same provider set as `discovery.resolve`. It plans only: CAR does not synthesize parameters or auto-invoke cross-kind services in v1. Each chosen step carries `invoke_kind`/`invoke_target` so callers can invoke via the existing governed surface (`declagents.invoke`, connector tool execution, `agents.invoke_external`, A2A dispatch, or — for a `registry` service — a plain `http` call to its dashboard URL). `rerank: true` optionally asks the model to listwise rerank each step's candidates; default `false`.
