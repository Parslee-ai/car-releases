### declagents

**In-daemon declarative agents.** A declarative agent is pure data — an identity (system prompt), a tool **allowlist** (names of tools the daemon already exposes), an optional deny list, a standing goal, an optional deterministic `goal { check, max_iterations }`, and scenarios (test cases). The daemon runs it with a generic model→tool loop: there is no command to spawn, so a non-developer installs nothing. Built by the coder→agent loop (an `agent`-kind project: `coder.start { project }` synthesizes a "scenarios pass" contract, the build loop generates the spec and drives its scenarios green in-daemon, and `coder.approve_merge` registers it). The project's committed `agent.json` and `scenarios.json` are versioned build output; the daemon runs the separately registered spec in `declagents.json`, so editing only the project file does not update the active agent. Rebuilding and approving registers the updated spec. This is a **parallel registry** to the supervised `agents.*` — a declarative agent has no command, so it never travels through the supervisor's absolute-path validation. `agents.list` read-merges declarative entries tagged `kind:"declarative"` (carrying `enabled` instead of process status), `capabilities:["chat"]`, and `description` (the trimmed standing goal when nonblank, otherwise the trimmed identity); hosts can call `agents.chat` with the declarative agent id and receive the normal `agents.chat.event` stream from the in-daemon runner. `agents.chat.cancel` is honored in-daemon via a local cancellation flag; the runner stops at the next model/tool/goal-check boundary and late frames are suppressed once routing is dropped.

**Ids** are unique ignoring ASCII letter case, the rule `agents.upsert` applies: saving a new declarative agent whose id differs from a registered one only in case (`Sales` beside `sales`) is refused with an error naming the existing id, because per-id files such as its spend meter's would be shared on a case-insensitive file system. Saving the same id again replaces it, and existing registrations are left as they are.

**Security**: the tool allowlist is strict — an empty/typo'd allowlist exposes ZERO tools, never the full set — and the daemon's inspector chain hard-enforces beneath it. A declarative agent can only call tools it was granted, gated by the same policy as the coder.

- `declagents.list` — **Params** `{}`. **Returns** `{ agents: [{ id, registration_id?, name, description, kind:"declarative", enabled, capabilities:["chat"], tools, goal?, inference?, scenarios, verification? }] }`; `description` is the trimmed standing goal when nonblank, otherwise the trimmed identity. `registration_id` says which registration of `id` the row is: the registry mints a new one when nothing holds the id (a first registration, or one after `declagents.remove`) and keeps it when a rebuild, rename or `declagents.revert` replaces the agent, so a host that remembered an agent by id can tell a rebuilt agent from a different one registered under the same id. Any value a caller puts in a spec is ignored. It is absent for a spec saved before the field existed, until that spec is next replaced, and it is not part of the agent's content fingerprint. `agents.list` declarative rows carry it too. `verification` is the spec's own (see `declagents.get`), present only when the registered version was saved without an independent check, so a host can tell when a rebuild under the same id changed the check status. Its `status` is `"not_checked"`; a status this daemon does not recognise (written by a newer one) reads as `"unknown"`. A missing `declagents.json`, or one that is empty or holds only whitespace, is an empty list; it holds no agents, so the next save writes over it. Any other file that cannot be read or parsed is an error naming the file, never an empty list: `declagents.list`, `declagents.get`, `declagents.invoke`, `declagents.run_scenarios`, `declagents.route`, `declagents.route_split` and `coder.projects.create` with `existing_agent_id` return that error, and every `declagents.*` mutation and `coder.approve_merge` registration refuses rather than write over the damaged file, which stays as it was for the operator to repair. `agents.list` still answers with every supervised agent and leaves out only the declarative rows, logging the error, so call `declagents.list` to tell "no built agents" from "could not read them". `discovery.resolve` drops declarative agents from its candidates and logs the error, the same way it skips a provider that times out. `agents.chat` to an id that is not attached keeps its "agent `<id>` is not attached to this daemon — …" refusal with the registry error appended.
- **Who sees which rows (`declagents.list`, `declagents.get`).** A session bound to a supervised agent (`session.auth { agent_id, token }`) gets only the row whose `id` is its own agent id from `declagents.list`, and `declagents.get` of any other id answers `no declarative agent '<id>'` (the refusal is logged), on every platform. Host sessions, the daemon-token operator and the CLI get every row.
- `declagents.get` — **Params** `{ id: string }`. **Returns** the full `DeclarativeAgentSpec` plus `registry_path`, the exact daemon-resolved file that supplied it. `registry_path` is response metadata and is never written into `declagents.json`. The spec carries `registration_id` as `declagents.list` describes. Builder-created specs may include `builder_draft: { template_id, name, responsibility, example, access, cadence, delivery, privacy, mail_access?, local_only?, working_folder?, timezone? }`; `mail_access` (default `false`) records that the person allowed read-only Mail, `local_only` (default `false`) that they asked for everything the agent reads to stay on this Mac, `working_folder` (default empty, meaning `~/CAR Agents/<agent name>`) the folder they chose, and `timezone` (default empty, meaning the Mac's own clock) the fixed zone their schedule keeps. All four are omitted when unset, so older drafts keep their exact JSON and fingerprint and behave as before. The runtime reads `local_only` (never the free-text `privacy` answer): the agent's runs, including its build's test cases, use only models on this Mac (see `declagents.invoke`); its build calls no verifier or auditor model and is saved with `verification: { status: "not_checked" }` (see `coder.start`); and Parslee never stands in for its saved model. A spec may carry `working_folder: string`, an absolute path: the folder the agent keeps between runs (see `declagents.invoke`). It is optional; a spec without it runs in a scratch folder as before. A Build an Agent build (one with a `builder_draft`) always records one, and refuses a folder that is the disk root, the home folder or above it, or inside CAR's state root; edited specs additionally include `previous`, the immediately preceding full spec with its own `previous` cleared. Both fields default absent, so legacy and hand-authored specs keep loading. A spec may also carry `inference: { model: string, provider: string, reasoning_effort: "low" | "medium" | "high" }`. The whole block defaults absent for adaptive routing; when present, a bare model is qualified as `<provider>/<model>`, a qualified id without a tag names the catalog row tagged `:latest` unless that id is itself a catalog row (car#2751), an already-qualified model must agree with `provider`, the route is strict, and the effort maps to the provider's native coarse reasoning control. On Claude and OpenAI reasoning models the runner adds the reasoning budget to `max_tokens`, capped at the catalog output limit (car#1989). The spec also includes `context: "car" | "self"` — who manages the agent's conversation context (see `declagents.invoke`). It is optional on disk and defaults to `"car"`, so a spec registered before the field loads unchanged, but the response always carries it. A spec may carry `verification: { status: "not_checked", reason: string }`, written only by the runtime when Build an Agent registered this version without an independent check because no auditor was available, or because, with `auditor_model = "auto"`, the model that built it could not be identified (`coder.md`, `auditor_model`); `reason` says which; its own scenarios passed and it runs like any other agent. It is absent for an independently checked build and for every spec written before the field, it is replaced on each registration, a model-written value is discarded, an unrecognized `status` still loads, and it is not part of the spec's fingerprint. The optional structured `cadence` is `{ trigger: "interval"|"cron"|"manual", schedule, timezone?, phrase }`; `phrase` preserves what the user entered, while `trigger` and `schedule` are the result from `schedule.suggest`. Its absence means no cadence was requested.
- `declagents.remove` — **Params** `{ id: string }`. **Returns** `{ removed: bool }`.
- `declagents.set_enabled` — **Params** `{ id: string, enabled: bool }`. **Returns** `{ ok: true }`. A disabled agent stays registered but refuses to run.
- **An unparseable registry file is never overwritten.** `declagents.remove`, `declagents.set_enabled` and `declagents.revert` error, and leave the file untouched, when the registry file exists but does not parse ("`<path>` is not a valid declarative-agent registry (…); refusing to overwrite it — fix or move the file"); reads (`declagents.list`, `declagents.get` and the others listed under `declagents.list`) return the same error naming the file. Only a missing, empty or whitespace-only file is an empty list.
- `declagents.revert` — **Params** `{ id: string }`. **Returns** `{ reverted: true, agent: DeclarativeAgentSpec }`. Restores the spec's one retained `previous` version atomically under the same id, without model generation or another build. The outgoing version becomes the new one-level `previous`, so another revert toggles back while history stays bounded. Errors without retained history. This is a host-lifecycle mutation and uses the same host-authority gate as remove and enable/disable.
- `declagents.run_scenarios` — **Params** `{ id: string }`. **Returns** `{ id: string, passed: integer, total: integer, all_passed: bool, can_revert: bool, results: [{ index: integer, input: string, expect: string, output: string, agent_said?: string, passed: bool, turns: integer, tool_calls: integer, error?: string }], run_error: string | null }`. Top-level `passed` is the count of passing cases; each row's `passed` is that case's boolean verdict. `index` counts from 1; `run_error` is `null` when the suite ran. Runs every scenario currently stored on the registered spec through the same declarative runner and case-insensitive expected-substring evaluator used before registration. For a spec with `working_folder`, each scenario runs in its own fresh throwaway copy of that folder's files (hidden files included; a link that leads inside the folder is copied as a link to the same place in the copy, so tools treat it as in a real run, and one that leads outside or nowhere is left out), so they see the person's inputs and never change the real folder; a folder with more than 1,000 files, folders and links, more than 64 MB, folders more than 16 levels deep, or anything unreadable is refused with an error naming the problem rather than copied in part. `run_error` reports suite-level infrastructure failure; completed per-case evidence remains in `results`. The exception is the agent's folder: if CAR can't use it for a scenario (the system refused, it got no answer within 45 seconds, or the folder can't be copied), `declagents.run_scenarios` returns an error naming the folder and the fix instead of a result, and results from cases that already ran in that call are not returned. It does not modify the agent.
- **Admission on `declagents.invoke` / `.run_scenarios` / `.route` / `.route_split`.** All four reach the same in-daemon declarative executor, so all four pass the admission `agents.chat` and `agents.message` apply when the caller is an *agent* rather than the host: the per-recipient channel guard (dedupe inside 10s, 20 per sender per minute) and the `AgentPermissionPolicy` decision at the `read_only` tier. Gating chat while leaving these open would just make them the way around it. For `route` and `route_split` the check is applied to the **chosen** agent, not the requested need, so a routed run is graded against the agent that actually ran. The host is exempt.
- `declagents.invoke` — **Params** `{ id: string, input: string }`. **Returns** `{ output, agent_said?, turns, tool_calls, model_served?, model?, stood_in?, error?, goal? }`; `model_served` is the serving catalog id and `model` is its temporary compatibility alias for older CarHost Work clients. A saved `inference` selection is applied to Work, direct, routed, and chat invocations and cannot be replaced by a per-call model parameter; host availability and policy may still refuse or narrow it. Without the block, routing remains adaptive. **Unavailable saved model.** Before the run, the daemon checks the saved model against its catalog (credentials checked for existence in the environment or OS secret store, never read). When the model is unavailable and the person has no other cloud model connected (an account, subscription, CLI sign-in or API key of theirs; on-device models do not count) and `parslee/advisor` is available, that Parslee route answers instead, strictly (no other route and no on-device last resort). **Local-only agents.** For an agent whose `builder_draft.local_only` is `true`, every model turn (its runs, `declagents.run_scenarios`, and its build's spec writing, repair and test cases) runs on a model on this Mac (a catalog row CAR runs on-device: MLX, Candle GGUF, a CAR-managed vLLM-MLX, Apple's on-device model; an Ollama or external vLLM-MLX endpoint does not count, since it may be on another machine). An unpinned agent routes adaptively with every other catalog model strictly excluded, so a remote model that would score higher is never picked. The run makes no model call and `error` names the setting when: no model on this Mac can answer, or the catalog can't be read (`This agent is set to keep everything it reads on this Mac, and no model on this Mac can run it. …`); the saved model is not on this Mac (`This agent runs on <model>, which isn't on this Mac, and it is set to keep everything it reads on this Mac. …`); or the saved model is on this Mac but unavailable (`This agent runs on <model>, which isn't available, and it is set to keep everything it reads on this Mac, so Parslee can't answer in its place. …`). Each ends `Install a model on this Mac, pick one, or edit the agent to turn off "Keep everything this agent reads on this Mac".` A per-run model choice cannot change this: a choice elsewhere on an unpinned agent is refused like a saved one, and a saved model stays authoritative. Parslee never stands in. The result carries `stood_in: { for_model, on_model, notice }` — the saved model, `"parslee/advisor"`, and `"Ran on Parslee because <model> isn't available."` — if and only if Parslee served at least one turn of the run. It stays when the run then fails for another reason (the turn cap, a goal not met, a change that did not go through), next to `error`, because it says which model ran, not that the run succeeded. It is `null` when Parslee never answered (Parslee failed, or the run was cancelled before any model answered) and on every run that was not a stand-in. A cancelled run reports the `model_served` of the turns answered before the stop. `output` stays exactly the agent's answer, or is empty with the answer in `agent_said` (below). If Parslee fails before answering, `error` is `This agent runs on <model>, which isn't available, and Parslee couldn't answer in its place: <reason>`; if it fails after answering a turn, `error` is `Parslee stopped partway: <reason>`, next to `stood_in`. A Codex CLI row counts as another connected model when `codex login status` confirmed it is signed in, and not when it confirmed it is signed out. When every credential state is known and another model is connected, or `parslee/advisor` is unavailable, the run makes no model call and `error` is `This agent runs on <model>, which isn't available. Reconnect it, or edit the agent to pick another model.`. When the daemon can't tell whether the saved model or another connected model is there (the secret store errored while checking a key or the ChatGPT sign-in, or a Codex CLI's sign-in is unknown: its check still running or timed out, and always on Windows, where it is never checked), nothing is decided from it: the saved model is tried strictly, before `parslee/advisor`'s availability is considered, and a failure reads `This agent runs on <model>, which didn't answer: <reason>. Reconnect it, or edit the agent to pick another model.` The same `result` object (with `stood_in`) is what `declagents.route` and `declagents.route_split` return for each run and what an in-daemon `agents.chat` turn carries on its `done` and `error` frames. Runs the agent on `input` entirely in-daemon (no process), bounded by a turn cap, with file tools rooted in an ephemeral scratch workspace — or, when the spec has `working_folder`, in that folder, created if missing and kept after the run. A folder agent may read and write only inside its folder: file tools (reads as well as writes) refuse a `path` that is not text and paths outside it, a listing or search with no `path` covers the folder, judged by where a path really leads, so a link already inside the folder that points out is refused, left out of `list_dir`, never walked by `find_files` or `grep_files`, and any hit that resolves outside is dropped; `write_file` and `edit_file` refuse a `.csv`, `.xlsx`, `.xlsm` or `.docx` file (any letter case; reading one is fine) with "Use append_spreadsheet_row / fill_word_template to change this file."; a write or edit to a file hard-linked from somewhere else is refused ("This file is linked from somewhere else, so the agent won't change it."), and the spreadsheet and Word tools replace a file rather than write through it, so a hard-linked file elsewhere keeps its contents; `write_file` and `edit_file` replace the file too (a link inside the folder is written at the file it names, and a file the person can't write stays unwritten), and reach it from the folder one folder name at a time without following a link, so a folder on the way swapped for a link after the path was checked, or moved out of the folder after it was opened (on macOS and Linux), is refused with "… changed while it was being saved, so nothing was saved. Try again." (a move in the instant between that check and the rename, or one made during the check itself by moving the folder out while its parent is moved into the working folder, is not caught; winning either needs rename rights over the moved folder's parent and over a folder outside on the same filesystem); on macOS and Linux the working folder is pinned when the run starts, and a write after it was renamed away and replaced by another folder or a link is refused with "The working folder … was replaced while the agent was running, so nothing was saved. Start the run again."; and it runs no commands — a build never gives it `shell` or a goal check, and a spec edited to add either is refused with an error — because a command could read files anywhere the person can. Its executor still write-confines any child to the folder and denies it Apple Events. A folder agent is not given the Parslee platform tools. The folder is resolved (symlinks followed) and refused if it is, or holds, the home folder or the disk, or lies inside CAR's state root. A folder agent is also offered `append_spreadsheet_row` (adds one row to an `.xlsx` first visible sheet or a `.csv`, creating it with `headers` when missing; `values` is a list in column order or an object keyed by header; the row goes after the last row holding a value, writing into an existing row below it that holds only formatting or formulas, keeping each cell's style and never writing over a formula, and refusing when that row is hidden or zero height, when a column it writes is hidden or zero width (including by a `sheetFormatPr` `defaultColWidth` or `baseColWidth` of 0 or less without its own visible width), when an empty cell it reuses has a number format (read from the workbook's styles) that would hide the value, can't be read, or picks its section by a condition such as `[>100]` (a numeric 0 also needs a `0` placeholder, a literal or `@` in its section: `#` alone shows it blank), when it would write a numeric 0 into a sheet that shows zeros as blank (`sheetView showZeros="0"`), when a conditional-formatting rule covering a written cell applies a number format (its `dxf` in the styles) that would hide the value or can't be read, or names an unknown `dxfId` (rules that only change colours, fonts or fills are fine), or when the sheet hides rows by default (`sheetFormatPr zeroHeight`, or a `defaultRowHeight` of 0 or less); text starting with `=`, `+`, `-` or `@` is an inline string in `.xlsx` and gets a leading `'` in `.csv`; a `.csv` field holding a comma, quote, line break, `;` or tab is quoted, and a row is appended with the file's own line ending (`\n`, `\r\n` or `\r`); a number with more than 15 significant digits is refused, asking for it as text (Excel would round it); a row whose values are all empty or null is refused with "There's nothing to add: every value is empty.") and `fill_word_template` (copies a `.docx` template to `output`, replaces its `{{name}}` placeholders including ones Word split across runs (text is found by the WordprocessingML namespace, whatever prefix the file uses; every `{{…}}` counts, whatever its name, and names match ignoring case, surrounding and repeated spaces, and typographic apostrophes, quotes and non-breaking spaces), never overwrites the template, refuses an existing `output` unless `overwrite: true`, saves nothing and names them when any placeholder has no value, refuses a value containing `{{` or `}}`, reads the filled document back before saving and saves nothing if any `{{…}}` remains, and returns `{ output, filled, unfilled, unused_values }`); both take paths relative to the folder, used exactly as given (a path that starts or ends with a space is refused, never trimmed), and refuse a spreadsheet, template or output that is a link ("This file is a link. Point the agent at the file itself."), run one at a time in the daemon (so concurrent appends each get their own row), ignore cell references past Excel's last column, refuse to append past Excel's last row (1,048,576), refuse a template with more than 5,000 placeholders (counted after split runs are joined), and refuse — changing nothing — a spreadsheet or template outside the shape real producers write, read with a namespace-aware XML reader and matched by namespace (XML comments, CDATA, processing instructions, a rebound namespace prefix, an element named like the edited ones in another namespace or position, a `dimension` with children, rows, cells or cell contents other than SpreadsheetML `row`/`c`/`v`/`f`/`is`, a `{{` outside paragraph text, or a placeholder split by anything but run formatting), asking the person to open and re-save it in Excel, Numbers, Word or Pages, also refuse, changing nothing, a sheet with merged cells, an Excel table, a PivotTable (linked from the sheet's relationships) or a filter (a sheet `autoFilter`, or the workbook's `_xlnm._FilterDatabase` name for that sheet), asking the person to unmerge the cells, convert the table to a normal range or turn off the filter, a CSV whose quotes don't balance or whose header line has a `;` or a tab outside quotes, a value or header holding a control character other than tab, line feed and carriage return or any other character a spreadsheet or Word document can't hold (rather than dropping it), a value named by a header that appears more than once in the sheet or two named values that land in one column, a sheet with a repeated row number, any part with more than one root element, and a `.docx` without its `[Content_Types].xml` or a package relationship naming `word/document.xml` as the main document. A line break or tab in a Word value is written as a Word line break or tab in the same run. Both tools are `sandbox_edit` tier. When the spec allowlists `mail_inbox`, `mail_search` or `mail_message_body`, it gets those three local Mail.app reads and nothing else (the spec's tools decide this, not `builder_draft.mail_access`, so a spec registered over RPC with those tools reads Mail): a saved agent is never offered `mail_draft` or `mail_send`, and calling any other Mail name is refused before Mail is reached. A run in which a tool that changes something returned an error, and no later call of the same tool succeeded, ends with `error: "The agent stopped without finishing: <step> didn't go through: <the tool's error>"` whatever the final answer says, and a scenario with that error fails. Before that, the first time in a run that the model ends its turn with such a failure standing, it is sent one more message, `<step> didn't go through: <the tool's error>. Do it now, or say why it can't be done.`, and continues: if it then makes the change, the run ends normally on its new answer; if it ends again with the change unmade, the run ends with that `error` and its new answer. This happens once per run (a `goal` run's later passes are not told again), only when the turn cap leaves at least one more turn, and never for a run that was stopped. Those turns count toward the cap; when the cap is reached, or the model call fails, after that message while the change still stands, the run ends as if the message had not been sent: with that `error` and the answer the model gave first. A run that ends with that `error`, or with `goal_not_met ...`, returns `output: ""` and the final answer as `agent_said`, because the answer is what the agent said, not what happened; `agent_said` is `null` on every other run, including a run whose `goal.check` could not run (exit 126 or 127, or it failed to start). The step is named in plain words, with the file when the call named one (as the call gave it, with the home folder shown as `~`; the tool's own error is quoted as it is): `filling the Word template "<output>"`, `adding a row to "<path>"`, `writing "<path>"`, `editing "<path>"` (`filling the Word template`, `adding a spreadsheet row`, `writing a file` or `editing a file` when the call named none), `running a command` for `shell`, `sending a web request` for `http_request`, `making the document` for `parslee_m365_generate_document`, and the tool's own name for any other tool. When the run works in the agent's own `working_folder` and change-making calls in it saved files (a successful `write_file`, `edit_file`, `append_spreadsheet_row` or `fill_word_template`; each file once, however it was spelled, shown relative to the folder), `error` names them first: `The agent stopped without finishing: it saved "<file>", "<file>" and "<file>", but <step> didn't go through: <the tool's error>`, with the first ten named and the rest counted (`and N more files`). Files a command or another tool changed are not named, because the run has no record of them. A run in a scratch workspace (an agent without a folder) or in a test run's copy of the folder names no saved files, since that folder is deleted when the run ends. Those tools are `write_file`, `edit_file`, `shell`, and every tool whose definition declares `"mutating": true` (`append_spreadsheet_row`, `fill_word_template` and `parslee_m365_generate_document` among them), except an `http_request` whose `method` is `GET`, `HEAD` or `OPTIONS` in any letter case, or is missing (the tool then sends `GET`): such a request only reads, so its failure never fails the run and its success clears nothing. A failure is also cleared by a later successful change on the same file (`path` for `write_file`, `edit_file` and `append_spreadsheet_row`, `output` for `fill_word_template`), whichever of those tools makes it, so following a refusal that points to another tool clears it: a folder agent's `write_file` on a spreadsheet ("Use append_spreadsheet_row / fill_word_template to change this file.") then `append_spreadsheet_row` on that file, or an `edit_file` with an empty `old_text` ("use write_file to replace a whole file") then `write_file` on that file. `append_spreadsheet_row` and `fill_word_template` are judged per file only, so their success on another file does not clear a failure that named a file. An error is the tool refusing or failing the call; a `shell` command that ran and exited non-zero is not one, since its exit code is part of the result the model reads. A failed call of any other tool (a read or a search, say) never fails the run, and a call to a tool the spec does not allow is refused without counting. When several failures stand, `error` names the earliest. With a `goal`, a pass that ends with such a failure standing is not checked: the next pass is told the step and its error and can still make the change, the pass's `goal.last_reason` is `<step> didn't go through: <the tool's error>`, and if the last pass ends with it standing, `error` is that message instead of `goal_not_met ...`. The run's system prompt names the folder and, for Mail, says the agent can never write drafts, send, reply or forward. When the spec has a `goal`, CAR runs `goal.check` in that same workspace after each pass, re-drives the agent with the verifier reason until the check exits 0, and returns `goal: { check, max_iterations, iterations, met, grounded, last_exit_code, last_reason }`; if the check never passes, `error` is `goal_not_met ...`. **Context policy.** With the spec's `context` at its default `"car"`, the run's growing history is compacted before each model call to fit the context window of the model that ran the turn (three quarters of it, measured on the provider's reported prompt size once there is one), pinning the identity and the original input and leaving the `[history compacted: ...]` system notice — the same compaction the assistant and coder loops use. With `context: "self"` CAR never compacts and the spec owns the transcript. The window is re-read after every call from the model that served it, so a mid-run fallback to a smaller model is compacted against the smaller window. A model absent from the catalog (or a catalog row whose `context_length` is `0`) has no known window. If the run never knew one, compaction is disabled for it and the daemon logs `compaction disabled: unknown context window for model <id>` once per invocation; if an earlier turn did know one, that budget is kept — losing it would leave the run unbounded over a routing detail — and the daemon logs `model <id> has no known context window; keeping the last known budget of N tokens` once instead. An unrecognized `context` value is not a parse error — it warns and falls back to `"car"`, so a hand-edited typo can never unregister the agent.
- `declagents.route` — **Params** `{ need: string, invoke?: bool, from?: string, visited?: string[] }`. **Returns** `{ chosen, candidates: [{ id, name, score, similarity, success_rate, edge_weight }], next_visited, invoked, result? }`. Capability-similarity routing: embeds `need` (query-side) and each eligible agent's capability surface (name + identity + standing goal + tools), then ranks by `score = 0.7·similarity + 0.3·success_rate + 0.2·edge_weight` (the AgentNet milestone, see `docs/proposals/agentnet-self-organization.md`). `success_rate` is the agent's learned success prior: the Beta(success+1, fail+1) posterior UCB (the `car-memgine::utility` substrate) over the raw success/failure counts persisted in `~/.car/routing.json` — folded across BOTH the agent-id key (outcomes recorded by `declagents.route`/`invoke`) and the agent's `agentdns://local/agent/<id>` identifier key (outcomes recorded by `discovery.report`), so `declagents.route` and `discovery.resolve` score the same agent identically (one agent, one score — H2 Part 2, `docs/proposals/h2-builder-discovery-acceptance.md`). The cold-start posterior mean is exactly the neutral `0.5`; the persisted EMA field remains in `declagents.routing_stats` for display but no longer drives ranking. Similarity dominates so cold-start ranking is correct, the prior nudges toward agents that actually finish work. `similarity` itself blends cold-start similarity (need vs the agent's static capability text) with learned similarity (need vs the agent's reinforced capability centroid, `0.6·cold + 0.4·learned`) once the agent has succeeded at least once — so an agent's effective profile drifts toward the needs it actually handles well. **Forward op:** when `from` (the delegating agent) is set, it is excluded from candidates and a learned directed edge `from → candidate` adds `edge_weight` to the score — so a proven delegation path re-ranks peers. `visited` is the set of agents already on the routing path (DAG/cycle guard): all are excluded, and routing refuses the next hop once 4 agents are already on the path (a chain runs at most 4 agents before terminating). To walk a Forward chain, the next hop passes `from = chosen` and `visited = next_visited` (the response echoes `next_visited = visited + [chosen]`, so each hop strictly grows the path and the hop cap always terminates it). `score` is an unbounded ranking score (a fully-forwarded agent can exceed 1.0), not a probability — only the order across candidates is meaningful. `candidates` are the top 3 ranked descending. With `invoke: true`, the top-ranked agent is run on `need` via the same governed path as `declagents.invoke`; its outcome is recorded, the `from → chosen` edge is reinforced/weakened by that outcome, and its `{ output, turns, tool_calls, error?, goal? }` lands in `result`. Errors if no eligible declarative agents exist.
- `declagents.route_split` — **Params** `{ need: string, invoke?: bool, max_subtasks?: number, decomposition_mode?: "vanilla"|"sad", sad_hints?: number, sad_iterations?: number, sad_convergence_jaccard?: number }`. **Returns** `{ subtasks: [{ subtask, chosen, score, result? }], count, invoked, decomposition_mode, rounds, initial_subtasks, final_subtasks, hints, hint_jaccard? }`. AgentNet's **Split** op as a fan-out: a planner model decomposes `need` into independent subtasks (`max_subtasks` clamped to [1, 10], default 5), then each subtask is routed to its best-matching agent by the same capability-similarity ranking as `declagents.route`. `decomposition_mode` defaults to `"vanilla"` for compatibility. `"sad"` enables Skill-Aware Decomposition: CAR decomposes once, retrieves candidate agent hints, re-decomposes with those hints, and stops early when hint-set Jaccard reaches `sad_convergence_jaccard` (default 0.6; hints clamp [1, 50], iterations [1, 3]). Any decomposition failure falls back to the last valid subtasks or the whole `need`. A per-subtask infra failure is captured into that subtask's `result.error` and the fan-out continues. **Cost:** `invoke: true` runs up to `max_subtasks` full agent loops sequentially; SAD adds extra decomposition/embedding work.
- `declagents.routing_stats` — **Params** `{}`. **Returns** `{ agents: { <id>: { successes, failures, ema_success_rate, learned } }, edges: { <from>: { <to>: weight } } }`. Read-only view of the learned routing topology — the success priors, the `learned` flag (whether the agent has a reinforced capability centroid), and directed agent→agent forward-edge weights that `declagents.route` ranks with. The centroid vector itself is omitted (large embedding, noise for observability). Empty when nothing has been routed yet.
- `discovery.resolve` — **Params** `{ need: string, limit?: number }`. **Returns** `{ services: [{ identifier, name, kind, protocol, score, similarity }], count }`. AgentDNS-style service discovery ([arXiv:2505.22368](https://arxiv.org/abs/2505.22368), design in `docs/proposals/agentdns-discovery-layer.md`): resolves `need` into ranked CAR services across providers, each named under the `agentdns://organization/category/name` scheme. Providers: **declarative agents** (`kind:"declarative"`, `protocol:"in-daemon"`, `agentdns://local/agent/<id>`), **observe-only registry services** (the dashboard-registered local services under `~/.car/registry/`, written by `registry.register` / `register_agent` / the supervisor — `kind:"registry"`, `protocol:"http"`, `agentdns://local/service/<name>`; only running/idle entries are surfaced, ranked by the entry's `capability` text and reachable at its `dashboard_url`), **connected MCP connector tools** (`kind:"connector"`, `protocol:"mcp"`, `agentdns://<connector-slug>/tool/<tool>`, `name` = the canonical `mcp_<slug>_<tool>` handle), **installed external agent CLIs** (Claude Code / Codex / Gemini — `kind:"external"`, `protocol:"cli"`, `agentdns://external/agent/<id>`; detection is cached ~60s to avoid per-call `--version` probes), and **registered remote A2A peers' skills** (`kind:"a2a"`, `protocol:"a2a"`, `agentdns://<peer-slug>/skill/<skill-id>`; each peer's agent card is fetched concurrently with a per-peer timeout and cached ~60s — register peers via `a2a.peers.add`). Ranking is uniform — cosine similarity of `need` vs each service's capability text blended with a learned success prior for **every** provider kind: the Beta(success+1, fail+1) posterior UCB (the `car-memgine::utility` substrate, shared with `declagents.route` — one agent, one score, both surfaces) over the routing-store history keyed by the service's `agentdns://` identifier (fed by `discovery.report`; a never-reported service's cold posterior mean is exactly the neutral 0.5). Declarative agents additionally fold in their agent-id-keyed history (the `declagents.route`/`invoke` learning) and blend their learned capability centroid. `limit` clamps to [1, 50] (default 5). Pure resolution — it does **not** invoke; the caller selects an `identifier`/`name` and invokes via the matching surface (`declagents.invoke`, or the connector's canonical tool name). Empty `services` (not an error) when nothing matches. A fifth provider, the **remote AgentDNS root server** (cross-vendor registry), is included when `CAR_AGENTDNS_ROOT_URL` is set — CAR POSTs the need to the root and folds its records into the same ranking via their description (signed-in users send the Parslee token as bearer). The root contract is `docs/agentdns-root-contract.md`; the provider is inactive until the backend is deployed and the URL configured. Provider gathering is best-effort and each probing provider is time-bounded (5s): a flaky connector, slow detection, unreachable A2A peer, or unreachable root is skipped, never failing discovery of everything else.
- `discovery.report` — **Params** `{ identifier: string, outcome: "success"|"failure" }`. **Returns** `{ identifier, outcome, successes, failures }` (the updated raw counts). Records a discovery-routed run's outcome into the routing learning store (`~/.car/routing.json`), keyed by the service's `agentdns://` identifier — for **every** provider kind (connector, registry, external, a2a, declarative), not just declarative agents. This is the feedback loop `discovery.resolve`'s success prior learns from (H2 Part 2): a service that keeps failing is demoted below a healthy sibling on the next resolve — e.g. a broken MCP-connector tool sinks under its backup provider — while a never-reported service stays at the neutral cold-start prior. The identifier is validated against the `agentdns://` scheme and must be passed **verbatim** from `discovery.resolve` (the parser validates, it does not normalize — a re-spelled identifier records feedback that ranking never reads; charset-valid identifiers for nonexistent services are persisted but never rank); `outcome` is strict (anything else errors). **`agentdns://local/agent/*` identifiers are rejected**: in-daemon declarative runs are recorded automatically by `declagents.invoke`/`route`, and their agent-id and identifier keys fold together at ranking time — reporting them here too would teach the same run twice. Recording is caller-attested — CAR doesn't verify the run happened; the caller that invoked the service reports what it observed.
- `discovery.route_compose` — **Params** `{ need: string, max_subtasks?: number, decomposition_mode?: "vanilla"|"sad", sad_hints?: number, sad_iterations?: number, sad_convergence_jaccard?: number, candidates_per_step?: number, rerank?: bool }`. **Returns** `{ plan: { steps: [{ id, subtask, service, invoke_kind, invoke_target }], edges }, decomposition, candidates, metadata }`. This is SkillWeaver-style decompose → retrieve → compose over the same provider set as `discovery.resolve`. It plans only: CAR does not synthesize parameters or auto-invoke cross-kind services in v1. Each chosen step carries `invoke_kind`/`invoke_target` so callers can invoke via the existing governed surface (`declagents.invoke`, connector tool execution, `agents.invoke_external`, A2A dispatch, or — for a `registry` service — a plain `http` call to its dashboard URL). `rerank: true` optionally asks the model to listwise rerank each step's candidates; default `false`.

#### Schedules

A declarative agent runs on its own when its `cadence` is a `cron` or `interval` schedule, the agent is enabled, the schedule is not paused, and the platform's scheduler can take it. The daemon installs one durable OS schedule per such agent, so it fires while the app is closed; it runs `<car> agent run --scheduled <id>` (the `car` installed beside the daemon). The job is kept in the task store as task `agent-<id>` (whose `agent_metadata` names the agent and its `registration_id`) under the label `ai.parslee.car.task.agent-<id>`.

- **macOS (launchd).** A cron, or an interval that fits the clock (minutes dividing an hour, or hours dividing a day), is installed as calendar times; any other interval as launchd's interval timer. The job's output is appended to `logs/agent-<id>.log` in the folder that holds the agent registry (`<state root>`, or the folder of the `CAR_DECLAGENTS_PATH` file when that is set). The default state folder's job carries no `CAR_HOME`, so the `car` it starts reads the app's credentials and any daemon it starts uses these labels. Under an overridden `CAR_HOME` the job carries that folder as `CAR_HOME`, and the task id and label carry a short hash of it (`agent+<hash>-<id>`; the `+` is a character no agent id may contain, so no default-folder agent's `agent-<id>` can match one), so two state folders with an agent of the same id keep separate jobs, and the default folder never reaps a tagged job that still has its task. A registry moved with `CAR_DECLAGENTS_PATH` gets its own labels too (the hash covers the registry, and the root as well when both are moved), and the job carries it. A job carries only the variables its daemon was started with, and never adds a `CAR_HOME` the daemon wasn't started with, so the `car` it starts, and any daemon that starts, uses the same labels and token folder as the daemon that installed it.
- **Linux (crontab)** and **Windows (Task Scheduler)** jobs cannot carry environment, so under an overridden `CAR_HOME` or `CAR_DECLAGENTS_PATH` the schedule is saved and reported `failed` with a note naming the folder, not installed. crontab takes a cron and an interval that divides the hour (or day) evenly; any other interval, such as every 7 minutes, is reported `failed` rather than installed at another frequency. Task Scheduler takes an interval of whole minutes up to 31 days (it repeats a task at most every 31 days) or a single time on one day or every day; weekday, several-day and fixed-zone schedules, including every fixed-zone interval, are reported `failed`. An interval (every N minutes or hours) there runs on Task Scheduler's own timer, with no clock times: it is not checked for lateness (`runs_on_clock` is `false`, and it never records a missed time), and after a daylight-saving change its runs may shift by an hour. A daily or single-day schedule keeps its clock time there and follows the 15-minute rule below. Task Scheduler does not redirect output, so there is no log file there.

A saved cadence that does not validate (hand-edited) is not installed either: `declagents.runs` reports its schedule `failed` with a "the saved schedule cannot run" note at once, reading it live; the next sync (any schedule change, or the daemon's start) takes its old job down, and says so in the note if that fails; and a launch of a job still in place does not run it. An agent whose id starts with `.` is not scheduled: its runs could not be recorded under that id, so its schedule is reported `failed` with a note saying so. A job another state folder stamped is never replaced, removed or reported as this one's, and the schedule is reported `failed` with a note saying so. Registering a build (`coder.approve_merge`), `declagents.set_schedule`, resuming with `declagents.pause`, `declagents.set_enabled` and `declagents.revert` install or replace the job; pausing, disabling and `declagents.remove` take it down. Approving a build keeps a pause made while it ran, when the built schedule repeats too. Changes to one state folder's schedules are serialized and each reads the agent as saved at that moment, so a remove or pause racing an install ends with the job matching the last saved state. An install that fails after the job was written removes the job again; if that fails too, the task is kept, switched off, and boot repair removes the job. Pausing stops only the schedule: `declagents.invoke` without a trigger (Run now) and `agents.chat` keep working. At boot the daemon reinstalls any of its schedules that is missing or still launches a `car` an update replaced, and removes any whose agent no longer runs on one, found through its task records. One exception: a job installed by a daemon started with only `CAR_DECLAGENTS_PATH` (no `CAR_HOME`) carries no stamp, so if its task record is lost no daemon can tell it is its own, and it is left in place rather than risk removing another registry's job; CarHost never sets that variable. `coder.approve_merge`, `declagents.set_enabled` and `declagents.revert` add `schedule: { state, summary?, next_run_at?, note? }` to their replies, where `state` is `active`, `paused`, `manual`, `none`, `disabled` or `failed` (saved but not installed; `note` says why). `declagents.remove` adds `schedule_note` only when the schedule could not be removed.

- **The cadence.** `{ trigger: "cron"|"interval"|"manual", schedule, timezone?, timezone_mode: "mac"|"fixed", phrase, paused?, active_since? }`. A Build an Agent build parses the builder's `cadence` answer (and its draft's `timezone`) with the `schedule.suggest` grammar when the build runs; an answer outside the grammar saves no cadence and `coder.approve_merge` returns a `schedule_note` saying so rather than failing. `timezone_mode: "mac"` (the default, and what every earlier cadence means) runs on the Mac's own clock wherever it is, and ignores `timezone`; `"fixed"` runs on the wall clock of `timezone` (an IANA name) wherever the Mac is, across either zone's daylight-saving changes. `paused` stops the schedule only, and only a `cron` or `interval` cadence is ever paused: a `manual` one is saved without it, and a saved `manual` cadence that says `paused` is read as not paused. `active_since` is when the schedule last started running on its own (registered, changed, resumed or re-enabled); a time before it is never run or reported as missed. Every registration, `declagents.set_schedule`, and `declagents.set_enabled` turning an agent on validate the cadence first: a five-field cron whose fields parse (plain digits, `*`, ranges, lists and steps; no sign) and stay in range (day-of-week is 0-6, Sunday first; constraining both day-of-month and day-of-week is refused; on the Mac's clock a cron must constrain at least one field and need at most 366 launchd calendar entries), a positive interval of at least a minute (`90`, `15m`, `2h`, `1d`; schedules can repeat at most once a minute, since each scheduled time is a minute), an empty schedule for `manual`, and, for a fixed zone, a real IANA zone. Enabling an agent whose saved cadence fails this changes nothing and says why. The cadence itself is left out of the spec's fingerprint, so pausing a schedule, or changing only the cadence, does not make an open edit of the agent stale; `declagents.set_schedule` on an agent made with Build an Agent also saves its builder answer, which is part of the fingerprint (see below). A fingerprint a project recorded before this, with the cadence counted, still names the same agent.
- **Due, late and missed.** A fixed-zone schedule with clock times is installed to fire every hour at each minute its times could fall on locally (its minutes shifted by 0, 15, 30 and 45, since zone offsets differ by whole quarter hours); a Mac-clock one is installed as written. For a schedule with clock times (a cron, or an interval that fits the clock), `car agent run --scheduled` runs the agent for the most recent time at or before the launch that is less than 15 minutes old and has not run; only when that time has a record (a run, a miss or a failure) does a launch up to 30 seconds early run the next one; a launch that early whose passed time is 15 minutes or more old and has no record records that time first (missed, or failed if a stopped run had taken it), then runs the next time in the same launch. A launch 15 minutes or more after its time (launchd's run on wake for a time the Mac slept through, or a fixed-zone check after the Mac was off) records the time as `missed` and runs nothing for it: there is no catch-up run. An interval that does not fit the clock, and on Windows every interval, keeps the OS interval timer and cannot tell a late launch from an on-time one: after the Mac sleeps it runs once on wake, never a backlog, and it reports no missed times. It runs for the minute a launch lands in, never for a minute that began before the schedule started or resumed. Nothing is reinstalled when the Mac changes zone or either zone changes for daylight saving. A time that a daylight-saving change skips does not run that day; one it repeats runs once, at its first occurrence, and counts as missed from then if it did not run.
- `declagents.set_schedule` — **Params** `{ id: string, phrase: string, timezone?: string }`. **Returns** `{ id, cadence, schedule: { state, summary?, next_run_at?, note? } }`. Parses `phrase` with the `schedule.suggest` grammar (`every N minutes`, `hourly`, `daily at 7:00 am`, `weekdays at 8:30`, `weekends at noon`, `every Monday and Thursday at 17:00`, `only when I ask`, …) and replaces the agent's cadence. `timezone` (IANA) fixes the zone and wins over one in the phrase. Without it, a zone written at the end of the phrase (`ET`, `America/New_York`) fixes the zone, and a phrase with none runs on the Mac's clock. A paused schedule stays paused when the new one repeats too. `only when I ask` ends the pause, so a schedule given after it starts running. An agent made with Build an Agent also gets `phrase` and `timezone` as its builder answer (`builder_draft.cadence`, `builder_draft.timezone`), so rebuilding it from the builder keeps this schedule; that answer is part of the agent's identity, so its fingerprint changes as with any edit. An unparseable phrase is an error naming it and changes nothing. Host-management only, like `declagents.set_enabled`: package clients reach it through the generated HostClient wrapper (`declagentsSetSchedule` / `declagents_set_schedule`), not a `CarRuntime` method.
- `declagents.pause` — **Params** `{ id: string, paused: bool }`. **Returns** `{ id, cadence, schedule }`. Stops (`paused: true`) or restarts the agent's schedule and takes its OS schedule down or puts it back. Only the schedule: the agent stays enabled, and Run now and chat work. Errors for an agent with no `cron` or `interval` cadence. Host-management only; package clients reach it through the generated HostClient wrapper (`declagentsPause` / `declagents_pause`).
- `declagents.runs` — **Params** `{ since?: string, id?: string, limit?: number, before?: string, run_id?: string }`. **Returns** `{ runs: [AgentRunRecord], schedules: [{ id, name, enabled, cadence, state, summary, runs_on_clock, next_run_at, last_run, missed, installed, note? }] }`. `runs` are scheduled-run records, newest start first, started at or after `since` (RFC 3339) when given, for one agent when `id` is given: each agent's newest `limit` (default 50, at most 200; `0` returns schedules only) older than `before` when given (a start time in RFC 3339, or a `run_id`, to page back from the last record of the previous page; `before` pages one agent's records, so it needs `id`, and the `run_id` cursor is exact where a time cursor skips records that started at that very instant). A listed record leaves out `result` and carries at most 2 KB of `output` and `error`, and of `agent_said` (copied from `result` when the run failed in a way its answer can't speak for), with `output_truncated: true` only when one of them was cut, and `result_omitted: true` when the record had a `result`; `run_id` (with `id`) returns that one run in full instead, with `result` and with `agent_said` at the top level as a listing has it, uncut. `since`, `limit` and `before` page the records only: `schedules` and their `missed` times are the same whatever they are. A record is `{ run_id, agent_id, agent_name, trigger: "schedule"|"manual", status: "running"|"succeeded"|"failed"|"missed", scheduled_for?, started_at, finished_at?, output?, error?, model_served?, stood_in?, result? }`, where `trigger: "manual"` is a missed time run by hand (below), `result` is the full `declagents.invoke` reply and a `missed` record is a scheduled time launched too late to run. Records are files at `agent-runs/<agent id>/<run id>.json` in the folder that holds the agent registry (`<state root>`, or the folder of the `CAR_DECLAGENTS_PATH` file), 0600 in 0700 folders on macOS and Linux (on Windows they take the folder's permissions), and each agent keeps its 200 newest; this method returns their contents, output included, so it is host-management only, like `declagents.pause`: package clients reach it through the generated HostClient wrapper (`declagentsRuns` / `declagents_runs`), not a `CarRuntime` method, and a bound agent's session is refused. `schedules` lists every agent whose cadence is `cron` or `interval`: `state` is `active`, `paused`, `disabled` or `failed` (should run but is not installed, or its saved schedule cannot run, even with an old job still installed; `note` says why), `runs_on_clock` says whether the schedule has clock times (so late launches are missed rather than run), `next_run_at` is the next clock time (for an interval off the clock, the last run plus the interval, an estimate) and `null` when paused or disabled, or when this platform's scheduler cannot take the schedule (which then lists no `missed` times either), `last_run` is the newest record, as a listed record shows it (a preview, no `result`), `installed` says whether this state folder's job is installed, `note` also carries the reason the last install was refused (an overridden folder on Linux or Windows, or a schedule the platform cannot take) until a later install succeeds or the schedule rests, and `missed` holds the latest 20 clock times since `active_since` 15 minutes or more old with no run, oldest first, counted after the times that ran are set aside (a `missed` record counts as no run). Once an agent has 200 records, no time up to 30 seconds after its oldest kept record started is reported (or can be run by hand), since a record started before that one may have run it and been pruned. It is meant for a host that shows each agent's schedule and its run history, including runs that happened while the host was closed, deduplicating by `run_id`.
- **Scheduled runs through `declagents.invoke`.** `trigger: "schedule"` marks a run the agent's schedule started, and only the scheduled-run path may send it: it requires host-management authority (`car agent run --scheduled` connects with this machine's host key, and refuses to start from a process with `CAR_AGENT_ID` or `CAR_AGENT_TOKEN` set; on a daemon with no host token installed nobody is the host, so every scheduled run is refused with `this operation requires the host-management role` and its cause: the launch records the time `failed` with that reason and exits 1, and the daemon logs it at warn and emits the host event `agent.scheduled_run_refused`, whose `agent_id` is the agent and whose `payload` is `{ scheduled_for, reason }`) and a `scheduled_for` the launch chose, checked as given (a time of the agent's schedule, since it started, at most 30 seconds ahead and less than 15 minutes old, with no run yet; never swapped for a newer time), plus, when given, a `run_id` not used before. The daemon re-reads the agent as saved, under the lock schedule changes take, and refuses a run for an agent now paused, turned off or removed ("has no active schedule"), or whose schedule this platform's scheduler cannot take (the same check that installs it; `car agent run --scheduled` refuses it too, so a job left from an earlier schedule never runs it). It then checks `run_id` is a plain file name (letters, digits, `-`, `_` and `.`, not starting with `.`) before anything is written, reserves the scheduled time atomically, so two launches of one time never both run within one CAR state folder (a registry shared by several state folders through `CAR_DECLAGENTS_PATH` is not supported for scheduling; the other is refused with "already has a run for its scheduled time"), writes the run record as `running` (if that write fails the reservation is given back, so a retry of the time can run), and rewrites it when the run ends; the reply gains `run_id`. A daemon that stops between reserving a time and writing its record leaves that time reported as missed; a later launch of it, however late, finds the reservation with no record, records the time `failed` ("the background service stopped before this run finished") once, and does not run it; the reply says the time was recorded as failed, and if that record cannot be written the launch fails rather than skipping. On every platform the record is read and rewritten under one per-agent file lock (`flock` on Unix, `LockFileEx` on Windows), so marking a run failed never overwrites a finished record. A scheduled run of an agent that reads Mail (built with Mail allowed, or allowlisting a Mail tool) fails before the model runs, with a plain message and a failed record, when the Mail Automation permission is not `granted`, rather than running without its mail tools. `car agent run --scheduled <id>` sends this: it picks the due time (or records a late one as missed, once), and gives the agent an input naming that time, its last finished scheduled run, or missed time run by hand, with a result, and any such earlier run with no finished record yet (it may still be running, or may have been cut off), each named as a scheduled run or one started by hand (a plain Run now or a chat leaves no record, so it is not named). When it cannot reach or start the daemon (it starts one with `--exit-with-parent` and the user's tool folders on `PATH`), it writes the failed record itself; when the daemon stops mid-run it marks that run failed only if it is still `running`; and a schedule paused, turned off or removed while the run was starting, or a time another launch took, leaves no record. `trigger: "manual"` (host-management authority) may be sent by Run now; with `scheduled_for` naming one of the schedule's missed times (a clock time since `active_since`, 15 minutes or more old, with no run), the daemon reserves that time for one by-hand run, under the same schedule lock and reservation rule as a scheduled launch (a scheduled launch never takes a time that old), writes the run record with `trigger: "manual"`, and the time leaves `missed`. A time that is not missed, or one already run by hand, is refused with a plain error; a by-hand run that fails to start still counts as that time's run. When the daemon starts, any record still `running` (a run the previous daemon was on when it stopped) is marked `failed` with "the background service stopped before this run finished". Any other `trigger` value is an error.
