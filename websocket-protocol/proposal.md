### proposal

#### `proposal.submit`
- **Params**: `{ proposal: ActionProposal, session_id?: string, scope?: RuntimeScope, ... }`
- **Returns**: serialized `ProposalResult`; each `ActionResult` may carry `rolled_back: true` when the action succeeded but an enclosing abort restored the proposal's state transaction. False is omitted. `status` still reports whether the action executed, `state_changes` is empty after rollback, and `error` may retain a human warning that external effects remain; never match that warning to detect rollback.
- Triggers `tools.execute` callbacks to the client for each `tool_call` action. See `docs/agent-ir-spec.md` for the proposal and result shapes.
- **Gated by the session's permission tier.** Before any action dispatches, the proposal is admitted against the session's granted standing tier (`permission.set_tier`, default `sandbox_edit`). An action whose required tier exceeds the grant — or a `full_access` action, which is always mandatory HITL — blocks the **whole** proposal: every action comes back `rejected`, nothing executes, and no state write lands. The error names the fingerprints to hand to `permission.approve`; re-submitting after approval succeeds. Run `permission.evaluate` first to see the same verdict without submitting. See the `permission.*` section.
- **Statically verified before dispatch.** The session runtime's static-verification gate refuses the **whole** proposal, before any action runs, on an unregistered tool, parameters that violate the tool's registered schema, a `tool_call` with no tool, or an **unmeetable dependency**: an action that needs a key (through `state_dependencies`, or a precondition that fails on an absent key) which is not in state at submission (read in the namespace the action executes in when the proposal has a `scope.tenantId`, below) and which nothing ordered before it can write — no declared writer (`expected_effects`, or a `state_write`'s key) that can itself run, and no `tool_call`. That includes a key nothing in the proposal declares writing. "Before" is the executor's order: an earlier dependency level, or earlier in a level that runs sequentially (one action, or any action with the default `failure_behavior: "abort"`). A dependency cycle among declared effects is the usual case. Such a proposal cannot complete through its declared effects and ordering; the error names each action and the key it waits on. A `tool_call` ordered before the action breaks the rule, because its handler can set the key without declaring it — a `state.set` sent from a `tools.execute` handler on this connection, an FFI `state_set` from a callback, a car-multi delegate writing shared state — so the plan may complete; streaming and long-running tool calls don't count, since they return before their handler is done. In that case, and for a key already in state, the per-action check rejects each blocked action when execution reaches it, and the other actions still run. The residual is a race: a `tool_call` in the same concurrently-run level, a streaming or long-running `tool_call` ordered earlier whose handler happens to finish in time, or another client's `state.set` on the session could set the key in time, and the gate refuses that plan anyway because it completes only by timing. Other precondition and state-dependency findings are per-action, because the check sees only declared effects.
- `session_id` (optional) scopes per-action policy validation to a session opened via `session.policy.open` on this connection's runtime. Global policies still apply, plus the session's. Omit for the default global-only path. See `docs/proposals/per-session-policy-scoping.md`.
- After a `tools.execute` callback explicitly returns terminal failure, this WebSocket session is halted. Later submissions return the normal whole-proposal `rejected` result shape and dispatch no tools until a host clears the latch or the client reconnects. No run is synthesized or completed automatically.
- `scope` (optional) is a `RuntimeScope` — `{ callerId?: string, tenantId?: string, claims?: object }` — attaching per-execution caller / tenant identity. When `tenantId` is set, the runtime routes per-action state R/W (`StateWrite` / `StateRead` / `Assertion` + action `expected_effects`) through the tenant-scoped view so distinct tenants can't observe each other's keys (Parslee-ai/car#187 phase 3). Every check made before an action runs reads each action's keys in the namespace that action executes in: the static-verification gate, the transactional pre-check, per-action preconditions and `state_dependencies`, and replan verification. A `StateWrite` / `StateRead` / `Assertion` is judged against the tenant's keys, so a key that exists only in shared state does not satisfy its dependency; a `ToolCall` runs on the unscoped path and is judged against shared keys, so a key a tool handler `state.set`s satisfies a later tool call's dependency. A `ToolCall`'s declared `expected_effects` are writes to both the shared key and the tenant's copy of it, because its handler can `state.set` the shared key while its callback's `state_changes` land in the tenant's namespace: such an effect frees a dependency in either namespace, and the transactional pre-check reports a conflict between such a tool call and a tenant `StateWrite` of the same key (write-write) or a tenant `StateRead` / `Assertion` reading it (read-write) when no dependency orders them. Ordering is the executor's, taken from the keys as written: a tenant action listing `k` in `state_dependencies` runs after a tool call declaring `k`, so that pair does not conflict, unless the action itself writes `k`: the executor's DAG records only the last declared writer of a key, so a `StateWrite` of `k` gets no edge to the tool call and the pair conflicts, as it does in an unscoped proposal. Two unordered tool calls declaring the same `k` report two write-write conflicts, one for `k` and one for the tenant's copy, and reject the same two actions. In strict mode the conflicting actions are rejected; in warn mode the conflicts are recorded as `TransactionConflict` events and the actions run (Parslee-ai/car#3133). None of these checks can observe another tenant's keys: naming one by its stored `tenant:<id>:<key>` form from a tool call finds nothing, so no refusal or conflict report can carry another tenant's value. A replanner is handed the state under raw key names, as for an unscoped proposal, minus other tenants' keys. Policies read the shared store for every proposal (see `policy.register`) (Parslee-ai/car#3121). The car-a2a bridge already passes this automatically for inbound A2A messages; direct WS callers building their own proposals attach it here. When both `session_id` and `scope` are supplied, the runtime currently routes through `execute_scoped` (scope wins) — combining per-session policies with per-tenant scoping is a follow-up.
