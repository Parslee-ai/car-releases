### lattice

The **CAR Lattice**: humans, CAR agents, CAR Coder, Claude Code, Codex, and other runtimes on this daemon find each other by capability and work together as peers. A participant that **joins** becomes a *node*: it declares a project, capability tags, and a status, and others find it by what it can do instead of by address.

CAR agents use these methods over the WebSocket. Claude Code, Codex, and other MCP clients use the matching tools on the daemon's `/mcp` endpoint (`lattice_join`, `lattice_leave`, `lattice_nodes`, `lattice_find`, `lattice_claim`, `lattice_release`, `lattice_claims`, `lattice_wait`). A CAR Coder run joins with `coder.start { lattice }`. People join as **human nodes** through the operator's client (`car lattice human join`). Everything lands in the same tables, so a search does not care which runtime — or whether a person — answers.

This is collaboration among participants that already exist, not orchestration: nothing here spawns, schedules, or commands a node. `lattice.find` returns addresses; the asker then uses `agents.message` (or `peer_message`) with the usual guard, policy, and audit, and the recipient decides what to do under its own permissions.

- **Identity**: every method keys on the caller's **peer address**, derived by the daemon — the bound `agent_id` for a WebSocket agent, the minted `mcp:<peer-id>` for an MCP session. There is no parameter that names whose profile or claim to change. An anonymous WebSocket connection has no address and is refused, unless it is the operator's host client, which may list, find, register human nodes, and answer for them. The connection must also still **own** that agent id: when a newer attach supersedes the binding (a respawn, or a second connection presenting the same `CAR_AGENT_ID`/`CAR_AGENT_TOKEN`), the older connection's calls are refused with "a newer attach superseded it" and its profile stops being listed, even if its socket stays open. A supervised agent that holds its own agent-bound connection must therefore not also let a `car-runtime` client in the same process bind with the inherited `CAR_AGENT_ID`/`CAR_AGENT_TOKEN` — that second attach takes the binding. Read the variables once and remove them from the environment before constructing another client, or rejoin after a "superseded" refusal.
- **Human nodes**: a person is addressed as `human:<name>` and listed with `type: "human"`. A message to one is not pushed anywhere: it is recorded as a request in an append-only ledger (`<state root>/lattice/requests.jsonl`), returns `outcome: "awaiting_human"` with an `answer_token` that only the asker receives, and is announced to host subscribers as a `lattice.human_request` event with payload `{ request_id, from, to, kind, cross_owner, mirrored }` — who asked whom and the kind, never the question, since host events are readable by every session. `mirrored` is true when the request actually became an approval row (which raises its own prompt) — the row is created before the event, and a failed mirror reports `false`; `cross_owner` when the question arrived over a connection with another owner's CAR. A review from another owner's CAR is never mirrored, including by the reconciler that re-mirrors pending reviews after a restart. One asker may have at most 10 unanswered requests open with one person; the cap is per asker, so one chatty agent cannot make a person unreachable for everyone else. The operator answers with `lattice.respond` (or `car lattice respond`); the answer reaches the asker as an `answer` message with `in_reply_to` set to the request's `id`, and a `lattice.human_answered` event is emitted. A `review_request` is also mirrored onto the host approval ledger as a system-level approve/deny row, so CarHost and the paired iMessage/Slack approval channels can decide it; those channels carry only approve/deny, never free text, so a question that needs words is answered with `lattice.respond`. `host.resolve_approval` refuses a `lattice-*` row from anything but the operator's host session — the row is system-level so those surfaces can reach it, and without that refusal the asking agent could approve its own review. It also refuses any resolution but `approve` or `deny`, because the resolution is passed back to the asker as the person's answer. The row itself carries who asked whom and a summary of the review's first line (at most 120 characters), never the full text: approval rows are readable by every session that reads host approvals or events. The full text is on `lattice.requests`. A reply to a request for a person counts only when it comes from that person's `human:<name>` address, so another peer cannot answer for them with a forged `in_reply_to`. Registering a human and answering for one require the operator's **host** session with no exception: on a daemon running without auth nobody is the operator, so nobody can. A request is recorded under the asker's peer address — an attached agent's `agent:<id>` sender becomes `<id>` — which is where the answer is delivered and who `lattice.wait` recognizes as the asker.
- **Persistence**: agent profiles and claims are in memory; human nodes (`<state root>/lattice/humans.json`), requests to humans, connections (`<state root>/lattice/connections.json`, mode 0600), standing auto-accept rules (`<state root>/lattice/org_rules.json`, mode 0600), and LAN knocks with their block and quiet lists (`<state root>/lattice/knocks.json`, mode 0600) persist across restarts. The request ledger is append-only and not yet compacted; a torn last line after a crash is terminated and skipped on load.
- **Work contexts**: profiles and claims are per work context. A node joined from a connection bound to an organization (a supervised agent, a `car claude` session, or a `coder.start { lattice }` run in that org) is listed and found only by callers bound to the same organization, and by the operator; personal callers never see it. It reaches another CAR only over a connection its own organization verified (`verified_by` `org:<org>` or `cert:<org>:<account>`): there, and only there, it is published (its listing row tagged `org`) and resolved by an `agents:<project>` share or a share list naming it; a personal connection or another org's never carries it. This owner's own devices receive every org node tagged with its org, but a device speaks for an org only from the roster of the login that holds that org here: the trusted own-device set spans every held login, so a device found under another login cannot list, receive, or send an org's work. Within that, an own device's org rows are shown only to sessions bound to that org, an org's message to an own device goes only to a node that device listed as the org's (an answer excepted), and an own device's org message reaches only that org's node. Org rows travel in a listing's `org_nodes`, apart from its `nodes`, so a CAR older than org tags shows only personal nodes; a cached listing is read only for the key that sent it. An address that rejoins in another context releases the claims it held in the old one. A `display_name` that is another live agent's address is refused only when that agent is in the caller's own view. Each organization (and each personal-bound account) has its own claim table, so the same `project`/`item` held in two contexts is two independent claims, and `lattice.claims` lists only the caller's context. An organization-bound caller sees no human nodes, and of other CARs' nodes only those tagged with its organization that arrived over a connection that organization verified (a row whose tag does not match its connection is dropped); personal callers see only untagged rows. Messages follow the same rule across CARs. An organization-bound sender may send to a node on another CAR only over a connection its own organization verified, and the message carries that organization in `carPeerFromOrg`. The receiving CAR accepts a `carPeerFromOrg` only over a Lattice connection that organization verified, then delivers an organization's message only to that organization's node and a message without one only to a personal node — so org work never lands in a colleague's personal agent, nor personal work in an org agent. A message a sender's context would refuse — including one whose org differs from the target row's tag — is refused before any cross-owner hold, so it never waits in the operator's queue. Only contexts under the default Parslee authority (`https://api.parslee.ai`) cross CARs: a connection's `verified_by` records no authority, so an org of the same id under a staging or self-hosted `api_base` stays on its own CAR. The same holds for peer messaging on this CAR: an organization-bound coder run's peer session carries the run's context, so it messages and is messaged only within its organization, and `peer_list` / `agents.peers` show node profiles only from the caller's own context. The operator's `lattice.claims` lists every context's claims; a host connection bound to an organization (`session.bind_context`) is refused the Lattice. Personal and legacy callers, and MCP sessions on the daemon's `/mcp`, behave as before.
- **Across daemons**: a node on another CAR is addressed `<node>@<car>` — its address there (`mcp:<id>`, an agent id, `human:<name>`) and this daemon's name for that CAR. Two kinds of CAR are reachable, and their trust never mixes:
  - **This owner's other devices** — the ones the end-to-end encrypted sync oplog already trusts, named by device name. Each daemon fetches the other's live nodes over the signed peer surface every 15 s (a listing is usable for 60 s), so `lattice.find` and `lattice.nodes` rank local and remote nodes together; remote rows carry `remote: "<car>"`. A message to `<node>@<car>` travels the signed peer surface, and the recipient sees the sender as `<node>@<its name for this CAR>`, so a reply is addressed by copying `from`. `lattice.wait` resumes on a reply from a remote node, and a person on another device answers exactly as a local one does.
  - **Another owner's CAR** — only through a **connection** both operators agreed to (`lattice.connect.*` below), named by the connection's label. That CAR sees, and may message, only the nodes this side shares on that connection; its key may call the Lattice methods and Lattice messages and nothing else on the peer surface (no fleet, tasks, or proposals); listings and message bodies on a connection are sealed (X25519 + ChaCha20-Poly1305, keyed per connection) — the routing metadata beside them (who a message is to and from, its kind, what it answers) is not, and the per-connection key is static, so there is no forward secrecy; give a connection that crosses a network you do not control an https peer URL (`--a2a-public-url`), and see #2260 for moving connections onto a scheme that seals the whole call with a fresh key per request; and a message that looks like a raw credential to the feedback scrubber is refused before it is sealed — a heuristic that catches tokens and keys in their usual shapes, not a guarantee against one deliberately encoded. Its requests to a person are capped per CAR (not per sender name, which that CAR chooses) and are never mirrored onto the approval channels: those prompt this owner about their own agents. Either owner can end the connection at any time.
  - **A colleague's CAR in this organization** — when org-scope sync is on (`PARSLEE_SYNC_ORG_SCOPE`), a CAR whose key an org admin **attested** (`lattice.org.attest`) can be offered a connection without an invite code or a fingerprint exchange (`lattice.connect.invite { member }`, then the colleague's `lattice.connect.accept { id }`). Attestation establishes identity only: until a connection is accepted, an attested key may call the two org handshake methods and nothing else — no listing, no messages. Once accepted, the connection is the same as any other (same scope, sealing, shares, and exit). See **Org-attested connections** below.
  - **Answering without being shared**: a node may ask a shared node on another owner's CAR without being shared itself — a Claude Code or Codex session gets a new `mcp:` address each time, so it usually cannot be shared ahead of time. The node it asked may send **one** `answer` back, with `in_reply_to` set to that question, and only to the asker, over the same connection, within seven days — long enough for a person to answer after a weekend. Anything else to an unshared node — a second answer, another of that CAR's nodes answering, a new question — is refused by both daemons, and the asker's daemon enforces it on its own rather than trusting the other side's. Only a question that was delivered opens an answer, and open questions are capped per connection, so one CAR cannot crowd out another's. Who may answer a question is remembered past the window: an expired question is unanswerable, never answerable by anyone.
  - **Nothing relays**: a remote node is reachable only on the daemon that serves it, and an inbound message is delivered only to a node served on the receiving daemon.
- **Declared, not verified**: a capability tag is the node's own claim about itself (an operator's, for a human node). It changes who appears in a search and authorizes nothing.

#### `lattice.join`
- **Params**: `{ project: string, capabilities: string[], display_name?: string, runtime?: string, status?: string, note?: string, type?: string, name?: string }`.
  - `project`, `display_name`, and `runtime` are 1–128 of `[A-Za-z0-9._-]`. `display_name` is a label, never an address; it defaults to the agent id (or `mcp-<prefix>`). Name the work, not the model or harness. `runtime` is shown to the operator's host client only: other agents never see it (see `lattice.nodes`).
  - `capabilities`: at most 32 tags of 1–64 bytes (letters, digits, spaces, `-_.+#/`), lowercased and de-duplicated. Prefer specific multi-word tags (`parser-debugging`) over single words.
  - `status`: `available` (default), `busy`, or `away`. `note`: one line, at most 280 bytes.
  - `type`: `agent` (default) or `human`. With `human`, `name` (1–128 of `[A-Za-z0-9._-]`) is required, the node's address is `human:<name>`, `project` is optional (default `all`), and the caller must be the operator's host client. A node in project `all` matches every `project` filter, so a project-scoped `lattice.find` still finds the person who decides.
- Calling again replaces the profile — that is how a node changes status.
- **Returns**: `{ self, rejoined, node: { address, display_name, runtime, project, capabilities, status, type, note, can_receive, updated_at_ms } }`.

#### `lattice.leave`
- **Params**: `{ human?: string }`.
- Without params, drops the caller's profile and releases every claim it holds. With `human`, the operator's host client removes that human node and closes every request still waiting on them (askers receive "no answer: … left the Lattice").
- **Returns**: `{ self, left, released_claims, closed_requests? }`.

#### `lattice.nodes`
- **Params**: `{ project?: string }`.
- Lists **live** nodes — an agent profile whose connection has gone is omitted even before cleanup runs; human nodes are always listed. The caller's own row carries `self: true`.
- **Returns**: `{ self, count, nodes: [node row + self] }`. A row from another CAR has `address: "<node>@<car>"` and `remote: "<car>"`.
- **`runtime` is operator-only.** It appears in rows returned to the operator's host client; rows returned to an agent (here, in `lattice.find`, `peer_list`, and `agents.peers`) omit it, and listings sent to another owner's CAR never carry it. Agents shown each other's model family or harness split into same-label factions that take more rounds and tokens and succeed less often, even when the label is an arbitrary tag (arXiv:2609.35928). Finding a peer goes by capabilities, which never read `runtime`.

#### `lattice.find`
- **Params**: `{ need: string, project?: string, include_unavailable?: boolean, limit?: integer }`.
  - `need` is plain language: `"Rust parser debugging"`. `limit` is 1–50, default 10.
- Matching is lexical and deterministic — it needs no model, so it answers the same on a machine with no local inference. The need and each tag are lowercased, split into words, stripped of filler words (`someone`, `good`, `need`, …), and reduced to a crude stem so `debugging`/`debugger`/`debug` meet. A tag scores only if **every** word in it appears in the need: `parser-debugging` does not match a need for `parser generation`. Nodes whose matched tags cover every word of the need rank first (`covers_need: true`), then by score, then by address.
- Excludes the caller, nodes that cannot receive a message, and — unless `include_unavailable` — nodes that are `busy` or `away`. Human nodes are included; a need like `"production deployment approval"` finds the person who holds that authority.
- **Returns**: `{ self, need, terms, count, matches: [node row + { matched, covers_need, score }] }`. `terms` is the need as the matcher read it, so a caller can see why nothing matched.

#### `lattice.wait`
- **Params**: `{ message_id: string, timeout_secs?: integer, answer_token?: string }`.
  - `message_id` is the `id` that `agents.message` / `peer_message` returned for the question. `timeout_secs` is 0–300 (default 30); `0` checks once without blocking.
  - `answer_token` is the token a message to a human returned. It is needed only when waiting from a different session than the one that asked.
- Blocks until a reply to that message arrives — a message with `in_reply_to` equal to `message_id` addressed to the caller (from an MCP inbox, consumed so it is not read twice, or pushed to an attached agent), or a human's answer recorded in the ledger — or until the timeout passes. Call again to keep waiting: a request to a person stays answerable for as long as the ledger holds it.
- **Durable resume**: a human's answer survives the asker's session ending and a daemon restart. The asking address retrieves it directly; any other session needs the `answer_token` — the request id alone is not enough, because it appears in host events and approval rows other sessions can read.
- **Returns**: `{ answered: true, source: "inbox" | "pushed" | "ledger", message }` or `{ answered: false, pending_human, waited_ms }`.

#### `lattice.requests`
- **Params**: `{ all?: boolean, to?: string, limit?: integer }`.
- **Authorization**: **host-only**, with no exception for a daemon without a host token.
- Requests addressed to human nodes, oldest first; pending only unless `all`. `to` is `human:<name>` or a bare name. The newest `limit` (1–1000, default 100) are returned.
- **Returns**: `{ count, total, requests: [{ id, from, to, kind, body, asked_at_ms, remote, origin, cross_owner, mirrored, connection?, answer?: { body, by, answered_at_ms } }] }` — `origin` is where the asker is as far as the daemon knows: `another_owner` (recorded connection), `device` (a CAR that is one of this owner's devices now), `local`, or `unknown` (another CAR this daemon cannot place: a question saved before connections were recorded, a removed device, or one of this owner's devices before its roster has synced — never presented as one of this owner's devices); `remote` is the asker's CAR (`<car>` from `<node>@<car>`) or `null` for an asker on this daemon; `connection` is the Lattice connection the question arrived over, **recorded when it was asked**, and `cross_owner` is whether there is one — so neither depends on what this daemon can see later (a device roster not yet synced, a connection since ended); `mirrored` is whether an approve/deny row exists for it right now, in which case a client answers it as that approval rather than with `lattice.respond` — `by` is `host`, `approval` (an approve/deny channel), or `lattice` (closed because the person left). The asker's answer token is never included.

#### `lattice.respond`
- **Params**: `{ request_id: string, body: string, acknowledge_processing?: boolean }`.
- **Authorization**: **host-only**, as above — an answer here speaks for a person.
- An answer to a node on another owner's CAR crosses like any message from here: until the owner has agreed on that connection, the call fails with the processing notice (the same text `agents.message` holds with) and sends nothing. Answer again with `acknowledge_processing: true` to agree, which records `acknowledged` on the connection and releases any message held only for that notice, and send. An agent cannot answer its own escalation: the ledger refuses an answer whose author is the asker.
- For a mirrored review, the approval row is resolved first: if an approval channel already decided it, that decision stands and this call fails naming it, so two different answers to one decision are never both recorded. Otherwise records the answer durably and delivers it to the asker as `{ from: "human:<name>", kind: "answer", in_reply_to: request_id, body }`. An asker that is no longer connected is not an error: the answer stays in the ledger for `lattice.wait`.
- **Returns**: `{ request_id, answered: true, delivery }` — `delivery` is the asker-side outcome, or a note that the answer was kept for a later `lattice.wait`.

#### `lattice.claim`
- **Params**: `{ project: string, item: string, ttl_secs?: integer, note?: string }`.
  - `item` names the work — a file, issue, branch, or task — 1–256 bytes on one line. Claims are scoped to `project`.
  - `ttl_secs`: 60–7200, default 1800. Claiming again as the holder renews; renew after `renew_after_ms`.
- Exclusive: the holder check and the insert happen under one lock, so concurrent claimants for one item get exactly one winner.
- A conflict is a **result, not an error**: `{ claimed: false, held_by: claim }` names the holder so the caller can message them instead of working around it.
- **Lifetime**: an MCP session's claims are released when the session ends (`DELETE /mcp` or idle expiry) — a reconnect is a new principal that could never renew them. A WebSocket agent's claims survive a disconnect until they expire, because a respawn reattaches under the same address. Its profile does not.
- **Returns**: `{ claimed: true, renewed, claim }` or `{ claimed: false, held_by }`, where a claim is `{ project, item, holder, note?, claimed_at_ms, expires_at_ms, renew_after_ms, holder_live }`.

#### `lattice.release`
- **Params**: `{ project: string, item: string }`.
- Releases a claim the caller holds. Another node's claim is not released: the result is `{ released: false, held_by }`, the same shape as a `lattice.claim` conflict.
- **Returns**: `{ released }` — `false` when nothing was held.

#### `lattice.claims`
- **Params**: `{ project?: string }`.
- **Returns**: `{ self, count, claims: [claim + { mine }] }`, live claims ordered by project then item.

#### `lattice.connect.invite`
- **Params**: `{ purpose: string, project: string, label: string, share?: string[], ttl_secs?: integer }`; or, to offer a connection to an attested colleague, `{ member: string, purpose: string, project: string, device?: string, label?: string, share?: string[], ttl_secs?: integer }` (see **Org-attested connections**).
- **Authorization**: **host-only** for this and every `lattice.connect.*`, `lattice.knock*`, `lattice.connections`, `lattice.disconnect`, `lattice.directory`, `lattice.relay.probe`, and `lattice.org.*` method — a connection extends trust to another owner, which only the operator decides.
- Starts a connection with another owner's CAR. `purpose` (one line, at most 280 bytes) is shown to the other owner and is refused if it looks like a credential; `project` binds the connection to one project; `label` is this side's name for that CAR (1–128 of `[A-Za-z0-9._-]`, unique among live connections and different from every device name, so `<node>@<label>` names one CAR); `share` lists the local node addresses the other owner may see and message (at most 64; empty shares nothing), each an address or an `agents:<project>` entry (see `lattice.connect.share`). `ttl_secs` is 1–86400, default 3600. The daemon must be serving its peer surface (`--a2a-bind`), whose URL goes into the invite.
- **Returns**: `{ connection, invite, our_fingerprint }`. Give `invite` to the other owner and tell them `our_fingerprint` out of band. The invite carries a one-time secret: it is accepted once, and never after it expires.
- With `member`: `member` is a colleague's account as `lattice.directory` lists it, and `device` picks one of their CARs when they have several. `org?: string` picks the org that vouches for them; it may be omitted when one org is configured, or when exactly one of several attests a reachable CAR of theirs, and the offer is refused rather than guessed otherwise. Their CAR is told at once (`car/latticeOrgInvite`, which carries the org) and records the connection as `offered`; nothing is shared or reachable until they accept. `label` defaults to one derived from the account. Returns `{ connection, next }`. Refused when org scope is off, the member has no attested and announced CAR, or the org policy refuses the project or share list.
- **Org policy** (when org scope is on): an invite-code connection counts as outside every organization, so it is judged by the most restrictive combination of every configured org's policy (a permission only if all allow it, the smallest cap, only the projects every allow-list names — disjoint allow-lists refuse every invite-code connection), and a policy with `allow_outside_org: false` refuses it on both `invite` and `accept`. An org-verified connection is judged by its own org's policy alone.
- **Fingerprints** on a connection (`our_fingerprint`, `peer_fingerprint`) are 128 bits of SHA-256 over the CAR's signing key, written as eight groups of four hex digits so they can be read aloud — long enough that a key cannot be generated to match one, which is what lets the fingerprint catch an invite code swapped in transit. A `fingerprint` param is compared ignoring case, spaces, and punctuation, must be 32 hex digits, and a mismatch is refused without saying what the presented key's fingerprint is. The other side's fingerprint is never returned before the connection is active — not by `inspect`, `lattice.connections`, or the `lattice.connection_requested` event — so the only way to supply it is to have been told it. (Other peer surfaces still show the shorter `aa:bb:cc:dd` label of an already-trusted key.)

#### `lattice.connect.inspect`
- **Params**: `{ invite: string }`.
- What an invite asks for, before accepting it. Changes nothing.
- **Returns**: `{ purpose, project, inviter_url, expires_ms, expired }`. The inviter's fingerprint is deliberately not included: the operator must hear it from the inviter, not read it off the invite they are checking.

#### `lattice.connect.accept`
- **Params**: `{ invite: string, label: string, fingerprint: string, share?: string[] }`; or, for a connection a colleague offered, `{ id: string, label?: string, share?: string[] }`.
- Accepts an invite with this side's own share list. `fingerprint` is required: the inviter's fingerprint as they told you another way than the invite; the call is refused unless the invite carries that key. Presents the invite to the inviting CAR over the signed peer surface; nothing is active until the inviter confirms. One live connection per other CAR. If the inviting CAR does not take the invite, nothing is kept and the call can be retried.
- **Returns**: `{ connection, next, our_fingerprint }` — tell the inviter `our_fingerprint`.
- With `id`: accepts an `offered` connection with this side's share list. No fingerprint: the inviting CAR's key was attested by the org, and its owner chose this CAR when offering. The connection is active on both sides when this returns (`car/latticeOrgAccept` carries this side's sealed share list and returns the inviter's). Returns `{ connection }`. If the inviting CAR cannot be reached, the offer stays `offered` and the call can be retried. To decline, use `lattice.disconnect`.

#### `lattice.connect.confirm`
- **Params**: `{ id: string, fingerprint: string }`.
- The inviter confirms the CAR that accepted. `fingerprint` is required: the other owner's fingerprint as they told you; the call is refused unless their CAR presented that key. The connection becomes active on both sides, and each side's share list reaches the other sealed. If the other CAR cannot be told, this side rolls back and the call can be retried.
- **Returns**: `{ connection }`.

#### `lattice.connections`
- **Params**: `{}`.
- Every connection, newest first, without secrets.
- **Returns**: `{ count, connections: [{ id, label, role, purpose, project, state, peer_url, peer_fingerprint, our_share, their_share, invite_expires_ms, created_at_ms, activated_at_ms, ended, sealed, notice_owed, verified_by, identity, peer_account, accepted_by, our_share_rev, acknowledged, relay_org, transport, relay_pending }] }`. `transport` is `parslee_relay` for a connection the Parslee relay carries (then `peer_url` is `null` and `relay_org` names the org whose relay carries it; `relay_pending` is the handshake step or notice still owed to the other CAR, see `lattice.knock`), else `direct` with `relay_org` and `relay_pending` `null`. `acknowledged` maps each processing class the owner has agreed to on this connection to when (`{ "may_use_cloud_model": <unix ms> }`), and is empty until the first cross-owner message is approved. `state` is `invited`, `awaiting_confirm` (the inviter's next step), `awaiting_their_confirm` (the invitee's wait), `offered` (a colleague offered it; this side's next step), `active`, or `ended`. `verified_by` is `fingerprint`, `org:<org>`, `cert:<org>:<account>` (a Parslee device certificate for that org), or `tofu` (a LAN knock; such a connection also carries `identity: "unverified"`, otherwise `identity` is `null`); `peer_account` is the colleague's account on an org-verified connection; `accepted_by` is `standing_rule:<id>` when a standing rule accepted it, else `null`. `peer_fingerprint` is `null` until the connection has been confirmed (it stays on an ended connection that was once active), for the same reason `inspect` omits it.

#### `lattice.connect.share`
- **Params**: `{ id: string, share: string[] }`.
- Replaces what THIS side shares on an active connection (the full list; empty shares nothing). Removing a node takes effect here at once — the other CAR can no longer reach it, whatever its cached listing says. The other CAR is told, sealed; if it cannot be reached, it converges on its next listing pull, which carries the same list and a revision number, so a late or replayed update can never widen it again. The other owner does not re-confirm: narrowing is always safe, and widening exposes only this owner's own nodes. This is how an owner shares a coding agent that joined after the connection was made.
- **`agents:<project>` entries.** Any `share` list (here and in `lattice.connect.invite`, `lattice.connect.accept`, an org offer and its acceptance, `lattice.knock` and `lattice.knock.accept`, and standing rules) may hold `agents:<project>` instead of an address, `<project>` following `lattice.join`'s project rule (1–128 of `[A-Za-z0-9._-]`, not starting with `.` or `-`). It stands for every live **agent** node on this CAR joined in exactly that project — never a human node, and not a node in project `all` unless the entry is `agents:all`. It is resolved at the moment of use: delivery admission, and the listing and share list the other CAR receives. So a Claude Code or Codex session that joins the project later (a new `mcp:<peer-id>` address every session) is reachable without another `lattice.connect.share`, and one that leaves or disconnects is refused at once. The other CAR never sees the entry: its `their_share` and listing hold the concrete addresses, as `<addr>@<label>` rows, under a share revision that rises whenever the resolution changes. A direct connection's other CAR picks that up on its next listing pull (every refresher pass, 15 s); over the Parslee relay the listing is mailed again when the resolved nodes change; over an org relay the listing goes out once a minute. `our_share` in `lattice.connections` keeps the entry as typed. **Org policy:** `allow_human_share` never applies to the entry (it resolves to agents only). A policy with a `projects` allow-list refuses `agents:<project>` for a project not on it. `max_share` counts the entry as one entry when the share list is checked, and bounds what it exposes: the resolved agents fill only the room the explicitly named addresses leave under `max_share` (and the 64-node limit), choosing the lexicographically first addresses, so a share that passed the policy exposes at most `max_share` concrete nodes in total. A later, tighter `max_share` shrinks that room at once; named addresses are never dropped by it.
- **Returns**: `{ connection, other_car_notified, not_live }`. `not_live` lists the shared addresses that are not a live node on this CAR right now (never an `agents:<project>` entry, which stands for whichever agents are live) (an agent that is not running or never joined the Lattice, or a typo): the other CAR sees no such node until it joins. Over the Parslee relay a listing is mailed again whenever the shared nodes change — one joins, leaves, or changes its profile — not only when the share list does.

#### `lattice.connect.label`
- **Params**: `{ id: string, label: string }`.
- Renames this side's name for the other CAR — the `<car>` in `<node>@<car>` addresses of its nodes. Host-only. The label follows the same rules as one given at invite, accept or knock time (1–128 of `[A-Za-z0-9._-]`, unique among live connections, not one of this owner's device names); an ended connection cannot be renamed. Only this side changes: the label is never sent, and the other owner's name for this CAR stays as it is. The other CAR's nodes are listed under the new name at once; addresses using the old name stop resolving.
- **Returns**: `{ connection, renamed }` (`renamed: false` when the label was already that). Announced to host subscribers as `lattice.connection_renamed` with `{ connection, previous_label }`.

Connection changes are announced to host subscribers: `lattice.connection_requested`, `lattice.connection_offered`, and `lattice.connection_active` with `{ connection }` (the row above), and `lattice.connection_ended` with `{ id, label, ended }`. `lattice.org_attestation_conflict` with `{ org, peer_fingerprint }` says an org admin attested, to this account, a CAR key none of this owner's CARs holds.

#### `lattice.disconnect`
- **Params**: `{ id: string, reason?: string }`.
- Ends a connection on this side immediately — the other CAR's key stops being accepted, its cached nodes are dropped, and requests to this side's people from that CAR are closed — and tells the other CAR. If the other CAR cannot be reached, the notice is retried every 15 s for up to a day (`notice_owed` on the connection), because until it hears, its side still holds the connection open. On a Parslee relay connection the notice goes through the relay only, and is retried with backoff for up to a day until the relay takes it (`relay_pending`); a relay refusal is reported, never treated as the other side hearing. The `reason` travels sealed, and is withheld if it looks like a credential; leaving never fails because of it. The ended record keeps who ended it and when. Ending a connection does not recall anything already delivered.
- **Returns**: `{ ended: { at_ms, by, reason, revoked_our_share, revoked_their_share, closed_requests, note }, other_car_notified, notice_retrying }` — `by` is `us` or `them` (or, on a record ended without either owner acting, `org` when the attestation it was verified with was revoked or expired, and `policy` when the org's `max_connection_secs` ran out).
- Declines an `offered` connection, and withdraws an org offer this side made, the same way: the other CAR is told.

**LAN knock.** Ask a CAR discovered on the local network to connect, without an invite code. Design: `docs/proposals/lan-knock.md`. The other owner sees what the knocker says its purpose and project are, and this CAR's 128-bit key fingerprint, and accepts with their own label and share list, or declines. The result is an ordinary connection (same scope, sealing, shares, the processing notice on the first message, and exit) with `verified_by: "tofu"`.

- **Identity is unverified.** There are no device certificates yet. A knock shows only the knocker's fingerprint, never a name taken from its advertisement or request; the label is the accepting owner's choice. Purpose, project and address are the knocker's own claims and are shown as such: the claimed address (`claimed_url`) is never matched against a discovered CAR or a connection, so a stranger cannot borrow a neighbour's name or standing by claiming its address. The knocked CAR proves it holds the key it answers with by signing the knock's challenge together with the URL it serves; the knocker refuses an answer whose URL is not the address it dialled (a relay). Keys are pinned (Lattice scope only) only when the receiving owner accepts. If it matters who the other owner is, compare fingerprints with them. A later certificate will make `verified_by` `cert:<account>`.
- **The advertisement** (`_car-a2a._tcp.local.`) carries the peer URL, the host name (as any Bonjour service does), a protocol version (`v=1`) and a random token minted at every daemon start (`tok`). It carries no key, account or email. The host name is still visible to everyone on the network; turning discovery off (`lattice.knock.settings`) withdraws the record. A record at this daemon's own URL is this daemon, whatever name it advertises; a record carrying this daemon's token at another URL is listed as `claims_this_car` and cannot be knocked.
- **A knock runs nothing.** An unpinned key calling `car/latticeKnock`, `car/latticeKnockAccept`, `car/latticeKnockDecline` or `car/latticeKnockWithdraw` gets a knock-only scope: those methods only. An org-attested colleague's key may call them too. Bodies are at most 4 KiB, checked before anything is admitted. Unpinned callers get 5 calls per minute per key and 60 per minute across all keys, separate from the invite handshake's budget; the answers of a CAR this one knocked on (accept, decline, withdraw from that CAR's proven key) skip the all-keys total so strangers cannot starve them, and have a per-key limit of their own (30 per minute). An org-attested or certificate-admitted colleague's key is admitted at its org scope, but its knock calls are still budgeted: the same 5 per key and 60 overall, in an org pool kept apart from the unpinned one so neither can starve the other (answers to a knock this CAR sent use the per-key answer limit, as above). The transport block list applies to it as well, and the daemon also enforces the decline cooldown and one pending knock per key. A blocked key, a declined one within a day, and every new knock while this CAR is closed to knocks are refused before a nonce is spent. A key of this owner's own devices is refused in both directions. A knock's claimed address must be on this network: a private or link-local IPv4 address (IPv4-mapped IPv6 is mapped first; the cloud metadata address 169.254.169.254 is refused), an IPv6 unique-local or link-local address, or a `.local` name; loopback only when this CAR itself is on loopback. CGNAT ranges (100.64/10, which Tailscale uses) and `*.ts.net` names are out of scope for knocks. A CAR whose own URL is not on the local network is told so when it tries to knock, and does not advertise itself. A knock never lists nodes, delivers a message, reads memory, calls a tool or dispatches fleet work.
- **Limits.** One pending knock per key and 32 in total; a knock expires after 24 hours. A host event (`lattice.knock_received`) is raised only for a new pending knock, and never for a quieted key. Thirty-two fresh keys can fill every pending slot for a day; closing this CAR to knocks is the remedy, and blocking or quieting individual keys keeps real requests visible.
- **Known limits.** A CAR that relays a knock (refused by the knocker, see above) still leaves the real receiver a pending row from the knocker's key until it expires (24 hours) or is declined. If the receiving owner changes the share list between a first accept whose answer was lost and the retry, the knocker keeps the first list it received; the retry's list is only what the receiver displays until it next changes its share with `lattice.connect.share`.
- **Key change.** Connections are keyed on the peer key. A CAR that reappears with a different key is simply a new knock from an unknown key and needs a fresh accept; nothing links it to the existing connection, which keeps its key.
- **Org policy.** A knock connection counts as outside every organization: with several orgs configured, the most restrictive combination of their floors applies (as for invite-code connections), including `max_connection_secs`; it is never one org's connection, so an org that stops being served or an expiring attestation does not end it. The knocker's org policy is checked when it knocks and again when the accept arrives; the accepter's when it accepts; and `lattice.connect.share` applies `allow_human_share` and `max_share` to nodes added later on any connection (narrowing to a subset of the current share always passes, even after the org closed the project or connections outside it).
- **Who may knock.** The methods below are host-only; there is no MCP tool, so an agent cannot knock by itself.

#### `lattice.knock`
- **Params**: `{ peer: string, purpose: string, project: string, label: string, org?: string }` on the local network, or `{ member: string, org: string, device?: string, purpose: string, project: string, label?: string, share?: string[], ttl_secs?: integer }` through the Parslee relay (below).
- With `org`, the knock presents this CAR's Parslee device certificate for that one organization (refused if this CAR holds none), so a colleague's CAR in that org sees the certified account instead of "unverified"; without it, no certificate is sent — a certificate names its org, and a knock goes to whoever answers on the network. `peer` is a discovered CAR, by advertised name or URL (see `lattice.knocks`); `purpose` (one line, at most 280 bytes, no control or Unicode format characters such as bidi overrides, refused if it looks like a credential) and `project` are shown to its owner; `label` is this side's name for that CAR once connected (same rules as `lattice.connect.invite`). The purpose and project travel unsealed to whoever answers at that address. Refused when the answer does not prove its key, names another URL than the one dialled, is this CAR or one of this owner's devices, or has a live connection; or when this owner's org policy refuses connections outside the org or this project.
- **Returns**: `{ knock: { id, label, purpose, project, url, identity, peer_fingerprint, sent_ms, expires_ms }, peer_fingerprint, our_fingerprint, identity: "unverified", next }`.
- **With `member`: through the Parslee relay.** Offers a connection to a colleague in `org` whose CAR this one cannot reach — both behind NAT, no peer URL needed on either side. `member` is the colleague's account as `lattice.directory` lists it for that org; `device` picks one of their CARs by name, and `fingerprint` (as `lattice.directory` lists it) picks exactly one: device names are not unique, so a client that let its owner choose a CAR sends its fingerprint. Without either, or when several match, the device with the newest certificate is chosen (one device, never all of them); a `fingerprint` that matches none of the member's listed devices is refused. The recipient comes from the org's Parslee relay directory, its certificate verified against this CAR's pinned roots; the offer is the org offer (`latticeOrgInvite`) carrying `{ id, org, purpose, project, x, expires_ms }` — `label` is this owner's own name for the connection and is never sent. The connection is recorded as `invited` with `peer_url: null`, `relay_org`, and `transport: "parslee_relay"`, and `verified_by: "cert:<org>:<member>"`; it is held to that org's policy floor (the built-in certificate-only floor — people may be shared, at most 8 nodes — when this CAR serves no org scope). Their CAR records it as `offered`; they accept with `lattice.connect.accept {id, share?, label?}`, and both sides are active once the acceptance and its answer have crossed the relay. Refused for this CAR's own account or key, for a member with no certified device in the org's directory, when a connection with that CAR already exists, when they already offered one to this CAR (accept theirs instead), when the directory refresh it needed was held back by the relay's directory limit (`not sent: … [rate_limited]`; a stale cache cannot show the member is absent), or when this CAR holds no certificate for `org` that binds a sealing key. `ttl_secs` (1–86400, default 86400 — a day, as long as the relay keeps it) bounds how long the offer waits.
  - **Returns**: `{ connection, to: { account, device, org, peer_fingerprint }, identity, relayed: true, transport: "parslee_relay", delivered, relay_error, next }`. `delivered` is whether the relay took the offer now; when it did not (for example `relay_error` says the colleague is "not reachable through Parslee (not in this org, signed out, or certificate lapsed)"), the offer stays and is retried with backoff until it expires. A relay refusal never ends a connection.
- **Parslee relay connections.** Every handshake step, listing and disconnect notice on a relay connection is owed on the persisted connection (`relay_pending` in its view: `{ method, attempts, next_at_ms, last_error }`) and re-sent by the daemon's relay pump: the offer every 10 minutes until it is answered or expires, the acceptance every 10 minutes until it is answered (so a lost answer is answered again), an answer, listing or disconnect notice until the relay takes it. Each re-send is a new relay item; the receiver deduplicates by the offer or connection id. An offer that is not accepted by its expiry ends, as does an acceptance unanswered past the expiry plus the relay's 24 hours, and the certificate pin that admitting the offer created is removed with it. Offers crossing in flight keep the one with the lower (inviter key, offer id) on both sides. A refused offer — or an acceptance of an offer that no longer stands — is answered once with `latticeRefused`, which ends the other side's pending row; so is an offer whose certificate verified but was not admitted here (for example a different key for a device this CAR already pinned). Received mail is acted on only from a colleague whose Parslee certificate for the org verifies (judged when the relay took it, against a fresh revocation list held now), only if signed within the last 24 hours and at most a minute ahead, and — except for the first offer — only from a key with a live offer or connection here (an acceptance must name one of that key's offers, open or ended within the offer and relay TTLs); anything else is dropped before admission. When this CAR cannot judge an item itself (its revocation list went stale, its pins file is unreadable, a connection record could not be saved), the item stays queued for a later pass. Traffic that overtakes the answer activating its connection waits only on the side that accepted and expects that answer, at most 32 items per sender; on an offer this side has not accepted (or one it made) it is refused. Everything else pulled is acknowledged, and a `lattice.relay.probe` probe is kept only for ten minutes after a probe `pull`. Offers from a key or certified account on this owner's knock block list (`lattice.knock.block`) are dropped unanswered before the certificate is admitted (no pin, no certificate event), and blocking withdraws an offer from that key or account still waiting here; quieted ones are recorded without a host event.
- **How long a relay connection holds.** A certificate-verified connection is judged from the newest certificate seen for its peer (it ends a day after that one expires). Over the relay that evidence comes from every relay mail (each carries the sender's chain), from `latticeCertRefresh`, which each CAR sends once on every relay connection when its own certificate renews, and, for a quiet connection, from the org's relay directory, which the certificate refresher reads at most every 30 minutes per org with an active relay connection (certificate-authenticated, no credential). After a restart a CAR reads no Parslee credential until the Lattice is opened, so it is reachable over the relay only until its own certificate expires — at most 12 hours; opening the Lattice (or `car auth status --refresh`) renews it. Messages, listings, share lists and disconnect reasons are sealed with the connection key inside the relay's own sealed envelope; a relay connection uses the relay only — never a direct call or the org stream. `agents.message` / `peer_message` to a node on it return `outcome: "relayed"`, `transport: "parslee_relay"`. Listings cross only with the handshake's answer, on activation, and when a share list changes (`lattice.connect.share`), never periodically. The pump pulls every ~25 s, every 2 s for two minutes after a send or an arrival, backs off on 429 and 503, and pulls an org only while this CAR holds a sealing-capable certificate and a fresh revocation list for it; it never reads a credential. Its state is `peers.cert_status` `relay.pump`.

#### `lattice.knocks`
- **Params**: `{}`.
- **Returns**: `{ accepting, discovered: [{ name, url, identity: "unverified", relation, status, connection_label }], incoming: [{ id, identity, certified, replaces_pin, cert_conflict, fingerprint, key, purpose, project, claimed_url, received_ms, expires_ms, quiet }], outgoing: [knock], blocked: [{ key, fingerprint }], quiet: [{ key, fingerprint }] }`. An incoming knock's `identity` is `"unverified"`, or `"cert:<org>:<account>"` when the knocker presented a Parslee certificate this CAR admitted for an org it holds; `certified` is then `{ org, account, device, expires_ms }` — the certificate's account, never a name the knocker chose. `replaces_pin` is `{ issuer, org, account, device }` when Parslee certifies this key for a device already pinned to another key: accepting the knock is consent to that rotation. `cert_conflict` is set when an org admin attested the knocking key to one account while Parslee certifies it as another: it names both accounts and the `peers.cert_conflict_clear` call that resolves it (the key earns no org standing until then). `relation` is `other` or `claims_this_car`; `status` is `none`, `knocked` (this side asked), or `connected` — only addresses this CAR dialled itself count, never one a knocker claims. Expired knocks are dropped first.

#### `lattice.knock.accept`
- **Params**: `{ id: string, label?: string, share?: string[] }`.
- Accepts an incoming knock with this owner's label (default derived from the fingerprint) and share list (the knocker offers none; each side changes its own later with `lattice.connect.share`). `car/latticeKnockAccept` carries this side's X25519 half and sealed share list in the signed body, and returns the knocker's sealed share list; the connection is active on both sides when this returns. This side's X25519 secret is recorded on the knock at the first attempt, so a retry after a lost answer completes the connection. If the knock was declined or blocked meanwhile, nothing is connected and the knocking CAR is told. If the knocking CAR cannot be reached or does not answer in time, the knock stays and the call can be retried; if it answers with a refusal (its knock lapsed or was withdrawn, or its policy refuses), the error says the knock cannot complete.
- A knock that arrived with a certified standing still in force (not revoked or expired, org still held) is accepted as `verified_by: "cert:<org>:<account>"` and held to that org's policy; otherwise it is `tofu` under the most restrictive policy of this CAR's orgs. Accepting a knock from a key Parslee certifies for a device already pinned to another key is the owner's consent to that rotation: the pin moves to the new key.
- **Returns**: `{ connection, identity, our_fingerprint, replaces_pin }` — `identity` is `"unverified"` or the `cert:<org>:<account>` tag; `replaces_pin` is `{ issuer, org, account, device }` when accepting moved a pin to this key, else `null`. Accepting any Lattice operation (this, `lattice.knock`, and the `lattice.connect.*` invite, accept, confirm and share) also allows the daemon to read Parslee credentials for device-certificate renewal.

#### `lattice.knock.decline`
- **Params**: `{ id: string, block?: boolean }`.
- Drops the knock and tells the knocking CAR (best effort; it raises `lattice.knock_declined` there, or ends that CAR's side if it had already gone active from an accept this side never completed). The key may not knock again for 24 hours, or until allowed with `block: true`.
- **Returns**: `{ declined, blocked, other_car_notified }`.

#### `lattice.knock.withdraw`
- **Params**: `{ id: string }`.
- Withdraws a knock this side sent: the row and its sealing secret are deleted and the other CAR is told (best effort; its pending row goes). A knock stuck without an answer can be withdrawn too.
- **Returns**: `{ withdrawn, other_car_notified }`.

#### `lattice.knock.settings`
- **Params**: `{ accepting?: boolean }`.
- Reads, or sets, whether this CAR is discoverable on the local network and takes new knocks. On by default. Off withdraws the mDNS advertisement and refuses new knocks before a nonce is spent; knocks already waiting stay until answered or expired, and answers to knocks this CAR sent still arrive. The setting persists in `knocks.json`.
- **Returns**: `{ accepting, advertising }`.

#### `lattice.knock.block`
- **Params**: `{ mode: string, id?: string, key?: string, account?: string, org?: string }`.
- `mode` is `block` (refused at the door; its pending knock is dropped), `quiet` (knocks recorded, no host event), or `allow` (lifts both and any decline cooldown). The key is named by `key` or by a pending knock's `id`. For offers through the Parslee relay, `account` with `org` names a certified colleague instead, whichever device they use (their offers are dropped unanswered, or recorded quietly).
- **Returns**: `{ mode, key: { key, fingerprint }, withdrawn }`, or `{ mode, key: { identity: "cert:<org>:<account>" }, withdrawn }` for an account. `withdrawn` lists the ids of relay offers from that key or account that `block` ended. `account` may not contain `:`.

**Org-attested connections.** Colleagues in one organization connect without exchanging fingerprints, and still consent to every connection. Design: `docs/proposals/org-attested-lattice-connections.md`. Requires org-scope sync (`PARSLEE_SYNC_ORG_SCOPE=<orgId>:<granter_hex>[,...]`, one entry per org separated by `;`), which is itself gated on the org-key cryptographer audit; with it off, every method below except `lattice.org.status` and the standing-rule methods refuses, and nothing about other connections changes.

- **Several orgs.** Every configured org must be one the signed-in login belongs to (its token's `memberships` claim, or its active organization when the token has no such claim); naming an org twice is an error. Each org has its own delivery subsystem (journal `sync/org-<org>`), its own key provider holding only that org's `K_org`, its own view, standing rules, and processed-mail record. Orgs open lazily and one at a time after the personal subsystem: on the first `sync.knowledge` or `sync.pump`, a write for that org, or the Lattice refresher's next tick (every 15 s). Until then that org's `lattice.org.status` entry says "not opened yet" and a colleague's `car/latticeOrgInvite` for it is refused. A write for an org whose open is in flight waits for it (up to 30 s). One org failing to open — including an unreachable org-key directory — leaves the others and personal sync working; its writes are refused, and the open is retried on `sync.pump` and by the Lattice refresher. An org not granted `K_org` yet opens but cannot encrypt or decrypt its ops. With exactly one org configured, a failed open now degrades to personal-only sync with `org_error` on `sync.pump`, where before the whole sync open failed. Granter seeds are per org: `PARSLEE_ORG_GRANTER_SEEDS=<orgId>:<seed_hex>[;...]`; the legacy `PARSLEE_ORG_GRANTER_SEED` applies to every configured org whose granter set holds its key. The methods below take an optional `org`, required for an admin or rule change when several orgs are configured. Every trust decision names its org: a peer's `org` on `car/latticeOrgInvite` / `car/latticeOrgAccept` is checked against that org's attestations only, with no fallback to another org; mail read from an org's stream is acted on only for a sender that org attests; and a connection is ended only by its own org's revocation or expiry, never re-homed. One connection per peer key across all orgs. An older peer that sends no `org` on an offer is refused when more than one org attests it; on an accept, the org of the offer it names is used, and must attest it. A connection is held to its own org's policy; in a pass where its org is configured but has no folded view it is held to the most restrictive floor, an expired attestation ends it either way, and a connection whose org is no longer configured ends (`ended.by: "org"`, "no longer served"). An org whose stream has not been folded yet counts as refusing invite-code connections: they are refused between the sync open and each org's first fold, and for as long as any configured org stays unfolded (for example, one that cannot open) — fail-closed. Removing the LAST configured org does not end its connections: with no org configured the refresher stops before enforcement, so they stay until an org is configured again or they are disconnected. The legacy `lattice/org_rules.json` and `org_mail_seen.json` belong to the single configured org, or, with several, to the one org whose sync journal existed before the org set was configured (the org a single-org daemon served) — never to whichever org happens to be active. The owner is recorded in `lattice/org_legacy_owner` and kept. With zero or several such orgs the legacy rules are unowned: they accept nothing, `lattice.org.status` lists them as `unowned_legacy_rules`, and `lattice.org.rule.remove {id}` removes one (`unowned_legacy: true`) once it is re-added for an org. The decision — an org, or unowned (`!unowned` in the marker) — is made once, the first time an org set is known, and kept across restarts and config changes. If it cannot be written down, `lattice.org.status` says so in `legacy_owner_unrecorded` and, for this run, the files are treated as unowned (fail closed). Rules and mail-seen records the owning org had under `lattice/org/<org>/` are merged into the legacy files when it becomes the owner. To decide again (for example, after cleaning up the config), stop the daemon and delete `lattice/org_legacy_owner`. A standing-rule write opens sync first only when `PARSLEE_SYNC_ORG_SCOPE` is set, so the org set is known before the rule is filed (if sync cannot open, the write is refused); without org scope it does not, and rules work as before. Other orgs' files are under `lattice/org/<org>/`.  The same daemon key appears in the endpoint record of every org it is in, which links those identities for anyone who reads more than one org stream.

- **Identity is attested, once per device.** Each daemon announces its CAR (account, device, peer URL, peer key; signed by that key) on the org-scoped sync stream. An org admin — an operator whose login-derived signing key is one of the granter keys in `PARSLEE_SYNC_ORG_SCOPE` — attests an announced CAR with `lattice.org.attest`, after checking its fingerprint with the member. The attestation is a record signed by that granter key; any member can write to the org stream, so a record that is not signed by a trusted granter is ignored, and one member cannot claim to be another. Attestations expire (1–366 days, default 90).
- **Consent is per connection.** An attested colleague's key may call only `car/latticeOrgInvite` and `car/latticeOrgAccept` (and the ordinary invite-code handshake) until a connection exists. Accepting takes this owner's own share list, or a standing rule this owner wrote (`lattice.org.rule.add`). Nothing an admin publishes creates, accepts, or widens a connection.
- **Exit.** An org-verified connection ends (`ended.by: "org"`) when the attestation it was verified with expires, or when a revocation issued at or after that attestation arrives — decided from evidence kept on the connection, so a daemon that has not fetched the org stream yet does not end anything. A revocation reaches each colleague at their next refresh (15 s cadence; the org stream is reconciled at most once a minute unless this daemon just published).
- **Policy floor.** A granter publishes `lattice.org.policy`; it can only narrow: refuse invite-code connections (`allow_outside_org: false`), refuse sharing `human:` nodes, cap the share list, allow-list projects, and end connections after `max_connection_secs`.
- **Org relay.** When a colleague's CAR cannot be reached directly (no route to its announced peer URL), the org handshake, peer messages, disconnect notices, and listings travel as signed **mail** on the org sync stream instead, and each daemon's Lattice refresher processes mail addressed to it with the same handlers the direct path uses — a relayed message is admitted by the receiving broker exactly as a direct one (shares, sealing, standing, audit). Mail is signed by the sender's CAR key and acted on only from an attested colleague's key; bodies, listings, share lists, and disconnect reasons are sealed with the connection key, so other members see only who mailed whom and when. An org **offer** is not sealed (no connection key exists yet): its purpose and project are visible to org members. Mail is processed once (`<state root>/lattice/org_mail_seen.json`) and ignored after a day. A relayed result says so: `lattice.connect.invite` and `lattice.connect.accept` return `relayed: true` (an accept then waits in `awaiting_their_confirm` until the inviter's answer arrives the same way), `agents.message` / `peer_message` return `outcome: "relayed"`, and a disconnect counts the other CAR as told once the notice is mailed. Relayed traffic moves at the refresher's org-stream cadence (at most once a minute when idle, at once after this daemon mails), and mail is not deleted from the org stream.
- **Not covered.** Attestation is only as good as the admin's fingerprint check and the org stream's integrity, which rests on the org key. The pubkey-table-poisoning path to that key is closed on the granter's side by confirmed-key pins (`org_key_pins` below, and the `org_granter` tool's `ORG_GRANTER_PINS`); backend publish authorization is still needed to stop a member's key being overwritten at all.

#### `lattice.directory`
- **Params**: `{ org?: string, refresh?: boolean }`.
- Colleagues (this account excluded) and their CARs, from two sources merged per account: colleagues an org granter attested on the org stream (with org-scope sync), and colleagues whose devices Parslee certifies for an org this CAR holds a certificate for, from that org's Parslee relay directory — the second needs no org-scope sync. Relay directory certificates are verified against this CAR's pinned roots and a revocation list every time they are read; the directory is cached in a plain file and fetched from the relay (authenticated by this CAR's certificate, no bearer) only when `refresh` is true or nothing is cached — never on a timer. With `refresh`, when a certificate it would read (without `org`, any held org's) is missing, expired, or not bound to this device's sealing key, one certificate pass runs first. The relay takes 6 directory requests a minute from one CAR's key, and that key is the same for every org, so the daemon keeps one budget across all orgs (the background pin renewal reads directories through it too) and sends no request past it, nor any inside the `Retry-After` of a relay 429 (held at most 10 minutes). A refresh held back serves the cache, with `relay.refresh_error` saying why and when to retry; with nothing cached the org's `relay` is `{ error, dormant: true }`. Either message starts `not sent:` and ends `[rate_limited]`. With several orgs, relay directories are read stalest first, so the ones held back on one refresh go first on the next. Nodes are not listed: those are visible only through a connection's share list.
- **Returns**: `{ org, count, members: [{ account, display_name, email, devices: [...] }], org_stream, relay }`. `display_name` is the org stream's name for an attested member; for a colleague known only from the relay it is the name Parslee sent beside the certificate (an unsigned display hint), or the account id when none was sent. `email` is Parslee's email for a relay colleague, else `null`. An attested device is `{ device, reachable, fingerprint, attested_until_ms, connection: { id, label, state } | null, source: "attestation", relay: false }`; `reachable` is whether the CAR announced a peer URL, and `device` is `null` when it has not. A certified device is `{ device, source: "certificate", identity: "cert:<org>:<account>", fingerprint, relay: true, reachable_direct: false, cert_expires_ms, connection, display_name, email }` (the last two as the relay sent them, or `null`). `org_stream` says whether the org stream contributed; `relay` is `{ fetched_at_ms, dormant: false, refresh_error? }` (`refresh_error` only when `refresh` was asked for and held back by the relay's limit, so `fetched_at_ms` is the cache's age), `{ error, dormant: true }` when this CAR cannot use the relay for the org (for example no certificate), or `null` when it holds no certificate for the org. With several orgs and no `org`: `{ count, members, orgs }`, where `orgs` holds each org's listing in that shape, each row of `members` also names its `org` (a colleague in two orgs appears once per org), and `count` counts distinct accounts.

#### `lattice.relay.probe`
- **Params**: `{ action: "send" | "pull", org: string, to_key?: string, text?: string }`. `to_key` (the recipient device's Ed25519 key, 43 characters) and `text` (at most 4096 bytes) are required for `send`.
- Host-only. A developer check of the Parslee relay (`docs/car-relay-protocol.md`) before any Lattice handshake rides on it. It authenticates to the relay with this CAR's device certificate for `org` alone — no bearer — and reads no credential; with no valid certificate for `org` that binds a sealing key it fails and names `peers.cert_status {refresh: true}` (`car auth status --refresh`) as the fix. `send` reads the org's relay directory, verifies the recipient's certificate against this CAR's pinned roots, seals the text to that certificate's `cnf.x25519` as relay mail (method `relayProbe`), and deposits it. `pull` runs one pull pass, opens every item addressed to this device, verifies each probe's inner signature and sender certificate (a fresh revocation list is required, and the certificate must be for `org`), shows it, and acknowledges it; other relay mail stays queued. The outcome is recorded in `peers.cert_status` `relay`.
- **Returns**: `send`: `{ action, org, id, expires_at_ms, to: { account, device, peer_fingerprint } }`, where `id` is the relay item id (`rk_…`). `pull`: `{ action, org, probes: [{ id, verified, text, at_ms, from: { account, device, peer_fingerprint } }], acked, ack_error, left_queued }`; a probe whose sender did not verify has `verified: false` and an `error` in place of `text`, and `from` carries only `peer_fingerprint`. The sender's certificate is verified at pull time, not at the probe's `at_ms`. `ack_error` is null, or the relay error when the acknowledgement failed: the opened probes are still returned, `acked` is 0, and they come back on the next pull. With no fresh revocation list, `pull` does not pull at all (`relay.dormant_reason: revocation_stale`) and `send` sends nothing; a list that goes stale during a pass leaves the affected probes queued rather than refusing them. A relay refusal is an error whose message ends in its code in brackets: `[feature_off]`, `[not_same_org]` (the recipient is not reachable through Parslee: not in this org, signed out, or certificate lapsed), `[recipient_full]`, `[rate_limited]`, `[payload_too_large]`, `[unauthorized]`, `[invalid_request]`, `[relay_unavailable]`, `[http]` or `[local]`.

#### `lattice.org.status`
- **Params**: `{ org?: string }`.
- Whether org connections are on, and this CAR's place in each org. With `org`, that org's fields. Otherwise `orgs` lists every configured org (a configured org that is not open appears as `{ enabled: false, org, reason }`); with exactly one configured its fields are also at the top level, as before, and with several `enabled` says whether any org is open. Every shape — several orgs, one org, or one org named with `org` — also carries `unowned_legacy_rules` (present only when non-empty: standing rules from before several orgs that no org can be shown to own) and `legacy_owner_unrecorded` (present only when that decision could not be written down).
- **Returns**: `{ enabled: false, reason }` when org scope is off; otherwise `{ enabled: true, org, account, granter, our_fingerprint, org_key_fingerprint, org_key_pins, attested, attested_until_ms, members, policy, rejected_records, pending, rules }`. `our_fingerprint` is what to tell the admin attesting this CAR. `org_key_fingerprint` identifies this member's X25519 org-key pubkey, which a granter confirms before wrapping `K_org` for it. `enrollment` is `{ code, fingerprint }`: the org enrollment code a new member installs with `car lattice org join <code> --fingerprint <fingerprint>` (it writes `PARSLEE_SYNC_ORG_SCOPE` to `$CAR_HOME/env` after checking the fingerprint, which an admin reads to the member another way than the code), or `null`. `org_key_pins` (granters only, else empty) maps each attested member's account to the org-key pubkey their signed announcement carries — confirmed by the fingerprint check made when attesting, and in the shape the `org_granter` tool's `ORG_GRANTER_PINS` file takes. `pending` (granters only) lists announced CARs with no attestation as `{ endpoint, account, device, announced_at_ms }` — without a fingerprint, which the admin must hear from the member. `rejected_records` counts org records that failed verification.

#### `lattice.org.attest`
- **Params**: `{ endpoint: string, fingerprint: string, display_name?: string, expires_days?: integer, org?: string }`. Without `org` on a several-org CAR, the one org the endpoint was announced in.
- Granters only — an operator whose login-derived signing key is one of the configured granter keys, or who set `PARSLEE_ORG_GRANTER_SEED` to the seed of one (64 hex digits, as the `org_granter` tool mints; a seed that is not a configured granter makes org scope fail to open). Attests that the CAR announced as `endpoint` (from `lattice.org.status` `pending`) belongs to the account that announced it. `fingerprint` is required and must be the one the member told the admin another way; a mismatch is refused without revealing the actual fingerprint. `expires_days` is 1–366, default 90.
- **Returns**: `{ attested: true, org, record_id, issued_ms }`.

#### `lattice.org.revoke`
- **Params**: `{ account: string, org?: string }`.
- Granters only. Voids every attestation of `account` in that org issued at or before now. Each colleague's connections with that account verified by that org end at their next refresh; another org's attestation of the same CAR is untouched. A later attestation re-admits the member.
- **Returns**: `{ revoked: true, org, record_id, issued_ms }`.

#### `lattice.org.policy`
- **Params**: `{ allow_outside_org?: boolean, allow_human_share?: boolean, max_share?: integer, projects?: string[], max_connection_secs?: integer, org?: string }`.
- Granters only. Publishes the org's Lattice policy, replacing the previous one whole; an omitted field takes its default (`true`, `true`, no cap, any project, no limit). The newest policy wins.
- **Returns**: `{ policy, org, record_id, issued_ms }`.

#### `lattice.org.rules`
- **Params**: `{ org?: string }`.
- **Returns**: `{ count, rules: [{ id, project, share, from, created_at_ms }] }` — this operator's standing auto-accept rules for the org. With several orgs and no `org`, every org's, each rule also naming its `org`. A rule accepts offers only from colleagues its own org attests.

#### `lattice.org.rule.add`
- **Params**: `{ project: string, share?: string[], from?: string[], org?: string }`. `org` is required when several orgs are configured.
- Accepts, in advance, offers from attested colleagues for `project` with this fixed share list — `from` limits it to those accounts. The operator's own choice: no admin action can create one. The org policy still applies when the rule accepts. At most 32 rules.
- **Returns**: `{ rule, org? }`.

#### `lattice.org.rule.remove`
- **Params**: `{ id: string, org?: string }`. Without `org`, the rule is found in any configured org.
- Withdraws a rule. Connections it already accepted stay.
- **Returns**: `{ removed: true }`.

**Parslee device certificates** (design: `docs/proposals/parslee-device-certificates.md`). For each held login and each org it holds, the daemon keeps a Parslee-issued certificate binding this CAR's peer key to `(account, device, org)`, refreshed every 6 h, stored as plain files under `<state root>/peer-certs/` (certificates are public). It reads credentials for that only after a sign-in change, an explicit `peers.cert_status { refresh: true }` (CarHost sends one when its Lattice screen appears; launch and reconnect never do), or a requested Lattice operation; boot reads none, and even then only for an issuance or renewal that is due. An issuer's revocation lists must never reset `seq`: after losing its counter, or rotating its signing key, it continues from the highest `seq` it ever published + 1 — a CAR never accepts a list that does not move past the newest one it holds, even when that list's signer is no longer delegated. A list refused only because its `seq` advanced faster than time allows still has its revoked keys applied at once; the issuer is then reported `degraded` until a list the CAR can accept arrives. `GET <authority>/.well-known/car-trust.json` answering 404 means the feature is off there. A peer presents its certificate and the delegation that signed it as the request header `x-car-peer-cert: <certificate>~<delegation>`, next to the signed `x-car-peer-*` headers; it is bound to the request by a separate header, `x-car-peer-cert-sig` (the same key's signature over the request's signed string plus the chain's hash), so it cannot be swapped on path, while the ordinary signature is unchanged and CARs that predate certificates still accept the request. A certificate that verifies against the roots pinned in this build, with a revocation list no older than an hour, for an org one of this CAR's logins also holds, earns that key **org contact** standing only — the two org handshake methods and the connection handshake, never a Lattice method, never device trust. It is refused outright when it names one of this CAR's own accounts, or when an org admin attested the same key to a different account in the same org (event `lattice.cert_attestation_conflict` with `{ org, account, peer_fingerprint }`); a refusal also withdraws any standing the key had. Such a conflict is sticky: the key earns no org standing from any source — certificate or attestation — until the owner clears it with `peers.cert_conflict_clear`. A later attestation is checked against the keys already admitted, so the key need not present its certificate again to be caught. One key may carry certificates under several accounts (a CAR is certified under every login it holds), so that alone is not a conflict. The first certified key for `(org, account, device)` is pinned (`<state root>/lattice/cert_pins.json`); a different key for a pinned device gets no certificate standing — it is an unverified first contact that needs consent — and is announced as `lattice.cert_key_rotation`. A connection verified by a certificate has `verified_by: "cert:<org>:<account>"`, is held to that org's Lattice policy, may use only that org's relay, and ends on a revocation (by key, credential or issuer key), when this CAR no longer holds the org, when the org's granters revoke the member, when the build no longer pins a usable root, or 24 h after the newest certificate seen from the peer expired. Relay mail from a certificate-verified colleague is accepted only on an active connection. While the org's policy is not folded, the most restrictive policy of the orgs this CAR serves applies; with no org scope configured at all, a built-in floor applies instead (people may be shared, at most 8 shared nodes, no new connections outside the org). The certificate reaches a peer on the agent card (`car_device_cert`) only when that peer's own signed card request presented a certificate for an org this CAR holds, and then only for that org. Builds ship with no pinned roots until Parslee's are provisioned; until then nothing verifies and none of this applies.

#### `peers.cert_status`
- **Params**: `{ refresh?: boolean }`. `refresh: true` is an explicit request: it allows credential reads and runs one issue/refresh pass now.
- Host-only. This CAR's device certificates and what it trusts on them.
- **Returns**: `{ enabled, usable, armed, device_id, key_revoked, peer_fingerprint, trust, revocation, certificates, contacts, pins, pins_error, conflicted, conflicts, directory, relay }`. `usable` is false when no pinned root is still within its `not_after`. `enabled` is false when this build pins no roots. `key_revoked` is true once Parslee answered `device_revoked`: this CAR's key can never be certified again under any account, issuance stops for good, and the fix is to re-key this device: stop CAR, move `peer-identity.key` (in the CAR state root) aside, and start CAR — a new peer key also gets a new device id, because CAR binds its device id to its peer key. `trust` lists each authority's `car-trust.json` fetch as `{ api_base, state: "on" | "off" | "error" | "degraded", fetched_at_ms, error }` (`degraded`: every list fetched for over 10 minutes was older than the one held). `revocation` lists each issuer as `{ issuer, seq, issued_at_ms, expires_at_ms, fresh, degraded, seq_jump_since_ms, floor, delegations: [{ kid, root_kid, expires_at_ms }] }` (`seq_jump_since_ms`: since when a list was refused for advancing `seq` faster than time allows; its revoked keys and credentials were applied, its freshness was not, and admission continues until the held list goes stale. `floor`: `{ seq, issued_at_ms, source: "unverified_stored_token", file }` when the ordering floor comes from a stored list this CAR can no longer verify because its signer is no longer delegated — trusted local state; deleting `file` drops the floor and the revocations stored beside it). `certificates` has one row per held (login, org): `{ account_id, email, api_base, org, state: "valid" | "refresh_due" | "missing" | "feature_off" | "device_revoked" | "device_identity_changed", credential_id, expires_at_ms, refresh_after_ms, error, attempted_at_ms, failures }` (`failures`: consecutive failed issuance attempts; the next waits 10 minutes, doubling per failure up to 6 hours). `contacts` lists keys admitted on a certificate as `{ peer_fingerprint, org, account, device, expires_at_ms, verified_by }`. `pins` lists `{ org, account, device, peer_fingerprint, first_seen_ms, last_cert_expires_ms, rotation }`, `rotation` being `{ peer_fingerprint, at_ms }` when a different key was presented for that device. `pins_error` is set when the pins file is unreadable: certificate admission is off until it is repaired (a `.bak` copy is kept; the file is never overwritten). `conflicted` lists the keys in an unresolved conflict. `conflicts` lists recent notes as `{ kind, org, account, peer_fingerprint, detail, at_ms }` (`kind` is `attestation_conflict`, `key_rotation` or `new_device`), each also raised as host event `lattice.cert_<kind>`. `directory` maps each held org to its last peer-directory read, `{ certified, fetched_at_ms }` or `{ error, fetched_at_ms }`: directory devices are listed only when their certificate verifies and matches the entry. `refresh_due` also covers a valid certificate that binds no sealing key (`cnf.x25519`) and was issued by a build before the Parslee relay: it is renewed at the next armed pass that is not backing off, with this device's derived X25519 key bound (a first bind, which Parslee allows). A certificate THIS build was issued without a sealing key (the issuer bound none) stays `valid` and is kept for the LAN peer surface; it is not renewed early for the missing key, and `relay.dormant_reason` says `no_sealing_key`. `device_identity_changed` means Parslee refused issuance because it holds a different sealing key for this device id (409 `device_identity_changed`: Parslee keeps the key write-once per device id, refusing both a different key and none after one was bound — see `docs/car-relay-protocol.md` §7). This build cannot cause it on its own: the sealing key is derived from the peer key and the device id is bound to the peer key, so a re-keyed CAR presents a new device id. It is terminal for that (device id, sealing key) — issuance stops and no credential is read for it — and the fix is to re-key this device: stop CAR, move `peer-identity.key` (in the CAR state root) aside, and start CAR — a new peer key also gets a new device id, because CAR binds its device id to its peer key. (An OLDER build that sends no sealing key after this one bound it gets the same 409; that is the older build's failure.) `relay` is `{ enabled_by_server: boolean | null, dormant_reason: string | null, last_pull_ms: number | null }`: `enabled_by_server` is null until a relay call completes, false after the relay answered 404 (off on that authority), true after any other relay answer; `dormant_reason` is null when this CAR could use the relay now, else one of `no_usable_root`, `feature_off`, `no_certificate`, `no_sealing_key` (its certificates predate the sealing key) or `revocation_stale` (no fresh revocation list to verify a sender against); `last_pull_ms` is the last completed pull pass (`lattice.relay.probe` or the Lattice relay pump). `relay.pump` is the Lattice relay pump's state: `{ orgs: { <org>: { not_before_ms, failures, last_pull_ms, last_error, dormant_reason } }, burst, seen }`, where an org's `dormant_reason` says why it is not pulled (for example `revocation_stale`, or this CAR holding no sealing-capable certificate for it).

#### `peers.cert_conflict_clear`
- **Params**: `{ peer_fingerprint: string }` — the 128-bit verification fingerprint `peers.cert_status` shows for the key.
- Host-only. The owner resolved an attestation/certificate conflict: the key may earn org standing again, each source applying its own checks (a disagreement that still stands is caught again).
- **Returns**: `{ cleared: boolean }`.
