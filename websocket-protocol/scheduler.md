### scheduler

#### `schedule.suggest`
- **Params**: `{ phrase: string, timezone?: string }`
- **Returns**: `{ cadence: { trigger: "interval"|"cron"|"manual", schedule: string, timezone: string|null, timezone_mode: "mac"|"fixed", phrase: string } | null, reason?: string, summary?: string }`
- Deterministic and inference-free. The supported grammar is `every N minutes` / `every N hours` (also `min`, `mins`, `hr`, `hrs`), `every minute`, `every hour`, `hourly`, `every half hour`, `daily at <time>` / `every day at <time>`, `weekdays at <time>` (also `every weekday`, `weekday mornings`), `weekends at <time>`, named days at a time (`weekly on Monday at <time>`, `every Monday, Wednesday and Friday at <time>`, `Tuesdays at <time>`), and `on request` / `only when I ask` / `when I ask` / `when asked` / `on demand` / `manually`. A time is `H:MM` on the 24-hour clock, or with `am`/`pm` (`8:30am`, `8 pm`), `noon` or `midnight`. Matching ignores case, repeated whitespace and a trailing full stop. Interval schedules use `Nm`/`Nh`; cron schedules use the ordinary five-field form (several named days become a list, `1,3,5`); manual schedules use an empty string.
- The Agent Builder's three shipped template phrases are also stable inputs: `Weekdays in the morning, plus when I ask` maps to weekday cron at 09:00, while `Whenever I assign a research question` and `When I ask for a reply or follow-up` map to `manual`.
- **Zones.** A phrase may end with a zone, an IANA name in any case (`America/New_York`) or one of `ET`/`EST`/`EDT`/`Eastern`, `CT`, `MT`, `PT` (each with its `S`/`D` forms and full name), `UTC`, `GMT`. A non-blank `timezone` param (an IANA name, trimmed) wins over a zone in the phrase. With either, the cadence has `timezone_mode: "fixed"` and that `timezone`, and an agent on it runs on that zone's wall clock wherever the Mac is; with neither, `timezone_mode: "mac"` and `timezone: null`, the Mac's own clock. A `timezone` param that is not an IANA zone is reported as `reason`. The zone is never embedded in the cron string. Unsupported or invalid phrases are not RPC errors: `cadence` is `null` and `reason` tells the caller which forms are accepted.
- `summary` reads the parsed cadence back in plain words for a host to confirm with the person, for example `every weekday at 8:30 AM, Mac time` or `every 15 minutes`.
- FFI: `suggestSchedule(phrase, timezone?)` (NAPI) and `suggest_schedule(phrase, timezone=None)` (PyO3) return the same JSON.

#### `scheduler.create`
- **Params**: `{ name: string, prompt: string, trigger?: "once"|"cron"|"interval"|"file_watch" = "manual", schedule?: string, system_prompt?: string }`
- **Returns**: task object (does NOT execute — just constructs the task definition)

#### `scheduler.run`
- **Params**: `{ task: object }`
- **Returns**: single execution result
- **Stateful dedup**: the daemon seeds the posted task with any prior execution
  history persisted for `task.id` (under `~/.car/tasks/`) before running, and
  saves the mutated task back afterward. This means the executor's deterministic
  occurrence guard survives across calls: re-posting the same Interval/Once/Cron
  task whose occurrence already ran returns the prior execution record instead of
  re-invoking the agent. `Manual` triggers carry no occurrence id and are
  intentionally never deduped (an explicit re-run is an intentional repeat).
- **Supervised agents**: a session bound to a supervised agent runs the task,
  but the task is not stored: no prior history is read and nothing is
  saved to `~/.car/tasks/`, so its occurrences are not deduped across calls.
  The store is shared (the daemon's command scheduler runs the enabled
  interval command tasks in it, and `scheduler.os_reconcile` reaps against
  it), and agents get no runtime scheduling (CAR in the Cloud outcomes D1,
  #3440). Host sessions, the daemon-token operator and the CLI are unchanged.

#### `scheduler.run_loop`
- **Params**: `{ task: object, max_iterations?: number }`
- **Returns**: array of execution results
- **Stateful dedup**: same prior-history seeding and write-back as
  `scheduler.run` — occurrences already serviced in an earlier call are skipped.
  From a supervised agent's session the task is not stored, as for
  `scheduler.run`.

#### Durable OS-level scheduling (`scheduler.os_*`)

`scheduler.run`/`run_loop` use in-process timers: if the daemon is down when a task is due, the run is missed. These methods delegate the *trigger* to the OS scheduler (`launchd` on macOS, `crontab` on Linux), which fires a command even with no CAR process running. Only `interval` and `cron` triggers are OS-schedulable (`once`/`manual`/`file_watch` are rejected). `program` + `args` are the command the OS runs to re-enter CAR and execute the task once (the caller owns this — e.g. a `car`/`car-server` invocation). Schedules are labeled `ai.parslee.car.task.<task_id>`.

- `scheduler.os_render` — **Params**: `{ task: object, program: string, args?: string[] }`. **Returns**: `{ label, launchd_plist, launchd_error, crontab_line, crontab_error, schtasks_xml, schtasks_error }` — a no-I/O preview of every backend (macOS launchd, Linux crontab, Windows Task Scheduler); each rendering is `null` when that backend can't express the schedule, with the reason in the matching `*_error`. (E.g. an interval that isn't a whole number of minutes can't map to cron; a `*/15` cron can't map to launchd's `StartCalendarInterval`; a multi-valued cron field can't map to a single `schtasks` trigger.)
- `scheduler.os_install` — **Params**: same as `os_render`. **Returns**: `{ label, backend: "launchd"|"cron"|"schtasks", detail, conflict_preserved? }`. Writes the plist to `~/Library/LaunchAgents` and `launchctl load`s it (macOS), appends a tagged crontab line (Linux), or registers a Windows Task Scheduler task via `schtasks /Create /XML` (Windows). Idempotent — replaces any prior schedule for the same task. On macOS the replacement is divergence-safe: the prior plist is claimed by rename (same inode) and the new plist published atomically; if some process wrote through a file descriptor it opened before the claim, those bytes are preserved at a sibling `<plist>.car-conflict-<utc>` file — never deleted or overwritten — and `conflict_preserved` carries that path (absent otherwise, and always absent for cron/schtasks). Also **persists the task to `~/.car/tasks/`** so the store stays the authoritative set of scheduled tasks (which `os_reconcile` reaps against); a persist failure aborts the install. Refused to a supervised agent on every platform, and the refusal is logged: agents get no runtime scheduling (CAR in the Cloud outcomes D1, #3440). An agent that should run on a schedule declares it as the `cadence` of its declarative agent (see `declagents.md`); it changes only with a new version of the agent, and only a person pauses or removes it. The error is `scheduler.os_install is not available to a supervised agent: agents get no runtime scheduling; an OS schedule runs any program as this user, so an agent's schedule is the cadence declared in its bundle (declagents), which only a person pauses or removes`. Role `operator_only`: host sessions, the daemon-token operator and the CLI are unchanged.
- `scheduler.os_uninstall` — **Params**: `{ label: string }` (full label or bare task id). **Returns**: `{ label, removed: boolean }`. Refused to a supervised agent on every platform, with the same reason as `scheduler.os_install` (`scheduler.os_uninstall is not available to a supervised agent: …`). Role `operator_only`: host sessions, the daemon-token operator and the CLI are unchanged.
- `scheduler.os_list` — **Params**: none. **Returns**: a JSON array of installed CAR schedule labels on this host. Refused to a supervised agent on every platform (`scheduler.os_list is not available to a supervised agent: …`): scheduled programs have no owner, so there are no "own rows" to give. Host sessions, the daemon-token operator and the CLI are unchanged.
- `scheduler.os_reconcile` — **Params**: none. **Returns**: `{ removed: string[], kept: number, errors: string[], reinstalled: string[] }`. Reaps orphaned schedules: uninstalls every CAR-managed label whose task is gone from `~/.car/tasks/` or whose trigger is no longer `interval`/`cron` (foreign launchd/cron entries are never touched). Then migrates: every installed `tasks.schedule` command task this state root owns whose OS job still runs the command directly (an install from before run recording) is reinstalled to fire through `car schedule run-recorded`, and listed in `reinstalled`, with `recording_since` set on the task so health checks measure from the move; agent schedules keep their own launcher, and a durable task with no OS job at all is reported as orphaned by `tasks.list` rather than reinstalled. A job that does not run the command its task record now names is not moved (an `errors` entry says so): the move writes the record's command into the job, and the record can be rewritten by calls with less authority than the one that installed it. A label whose task file exists but cannot be parsed is kept, not reaped. Best-effort per label — a failure is recorded in `errors` and the pass continues. Runs automatically at daemon boot; call this to reap on demand. Because `os_install` persists the task, a label with no backing task is normally a genuine orphan. If the task store can't be **read** (permission/IO error), it returns an error and reaps nothing rather than mistaking the failure for "no tasks"; a missing store dir is treated as legitimately empty.
- FFI: `renderOsSchedule`/`installOsSchedule`/`uninstallOsSchedule`/`listOsSchedules`/`reconcileOsSchedules` (NAPI) and the `snake_case` equivalents (PyO3).

#### `tasks.*` — daemon-native deterministic (command) scheduler (car-releases#72)

Schedule a **deterministic command** on a cadence expressed ONCE, with the OS backend hidden — the higher-level abstraction over the `scheduler.os_*` primitives for consumers who want "ask CAR to run my script on a cadence" rather than "deal with launchd/cron". The command runs a `program` + `args` (not an LLM prompt).

- `tasks.schedule` — **Params**: `{ name, program, args?: string[], cadence: { interval_secs?: number | cron?: string }, durable?: boolean, working_dir?, env?, timeout_secs?, stdout_path?: string, stderr_path?: string }` — the cadence is expressed once (exactly one of `interval_secs` / `cron`). camelCase spellings (`intervalSecs`, `workingDir`, `timeoutSecs`, `stdoutPath`, `stderrPath`) are accepted too. **Returns**: `{ id, durable, backend: "launchd"|"cron"|"schtasks"|"daemon", stdout_path, stderr_path, task }` (`schtasks` = Windows Task Scheduler).
  - **Run recording (car-releases#88).** A durable task's OS job does not run `program` directly: it launches `car schedule run-recorded <id> --digest <hex> --car-home <root>`. The `car` CLI is found as the current program, the one beside it, or on `PATH`, and is used only if its `schedule run-recorded --help` succeeds and names `--digest`; with none that does (the npm and PyPI packages ship no `car`, so from node or python an older `car` on `PATH` is passed over), the call fails and nothing is persisted. `--digest` is a SHA-256 over the task's whole `command` (program, args, env, working_dir, timeout_secs and the log paths) at install. At each firing the recorder compares it with the record's command and, if they differ or the job carries none, does not run anything: it records a `failed` execution saying the command changed after install. The record is read at every firing and can be rewritten by less trusted calls than `tasks.schedule` (`scheduler.run` saves the task its caller passes), so the digest is what keeps an installed job running the command it was installed with; changing a durable task's command means scheduling it again. The recorder writes a start stamp before the command starts (`last_run_at`, `status: "running"`, an in-flight execution with no `finished_at`), runs `program` with `working_dir`, `env` (on top of what the OS scheduler provides, with `CAR_HOME` set to the owning root) and `timeout_secs` (no limit when unset; the whole process tree is killed when it passes), then writes the exit stamp: `run_count + 1`, `status` `completed`/`failed`, and the execution's `exit_code`, `finished_at` and `error`. History keeps the newest 50 executions. Its process exits with the command's exit code.
  - **Output capture (car-releases#102).** stdout and stderr are appended to `stdout_path` / `stderr_path` (absolute paths; default `<CAR_HOME>/logs/tasks/<id>.log`, stderr sharing the stdout file). A missing file is created owner-only (0600). A log in `<CAR_HOME>/logs/tasks/` is CAR's: it is kept at 0600 and, once past 10 MiB, renamed to `<name>.1` (replacing the previous one) before the next run appends. A file the caller named elsewhere keeps its permissions and is never rotated. The recorder does the redirection, so launchd, cron and Task Scheduler behave the same; in the shared default file each run is bracketed by `--- car: … ---` lines. A daemon-timer task (`durable: false`) appends its output to the same files. The resolved paths are persisted on the task's `command` and returned here and by `tasks.list`. CAR picks the backend: `durable: true` (default) installs to the OS scheduler so it fires even when car-server is down — **`*/N` cron is normalized** (expanded to a launchd calendar array) so the same input works on macOS and Linux; `durable: false` uses the in-daemon timer (fires only while car-server runs, `backend: "daemon"`), which supports `interval_secs` only (a cron cadence requires the OS backend). The task is persisted to `~/.car/tasks/` first (authoritative for `os_reconcile`). Commands execute with the daemon OS user authority; no per-task permission tier is enforced. Host-management only. A supervised agent is refused on every platform: a bound agent is never the host, so it gets the host-role refusal, and behind that gate the method refuses a bound agent again with `tasks.schedule is not available to a supervised agent: agents get no runtime scheduling; …`, the same reason as `scheduler.os_install` (CAR in the Cloud outcomes D1, #3440). On a daemon with no host token installed nobody is the host, so every session gets the host-role refusal and its cause ("Host authority fails closed"). Host sessions are unchanged.
- `tasks.list` — **Params**: none. **Returns**: an array with **every** record in the task store: `{ id, name, kind: "command"|"agent"|"dream"|"prompt"|"unreadable", program, args, trigger, schedule, durable, backend: "os"|"daemon"|"orphaned"|"none", enabled, status, last_run_at, run_count, last_exit_code, stdout_path, stderr_path }`. A task file that cannot be parsed is listed rather than dropped, as `{ id, name: "", kind: "unreadable", backend: "os"|"none", status: "unreadable", file, error }` (`backend` is `os` while a job is still installed under its id). `backend` says what runs the record: `os` an installed OS job; `daemon` the daemon's interval timer (command tasks) or its dream loop (`car-dream`, stamped after every pass; in this build the loop's memory engine holds none of the user's memory, so each pass is stamped `failed` and marked detached rather than reading as a completed consolidation), which fire only while car-server runs; `orphaned` a durable task (or agent schedule) whose OS job is missing, so nothing runs it — its `status` reads `"orphaned"` too, and the daemon timer does not adopt it; `none` a record that runs only when invoked (a `scheduler.create` prompt task, a once/manual trigger). `program`/`args`/`stdout_path`/`stderr_path` are `null` for a record that is not a command. `car doctor` reads the same store and reports orphaned tasks, installed command jobs that predate run recording, enabled tasks well past their cadence (measured from the last run, or from when recording began for a migrated job) and unreadable task files, and notes, without counting it as a problem, a dream loop that does not reach the user's memory. Refused to a supervised agent on every platform (`tasks.list is not available to a supervised agent: …`): the rows carry every scheduled program's program and arguments and have no owner. Host sessions, the daemon-token operator and the CLI are unchanged.
- `tasks.unschedule` — **Params**: `{ id }` (bare id or full `ai.parslee.car.task.<id>` label). **Returns**: `{ id, os_removed, deleted, orphaned }` — removes any OS schedule AND deletes the task from the store (so the daemon timer drops it too). `orphaned` is true when the record was a durable task whose OS job was already gone, which is why `os_removed` is false for it. Host-management only, like `tasks.schedule`: a supervised agent is refused on every platform (the host-role refusal, and behind it `tasks.unschedule is not available to a supervised agent: …`), and on a daemon with no host token installed every session is refused. Host sessions are unchanged.
- FFI: `scheduleTask`/`listScheduledTasks`/`unscheduleTask` (NAPI) and `snake_case` equivalents (PyO3).
