### agents

**Lifecycle authorization (car#1295).** A connection that authenticated as an
agent — `session.auth { agent_id, token }` — may `agents.start`, `stop`, or
`restart` only that same agent. A host-management connection may control any
agent. When a host token is configured, an unbound daemon-token connection is
not host authority and is refused; this closes the second-connection bypass
where a supervised child reused `CAR_AUTH_TOKEN` without binding `agent_id`.
On a daemon with no host token installed (`--no-auth`, a failed host-token
write at startup, or an embedder that installs none) nobody is the host, so an
unbound client is refused too, with the host-role message and the cause; such a
daemon reports `single_principal_mode` in `capabilities.list` and `session.auth`
(car#3404). A bound agent still acts on itself. On Linux a supervised agent is
not started at all under `--no-auth`: its status is `errored`, and its
`status_reason` says the daemon runs with `--no-auth`.

**Workers.** An orchestrator may also `agents.start`, `stop`, `restart`,
`wait` and `remove` its own workers, by handle, and nothing else's: any other
worker handle, existing or not, is refused with `-32003`, `not_your_worker`.
See `workers.md`.

`agents.upsert`, `agents.install`, and `agents.remove` require host-management
authority, except that an orchestrator may remove its own workers. They are
unavailable to every non-host session on every daemon: upsert/install define
what the supervisor executes, and removal mutates the host-owned process
inventory.

**The CLI presents CAR's local host key for these only after you say yes
(car#2444).** `car install`, `car uninstall`, `car start`, `car stop`,
`car restart`, `car do`'s registration with CarHost (the older-daemon
fallback and `car do --serve --governed-host`), and the approval-policy changes
`car approvals default`, `set-tool` and `reset-tool` (`agent_permissions.*`)
follow the rule agent builds
follow (see coder.md, "Agent builds need the CAR app or you at your terminal").
When stdin and stderr are a terminal and `--yes` is not given, they ask first on
stderr (for example `Stop agent 'my-agent' with CAR's permission? [y/N]`); a no
sends nothing and prints `cancelled.`, and a yes presents the key when the key
file exists. Otherwise (`--yes`, or stdin or stderr not a terminal) they never
present the key and make the ordinary call, so a daemon with a host token
refuses it with `this operation requires the host-management role`, followed by
a line saying an unattended run never presents the key (and, when the key file
is missing too, where CAR expected it). A daemon with no host token refuses it
as well, and every other session's.

**`--as-host` (PR 6d).** `car install`, `car uninstall`, `car start`, `car stop`
and `car restart` take `--as-host`, for a deploy script run by the server's
owner: it presents CAR's local host key without asking, with or without a
terminal or `--yes`. It needs the host-token file, and without it the command is
refused before connecting, naming the file. It is refused, before connecting,
in a process started as a supervised agent. That refusal reads only
`CAR_AGENT_ID` and `CAR_AGENT_TOKEN`, which an agent controls. On Linux the
agent's wall keeps the host-token file from it. On the Mac an unwalled agent
inherits `HOME` and can read that file, so it can unset both variables and
present the key (car#3706). Plain `--yes` still never presents
the key. With `CAR_AGENT_ID` or `CAR_AGENT_TOKEN` set they never present the key:
`agents.install`, `agents.remove` and the approval-policy changes are refused
before connecting, and
`agents.start` / `stop` / `restart` go out under the agent's own identity.
CarHost, the Windows tray (whose dashboard sends `agents.start` / `stop` /
`restart`, and whose setup wizard sends `agent_permissions.set_default`, on its
own host-authenticated connection), `car claude`, CAR's boot-time
registration of Parslee Core, and the SDKs are unchanged. Like every host-only
action, this does not stop a program running as you that reads CAR's local host
key.

`agents.wait` and `agents.tail_log` retain the narrower bound-identity rule: an
agent may read only itself, while an unbound operator may read any id. The rule
is listed per method rather than asserted for the namespace, because not every
`agent_id` here is a subject: `agents.chat` and `agents.chat.*` take the agent as
the RECIPIENT of a turn and are cross-agent by design. `agents.list` and
`agents.health` enumerate and take no id at all.

`declagents.remove` and `declagents.set_enabled` are also refused to a bound
supervised-agent session. A declarative agent runs in-daemon and has no
per-agent token, so there is no bound "itself" exception: only host-management
authority may remove or disable one. On a daemon with no host token installed
(including one started with `--no-auth`) nobody has it, so every session is
refused ("Host authority fails closed").


> **Observe-only mode** (Parslee-ai/car-releases#44). The supervisor
> takes an exclusive OS-level lock on `<manifest>.lock` so two
> car-server processes can't supervise the same manifest and
> double-spawn every agent against shared external state. A
> secondary daemon that hits the lock at boot logs a clear warning,
> installs an *observer* marker, and continues running with the
> agents.* namespace partially degraded:
>
> - `agents.list`, `agents.health` keep working — they fall back to
>   reading the manifest directly (runtime fields like `pid`,
>   `status`, `restart_count` default; only the primary daemon
>   sees live state).
> - Every other agents.* method returns an error containing
>   "observe-only" plus the manifest path the lock-holder owns,
>   signalling that the caller should route the request to the
>   primary daemon (or give this daemon its own manifest via
>   `--agents-manifest` / `CAR_AGENTS_MANIFEST`).
>
> Single-daemon deployments are unaffected.

#### `agents.register_basics`
- **Params**: `null`
- **Returns**: `null`
- Registers CAR's built-in agent utility tools (`read_file`, `write_file`, `edit_file`, `list_dir`, `find_files`, `grep_files`, `calculate`) on this client's session and runs them in the daemon: a later `proposal.submit` calling `calculate` executes there instead of being sent back to the client as `tools.execute`. Mirrors `Runtime::register_agent_basics`. Idempotent. The file tools act on the daemon host (its working directory), so a supervised-agent session is refused with `agents.register_basics is not available to supervised agents`; such an agent registers its own tools with `tools.register`. A session already bound with `session.bindSubstrate` or `session.bindSandbox` keeps that environment.
- **CAR's own files are refused.** On the daemon host, a built-in file tool whose path resolves to one of CAR's credential files (the `run/` copies of `auth-token` and `host-token`, `env`, anything under `secrets/` and this host's peer identity key `peer-identity.key` under the state root, `CAR_HOME` else `~/.car`; and the platform copies of `auth-token` and `host-token` in the per-platform token folder, which is `<CAR_HOME>/ai.parslee.car` when `CAR_HOME` is set and otherwise `~/Library/Application Support/ai.parslee.car` on macOS, `$XDG_RUNTIME_DIR/ai.parslee.car` or `~/.config/ai.parslee.car` on Linux, and `%LOCALAPPDATA%\ai.parslee.car` on Windows) or authority files (the approval journal the daemon records to, `approvals.jsonl` under the state root unless the embedder configured another, and `agent-permissions.json` under the state root), or the host configuration a daemon-token client must not rewrite: the supervised-agent manifest `agents.json` and each agent's `agents/<id>/manifest.toml`, each worker's `workers/<handle>/spec.toml`, the declared-agents registry `declagents.json` (or `CAR_DECLAGENTS_PATH`), the scheduled-task store `tasks/`, and the messaging configuration `messaging.json`, fails with `file access refused: CAR's daemon credential files … are never reachable through the daemon's agent file tools` (or `file access refused: CAR's authority and host configuration files … are never reachable through the daemon's agent file tools`). The message names the class of file, never its contents. When the supervisor runs on a configured manifest (`--agents-manifest` / `CAR_AGENTS_MANIFEST`), or the daemon only observes a manifest another daemon owns, or the approval ledger on a configured journal, those files, and the `agents/<id>/manifest.toml` and the `workers/<handle>/spec.toml` files beside that manifest, are the ones refused, in addition to the state-root defaults. This holds on every session, including one that never called `agents.register_basics` but registered a tool named `read_file` whose callback answers "unknown tool" (the engine falls through to its built-in). The check is on what the path resolves to: a relative spelling, `..`, a symlink (dangling ones included, since writing through one creates its target), a hard link (macOS and Linux, where the file's identity is compared), a write that would create a new file under `secrets/`, and a not-yet-existing name the volume folds to a protected one (`RUN/HOST-TOKEN`, `approvalſ.jsonl`) are refused the same way. `grep_files` over a folder that holds one of these files still runs and leaves that file out of its matches; `list_dir` and `find_files` refuse only a protected target, since they return names and not contents. A human approval of the call does not lift the refusal. A new name containing non-ASCII characters directly in the state root, `run/`, the platform token folder or `secrets/` is also refused, with `file access refused: the daemon's agent file tools do not create a new non-ASCII name in CAR's state, run, token or secrets folder, because it cannot be told apart from CAR's own files`; an existing file with such a name, an ASCII new name there, and a non-ASCII name anywhere else are unaffected. What this does not protect: the user's own files, which stay readable and writable through these tools by a daemon-token client. Every other path behaves as before.

#### `agents.list`
- **Params**: `{}`
- **Returns**: `[ ManagedAgent ]` — every supervised entry in `~/.car/agents.json` plus its current runtime status, as one flat object per agent: `{id, name, command, args, cwd, env, restart, max_restarts, backoff_secs, auto_start, method_allowlist?, secrets?, secrets_notice, capabilities, delegate_for?, spend_caps, budget, at_budget?, status, pid, last_exit_code, restart_count, started_at, blocked_by_pid?, status_reason?, last_error?, attached, tools?, manifest_path, log_path, stderr_log_path, session_id?, network_fence_warning?, handshake?}`. The agent's settings sit at the top level of the row, beside its status, not under a `spec` key: read a row's name as `row.name`, not `row.spec.name`. The agent's per-agent `token` is never in the row. `cwd`, `pid`, `last_exit_code`, `started_at` and `secrets_notice` are always present and `null` when unset; a field marked `?` is left out when unset. `status` is one of `stopped | starting | running | backoff | errored`. `spend_caps` is the agent's declared caps as written in its bundle, `[ { usd, per } ]`, `[]` for an agent with none; `budget` is `uncapped | under | at_budget`; `at_budget`, present only while a cap is reached, is `{ cap: { usd, per }, holding, resets_at, zone }`, as `spend.status` returns it. "At budget" is a budget state, not a `status` (the process is running), so `status` keeps its five variants. The caps apply to model calls made through CAR; see [spend](spend.md#spend). `last_error`, present once the current run has had one, is `{ kind, exit_code?, signal? }` (see `agents.wait`): CAR's enum and numbers only, cleared by a fresh start. `method_allowlist` is absent for an unrestricted legacy token, present (including `[]`) for a scoped token, and is shown by `car inspect`. `tools`, when present, is the attached flagship assistant's sorted current model-visible tool names, obtained through a bounded reverse query; it is omitted for detached, older, and other supervised agents rather than inferred from broad capabilities. `manifest_path` is the daemon-resolved per-agent `agents/<id>/manifest.toml`; `log_path` and `stderr_log_path` are the stdout/stderr redacted `.log` files of the agent's newest finished run (see `agents.tail_log`, Per-run log files), never a running run's raw file; `<id>.stdout.log`/`<id>.stderr.log` for an agent with no finished run yet, only while nothing is at that name, or else the agent's log folder itself: never a log from before per-run files, and never a symbolic link. Declarative rows remain tagged `kind:"declarative"` and carry their manifest tool allowlist and, when the registry has assigned one, `registration_id` (see `declagents.list`), but do not carry supervised paths.
- `blocked_by_pid` (car#732) is present only when the agent is in `backoff` **because a live process this supervisor does not own is already running as it** — typically one that outlived a previous `car-server` and still holds the agent's port. Without it, `backoff` + `pid: null` + a healthy process on the port is indistinguishable from a broken agent, and the cause is only visible via `lsof`. Stop the named pid and restart, or leave it: supervision resumes automatically once it exits.
- `attached` is `true` once the supervised child has called `session.auth { agent_id }` and bound a WS connection (#169). `session_id` carries the bound `client_id` while attached. The lifecycle status alone can't distinguish "alive but never attached" from "alive and attached".
- Declarative agents from `declagents.json` are merged in as `kind:"declarative"` rows. When that file exists but cannot be read or parsed (an empty or whitespace-only file is an empty registry, not an error; see `declagents.list`), `agents.list` still returns every supervised row and leaves out only the declarative ones, logging a warning that names the file; `declagents.list` returns the error.
- `handshake`, present once the agent has authenticated and called `server.handshake` against this CAR, is its most recent handshake as the daemon recorded it: `{observed_at, client_protocol_min?, client_protocol_max?, server_protocol_min, server_protocol_max, negotiated_protocol?, client_version?, server_version, refusal?}`. `negotiated_protocol` absent means the daemon refused the handshake (`refusal` carries the message) and the agent cannot use the daemon; `negotiated_protocol` below `server_protocol_max`, or a `client_version` different from `server_version`, means it connected and is drifting. Read from `agent-handshakes.json` beside `agents.json` (for a worker, from `workers/<handle>/agent-handshakes.json` in its own root), which `car doctor` also reads (car-releases#104).
- `network_fence_warning` is present on a worker's row while this CAR starts workers without the network fence (CAR-544): "Network fence: not built yet. This worker can reach any host." `car agents` and the dashboard show it in red.
- **Who sees which rows.** A session bound to a supervised agent (`session.auth { agent_id, token }`) gets only its own row, so one agent cannot read another agent's spec, `env` values or log paths. An orchestrator also gets its own workers' rows, and no other worker's. A worker's `manifest_path`, `log_path` and `stderr_log_path` are inside its own root, `<CAR_HOME>/workers/<handle>/`. Host sessions and the daemon-token operator (the `car` CLI and the dashboard) still get every row. `agents.health` follows the same rule: an agent-bound session gets only its own row (no other agent's id or command line), and an orchestrator also its own workers' rows; host and operator sessions get every row.
- Driven by `car_registry::supervisor::Supervisor`. Closes [Parslee-ai/car-releases#27].

#### `agents.upsert`
- **Authorization**: host-management authority.
- **Params**: `AgentSpec` — `{ id, name, version?, command, args?, cwd?, env?, restart?, max_restarts?, backoff_secs?, auto_start?, interpreter?, method_allowlist?: string[], secrets?: string[], delegate_for?: string[] }`. `version` is the bundle version `agents.install` recorded for the agent. `restart` is `never | on_failure | always`. `id` must be filename-safe (alphanumeric + `-_.`) and is unique ignoring ASCII letter case: a new id that differs from an existing agent's only in case (`Bob` beside `bob`) is refused with an error naming the existing id, because ids name files and folders (`agents/<id>/`, `logs/<id>.*`, `memory/agents/<id>*.json`) that a case-insensitive file system such as APFS would share. Re-upserting the same id is unchanged, and existing registrations are left as they are. When the agents folder exists but cannot be listed, a new id is refused (`cannot be checked against the installed agents: reading <folder> failed: …`) rather than checked against an empty list.
- **Returns**: the resulting `ManagedAgent`.
- Persists the manifest; the agent is NOT auto-started — call `agents.start` (or rely on `auto_start: true` for the next car-server boot).
- **A non-empty `spend_caps` is refused.** Spend caps come from the installed bundle's `[spend]` table and change only by installing a new version (`agents.install`). An upsert whose payload carries a non-empty `spend_caps` is refused with "agents.upsert does not accept `spend_caps`: …" and changes nothing. An absent, `null` or empty (`[]`) `spend_caps` — what an `agents.list` row of an uncapped agent carries, so a round-tripped row is accepted — is ignored, and a plain upsert keeps the installed caps either way. An agent registered at boot with a bad installed cap (`status_reason` "not started: …") refuses a plain upsert with that reason until a version whose caps validate is installed. The caps apply to model calls made through CAR; see [spend](spend.md#spend).
- **`method_allowlist`** scopes the per-agent token to a subset of daemon methods whose generated capability role is `agent`, `operator`, or `owner`. Unknown and `host`-role names are rejected at upsert/install. The list narrows existing authorization rather than granting the listed role. This scopes the agent credential only: on the Mac it does not confine a same-user process, which can read the daemon token file, and on Linux the sandbox makes it a wall. The supervisor never puts the daemon-wide `CAR_AUTH_TOKEN` into the environment of an agent that has a `method_allowlist` or work context, or of any agent on Linux (#3008). Omit it for backward-compatible unrestricted behavior; pass `[]` to deny every application method. When an upsert omits both the token and the allowlist for an existing scoped agent, both are retained together so an older client cannot silently widen the token. Removing the scope requires supplying/rotating the token explicitly.
- **`delegate_for`** (car-releases#109) makes the agent a **human delegate**: each entry is `human:<name>`, and the agent may then read and answer that person's Lattice requests, set that person's node status and note, forward questions it received to that person on the asker's behalf (`agents.message { on_behalf_of }`), and read `multiplayer.list` / `multiplayer.get`, over its own agent connection, without the host credential. Consent stays the operator's (see [lattice](lattice.md#lattice), **Human delegates**). Only this method sets it, and only from the operator's host client: an upsert from anything else that changes `delegate_for` is refused (`-32020`, `consent_is_host_only`), including on a daemon without a host token, where nobody is the host. `agents.install` keeps the grant already recorded for the id and never takes one from a publisher's manifest, and a worker started from a bundle never carries one. A personal agent only: an agent with a `work_context` is refused one. Entries are checked (`human:` plus 1–128 of `[A-Za-z0-9._-]`), sorted and de-duplicated. **Revoke** by upserting without the entry; the daemon reads the grant from the spec on every call, so it takes effect on the agent's next call over a connection that is already open. Unlike `method_allowlist`, an upsert that omits `delegate_for` does not retain it: omitting it is how it is revoked. `agents.list` shows it, and `lattice.nodes` lists each person's `delegates`.
- **Linux folder wall.** On Linux every supervised agent is locked into its own folder (`<CAR_HOME>/agents/<id>/`, read-only, with `data/` read-write) before it runs, using Landlock (Linux 6.2 or newer with Landlock enabled). `HOME`, `TMPDIR`, `TMP`, `TEMP` and the `XDG_*` directories point inside `data/`, and the agent starts in `data/` unless `cwd` names a folder inside its own. A `cwd` outside the agent's own folder is refused (`errored`, reason "outside its own folder"), and an absolute path in `args` outside it, the system paths and `/nix/store` is simply not readable; a `command` outside them is refused. On Linux 6.12 or newer (Landlock ABI 6) the agent also cannot signal processes outside its wall or connect to abstract Unix sockets, and on Linux 7.1 or newer (ABI 9) it cannot connect to pathname Unix sockets outside its folder; on older kernels it can, so the server owner keeps other same-user programs (tmux, screen, `systemd --user`, rootless Docker) off the server or uses the Docker image. When the kernel cannot enforce the wall, or the folder cannot be prepared, the agent does not start: `agents.list` shows `errored` and a `status_reason` that begins "This server's Linux kernel can't confine agents to their own folders", and the supervisor does not retry.
- **macOS folder wall, for workers and orchestrators only.** On a Mac, a worker and an orchestrator (a manifest with `[[workers]]`) are locked into the same folders with the same grants, applied with Seatbelt (`/usr/bin/sandbox-exec`) from the same plan: the folder read-only, `data/` read-write, the system paths a Mac program needs (`/bin`, `/sbin`, `/etc`, `/System/Library` and the dyld cache cryptexes, `/Library`, the active developer directory's bundle, `/private/var/{select,run,db/timezone}`, and the program parts of `/usr`, `/usr/local` and `/opt/homebrew`: `bin`, `sbin`, `lib`, `libexec`, `include`, `share`, `Cellar`, `opt`, `Caskroom`, `Frameworks`, `Library` and the CA bundles under `etc/`, never a prefix whole, so a Homebrew service's data under `var/` and its configuration under `etc/` are not readable), and nothing else: CAR's token files, its key store (the `secrets/` folder), the user's home, other agents' and workers' folders and the rest of `CAR_HOME` are refused. System services are closed too, because each answers as the daemon's user outside the wall: every Mach service is refused except five a command-line program needs (user and group names through `opendirectoryd`, certificate trust evaluation through `trustd`, proxy and DNS configuration through `configd`, and the temp folder path through `dirhelper`), so Spotlight (`mdfind`, `mdls`), the Keychain, the pasteboard, the window server, screen capture, preferences and Launch Services are unreachable; preferences are neither read nor written through `cfprefsd`, no IOKit driver is opened and no IOKit registry property (the serial number, say) is read, hard links and clones are made only inside the agent's own `data/` (a readable file cannot be given a second name there), the system keychain files under `/Library/Keychains` and the system logs under `/Library/Logs` are refused, and a worker gets no POSIX shared memory or named semaphore. Unix sockets outside its own `data/` (the system resolver and log excepted), signals outside its own sandbox, the process table through all three of its doors (`process-info`, the `kern.proc` sysctls that `ps` reads, and `proc_listpids`), Apple Events, launchd jobs and Launch Services opens are refused as well. **System V IPC is open and must be assumed to be a data channel between labels:** the profile denies the System V operations Seatbelt offers, but none refuses creation, so `shmget`, `semget` and `msgget` succeed for every binary (each leaves a system-wide object the worker cannot remove, the table can be filled, and a key's existence is a signal between labels); attaching to or opening another label's existing object was refused for every binary measured from inside the wall (Apple's `python3`, Homebrew's ad-hoc-signed `python3`, a C program), and for a binary nobody measured a channel must be assumed. Linux is no stricter: Landlock does not mediate System V IPC at all. What else stays open or limited, as measured on macOS 26: TCP and UDP (no network fence yet); `sysctl` reads other than `kern.proc.*` (the CPU count and the like); the hardware UUID (`gethostuuid(2)`, a system call Seatbelt has no operation for); signal 0 to any process of the user (a liveness probe); the rest of `/Library`, which is root-owned and world-readable; the five services above; and the temp folder: `TMPDIR` points into the agent's own `data/tmp`, which Python's `tempfile`, node's `os.tmpdir()` and every program that honours `TMPDIR` use, but `mktemp` and `mktemp -t NAME` with no path use the user's shared temp folder and fail, while `mktemp "$TMPDIR/x.XXXXXX"`, `mktemp -d "$TMPDIR/d.XXXXXX"` and `mktemp -p "$TMPDIR"` work, and bun's `os.tmpdir()` reports `/tmp`, where its writes fail. The `/usr/bin` shims for `python3` and `git` run their tool after printing a harmless `xcrun_db` cache error. The start-up self-test covers the file rules, the service deny and the clone rule; every other rule is covered by the test suite only, and the rows that need a system call run Apple's `python3`, which Seatbelt treats more strictly than ordinary binaries, so they prove their rule for that binary only. Measured on macOS 26 only; an older release whose `sandbox-exec` rejects one of the profile's operations fails the self-test and refuses workers. Everything the agent starts inherits the sandbox. A Mac where the profile cannot be applied (the daemon itself runs inside a Seatbelt sandbox, which macOS cannot nest) refuses the agent with a `status_reason` that begins "This Mac can't confine agents to their own folders". A walled Mac agent left running by an earlier daemon is never adopted at boot: it is stopped and started afresh, walled, as on Linux. Every other Mac agent is unchanged. Two things the Mac wall does not have: a per-agent init (a walled Mac agent's tree is ended by process group, as every Mac agent's is), and a network fence (neither platform has one yet).
- **`secrets`** lists the names of secrets the agent needs from CAR's secret store (the OS keychain; on a Linux machine with no Secret Service, one owner-only file per key under `~/.car/secrets/`). At every start the daemon fetches exactly those names, checks the daemon's policy rules for each, writes a value-free audit row per read, and puts each value in the child's environment under the same name. A missing secret, a policy denial or a locked store blocks the start with a reason that names the secret or store (`agents.list` shows it as `status_reason`); a locked store retries with backoff, the others stop at `errored`. An agent that lists nothing receives no provider keys, and `agents.list` carries a `secrets_notice` with the line to add. Upsert rejects a name that is not a valid environment variable name, is empty, contains `=`, is longer than 128 characters, is one CAR or the OS controls (every name in the pass-through list below, `LD_*`, `DYLD_*`, `PYTHON*`, `NODE_OPTIONS`, `PERL5OPT`, `RUBYOPT`, `JAVA_TOOL_OPTIONS`, `BASH_FUNC_*`, `PROMPT_COMMAND`, `GIT_SSH_COMMAND`, `GIT_CONFIG_*`, `DOTNET_STARTUP_HOOKS`, `CORECLR_*`, `CAR_*`, `LC_*`, `XDG_*` and similar), or is also a literal `env` key. A manifest read from disk is checked the same way when the agent starts; an invalid declaration fails that agent's start with a reason, and declared values are applied before the supervisor's own `CAR_*` variables so a declaration can never replace them. A supervised agent's `secret.get` is limited to these names; any other name is refused with `not_declared`, and `secret.list`, `secret.status`, `secret.put` and `secret.delete` are refused to a supervised agent's session. CAR's own assistant (`parslee-core`, `car-assistant`) is the exception: it may read provider keys, resolved from the environment first, then the secret store.
- **What a declaration is, and is not.** CAR protects people from the agents they create on their own computers by controlling what it hands each agent: an agent gets whatever CAR deliberately gives it, which is its declared secrets. Agents run as the same OS user as the person, and CAR does not wall them off from that user's files. Such an agent can read the secret store, `~/.car/secrets` and the daemon token file directly, and the daemon's own token still reaches every child. A declaration is therefore not a boundary between an agent and its user's files.
- **The child's environment** is not the daemon's. It starts from an allowlist (`PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `TMPDIR`/`TMP`/`TEMP`, `TZ`, `LANG`, `LANGUAGE`, `LC_*`, `XDG_*` directories, `CAR_HOME`, `SSH_AUTH_SOCK`, the proxy variables `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` (and lowercase forms), `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`; on Windows also `SystemRoot`, `PATHEXT`, `COMSPEC`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `ProgramData`, `ProgramFiles*` and the other variables a program needs to start), then the `CAR_*` variables the supervisor sets (`CAR_DAEMON_URL`, `CAR_AGENT_ID`, `CAR_AGENT_TOKEN`, `CAR_AUTH_TOKEN` when auth is on, `CAR_WORK_CONTEXT` for an agent with a work context), then declared secrets, then the literal `env` byte for byte. Everything else the daemon holds is dropped. An agent adopted after an unclean daemon death keeps the environment it started with until its next restart. Each start appends a value-free line (kind, environment, declared names, variable names, and, for an agent that declares nothing, the same notice `agents.list` shows) to `agent-starts/<id>.jsonl` beside the manifest.
- **`interpreter` sugar (#171)**: instead of hand-coding `/opt/homebrew/bin/node` (or whatever the current PATH resolves to), pass `interpreter: "node" | "python" | "deno" | ...` and the supervisor resolves the bare program name against `$PATH` *once* at upsert and writes the absolute path into `command`. Resolution then freezes — subsequent PATH changes do not silently rewire which binary the spec points to. The strict no-PATH-lookup rule at upsert time still holds: an interpreter that resolves into `/tmp` or fails the executable-bit check is rejected.

#### `agents.install`
- **Authorization**: host-management authority.
- The agent id follows the same rule as `agents.upsert`: unique ignoring ASCII letter case, checked against supervised agents and installed agent folders, under the same lock as the install.
- **Params**: `AgentManifest` — the nested TOML shape from
  `docs/proposals/contributed-agents.md`, JSON-encoded for the
  wire: `{agent: {id, name, namespace?, version?, …}, publisher?,
  runtime?, lifecycle?, transport: {kind, …}, capabilities?}`.
  `transport.kind` is `pure_data` or `external_process`; the
  per-kind sub-table carries the rest. External-process transports accept the
  same optional `method_allowlist: string[]` scope as `agents.upsert`.
  An optional top-level `upgrade: boolean` sits beside the manifest's own
  keys (see "Installing over an installed agent" below).
- Optional top-level `owner_assistant: boolean` (default false) binds the
  installed agent as the owner's named assistant after installation succeeds.
  The binding is durable in the conversation floor; worker bundles are refused.
  Without a binding, owner-floor submissions are refused. The host may also
  bind an existing installation with `conversation.assistant.bind {agent_id}`.
- **Returns**: `{report: {missingOptional: [{namespace, feature}]}, agent: ManagedAgent | null}`.
  `agent` has the same flat shape as an `agents.list` row, without the list-only fields (`attached`, `tools`, `manifest_path`, `log_path`, `stderr_log_path`, `session_id`, `network_fence_warning`, `handshake`). The installed spec records `version`, the manifest's `agent.version`, but `agent` does not carry it.
- A **worker bundle** (`[agent] role = "worker"`) is never installed as an
  agent: it goes to the bundle store, `<CAR_HOME>/bundles/<name>/<version>/`,
  and runs only as a worker an orchestrator that declares it starts with
  `workers.start` (see [workers](workers.md#workers)). The result is then
  `{worker_bundle: {bundle, version, declared_by: [orchestrator ids], environment: "absent"}}`
  instead of an agent row. The same version installed twice is refused.
- An **orchestrator** (a manifest with `[[workers]]`) is refused install with
  `-32013` and `data.reason` `auth_disabled` under `--no-auth`, or
  `fence_unavailable` where its workers could not run walled (Windows, a Linux
  host without Landlock, a Mac where the wall's self-test fails). The same refusal applies
  to `agents.start` and `agents.restart` of an orchestrator, and of a worker's
  handle when any admission check fails.
- `agents.upsert` refuses to edit an orchestrator (install a new version
  instead), to add `[[workers]]` declarations, and any payload carrying a
  `worker` record or an id starting with `wk_`.
- A worker's token works only on its WebSocket session; MCP refuses it. Every
  daemon boot mints a fresh token for each worker, so a worker process that
  outlived its daemon cannot connect back, and a surviving worker process is
  killed at boot rather than adopted.
- Installing over an installed agent (car#3264): an id already in use, by a
  supervised agent or one tracked on disk only, is refused and nothing
  changes, the installed agent keeps running. The error names the installed
  agent and its version and says how to upgrade on purpose. The same version is
  refused as `agent <id> <version>: this version is already installed`, with or
  without `upgrade`, and the error says to remove the agent first to install it
  again. Versions are compared by semver when both parse (a leading `v` is
  accepted, so `v1.0.0` is `1.0.0`), otherwise as exact strings. A different
  version replaces the installed agent only when the params carry
  `upgrade: true` (`car install --upgrade`), and then replaces it exactly as an
  install always did. An older version is a different version, so
  `upgrade: true` also rolls back: asking for it is the explicit choice. Two
  bundles that declare no version are not taken to be the same version, so
  `upgrade: true` may replace one with the other. An install never switches an
  agent between supervised (`external_process` with a command) and tracked on
  disk only (`pure_data`, `health_url`-only): that is refused with "Remove it
  first", upgrade or not. `agents.upsert` is unchanged in what it replaces; an
  upsert that names no `version` keeps the recorded one, as it keeps the
  token. The id is validated (the `agents.upsert` id rule) before any path is
  built from it.
- **`[spend]` is validated** (`docs/agent-bundle-spec.md`, "`[spend]`"). A
  manifest with a `[spend]` table needs `[runtime] bundle_format_version = 3`
  and `car_min_version = "0.59.0"` or newer, and each cap must be
  `{ usd = <number greater than 0>, per = "hour" | "day" | "month" }`, each
  period at most once. A failure is `manifest validation failed: <text>`
  where the text names the field — "agent `<id>`: [spend] needs [runtime]
  bundle_format_version = 3", "[spend] needs [runtime] car_min_version =
  \"0.59.0\" or newer", "[spend] caps[1].usd must be greater than 0 (got -5)",
  "[spend] caps[0].usd must be a number of US dollars (got \"ten\")", "[spend]
  caps[2].per must be one of hour, day, month (got \"week\")", "[spend] cap for
  day declared twice", "[spend] caps[0] has an unknown field `limit`",
  "[spend] caps[0] needs usd and per", "[spend] caps[0].usd must be at most
  $1,000,000,000,000 (got …)" — and nothing is installed. An install that
  changes the caps of an installed agent (`upgrade: true`) applies them to the
  agent's next model call with no restart, and appends the change to its cap
  history (`spend.status.cap_history`). The caps apply to model calls made
  through CAR; see [spend](spend.md#spend).
- Runs install-time validation against the daemon's default host
  capability advertisement (Parslee-ai/car#182 phase 3):
  - `runtime.car_min_version` (if present) must be satisfied by
    the daemon's own semver. Accepts a bare semver (interpreted
    as `>=`) or a cargo-style requirement (`">=0.8, <0.9"`).
  - Every `capabilities.required[namespace][feature]` must be
    advertised by the host. Fail-closed on any miss.
  - `capabilities.optional` is reported back as `missingOptional`
    when the host can't satisfy it — informational, not
    blocking.
- For `external_process` manifests with a `command`, the
  supervisor adopts the agent (mints a token if absent) and
  returns it. For `pure_data` and `health_url`-only manifests,
  the manifest is written to `~/.car/agents/<id>/manifest.toml`
  but `agent` comes back `null` (the supervisor only spawns
  command-shaped externals in phase 3).
- Signature verification: when the manifest carries a
  `[publisher]` block, the signature is verified via
  `car_bundle::verify_signature`. Phase 3 is still
  warn-but-not-reject for failed signatures (logs a warning,
  still installs); phase 4+ may tighten.

#### `agents.health`
- **Params**: `{}`
- **Returns**: `[ { id, command, ok, reason? } ]` — one entry per managed agent. `ok: true` means `validate_command(command)` still accepts the path; `ok: false` populates `reason` with the validator's error (file missing, no execute bit, lives under a scratch dir, etc.).
- Use after a system upgrade to surface broken specs before `agents.start` does. Pairs with the `interpreter` sugar — when `ok: false` for an interpreter-resolved entry, the host can re-upsert with the same interpreter name to pick up the new path.

#### `agents.remove`
- **Authorization**: host-management authority; or an orchestrator for one of its own workers. An agent never removes itself (the host-role refusal), and a bound agent naming another agent is refused with "agents.remove `<id>` is not `<caller>`'s to remove: a supervised agent may remove only its own workers". `car uninstall` run as a supervised agent is still refused before it connects.
- **Params**: `{ id: string, stop?: bool }`. `stop` (default `false`) applies to a worker only: a worker that is running, starting or in backoff is refused without it (`-32003`, `worker_running`). Removing a worker keeps its records for the server owner, marked removed (see `workers.md`). Removing an orchestrator stops and removes its workers first.
- **Returns**: `{ removed: bool, log_scrub_error?: string }` — `log_scrub_error` is present when a run's redacted log could not be written or its raw file could not be removed (see `agents.tail_log`, Per-run log files); the files outlive the agent, the tail keeps redacting those values until the daemon restarts, and a later daemon withholds those raw files.
- Stops the running child first if it's up. Idempotent. An agent tracked on disk only (a `pure_data` or `health_url`-only install) has its `~/.car/agents/<id>/` folder deleted and reports `removed: true`, which frees its id for a plain `agents.install` again; if any file in that folder cannot be deleted the call fails, and the folder may be left partly deleted. When that stop is declined (see `agents.stop`) the call fails with the same error and removes nothing, so the spec of a process that is still running is never dropped. The rest of this paragraph is about a supervised agent or worker, not a disk-only install. When the files the next boot would load the agent from cannot be deleted (each `manifest.toml` under `~/.car/agents/` that declares its id, whatever its folder is called, or a worker's `spec.toml`), the call fails with an error naming the file and the agent stays installed, so the daemon and the next boot agree (the removal has already stopped it, and does not start it again); call it again once the file can be deleted. Once those files are deleted the call succeeds: it rewrites no other agent's `manifest.toml`, so nothing saved for another agent can turn a completed removal into an error. A failure to delete what is left after them (the rest of that agent's folder, or a worker's other files such as its handed-over values) is logged by the daemon, not returned as an error, and those files stay on disk. A `manifest.toml` there that the daemon cannot read fails the call the same way, before anything is deleted, since the next boot repairs its permissions and may load it as this agent; a restart makes it readable. A `manifest.toml` that is a symbolic link is skipped, as boot skips it. Removing an agent deletes only the folders under `~/.car/agents/` whose manifest declares its id (and a folder named after the id whose manifest does not parse), never another agent's.

#### `agents.start`
- **Authorization**: the same bound agent id, an orchestrator for one of its own workers, or host-management authority.
- **Params**: `{ id: string }`
- **Returns**: `ManagedAgent`
- Spawns the child if it isn't running. No-op when already `running` or `starting`. Resets `restart_count`.
- Fails with `agent <id> not found` when no such agent is registered, including when a concurrent `agents.remove` drops it while the start is in flight (even if an agent with the same id is added back meanwhile, with a new token or with an identical spec and token): nothing is started, and the call never returns a `starting` agent that no longer exists. If an `agents.upsert` replaces the agent's spec while the start is in flight, the call fails with `agent <id> changed while it was starting; nothing was started. Start it again to run its current spec`. A start never runs a spec the agent no longer has, and never stops the process of the agent that replaced it. Once the start has installed its supervision loop, a concurrent `agents.remove` followed by a re-add under the same id fails the call with `agent <id> not found`, even when the re-added spec and token are identical, because the re-added agent is not the one that was started; an `agents.upsert` that edits the agent in place at that point (a new spec or a rotated token) returns the agent with its current spec.

#### `agents.stop`
- **Authorization**: the same bound agent id, an orchestrator for one of its own workers, or host-management authority.
- **Params**: `{ id: string, signal?: "term" | "kill" }`
- **Returns**: `ManagedAgent`
- `term` (default) sends SIGTERM and waits the supervisor's grace window before escalating to SIGKILL; `kill` skips the grace. A stop that has started finishes, through the SIGKILL, even if the client disconnects or abandons the call during the grace window; the same holds for `agents.restart` (which still starts the agent again) and `agents.remove` (which still drops the spec). On daemon shutdown every agent is stopped with `term` under one overall budget; any agent still alive when the stops finish or the budget expires is sent SIGKILL before the daemon exits, unless its pid can no longer be verified as the agent's. Once shutdown has begun, `agents.start` and the start half of `agents.restart` (and an install of an `auto_start` agent) fail with `the daemon is shutting down; agent <id> was not started`.
- An agent adopted from a previous daemon is signalled only while its pid is provably the agent's process (its recorded start token matches). When the token cannot be read, the stop is **declined**: the call fails with an error beginning `stop of agent <id> declined`, the agent stays `running` and supervised, and its pid file is kept. If the token became unreadable during the grace window, the error says the SIGTERM may already have been sent and the SIGKILL was withheld; the exit that SIGTERM causes then leaves the agent `stopped` instead of restarting it. The token read failure is transient: retry the stop. Windows records no start token, so a stop there is never declined. A successful stop clears the pid file only once the process is gone; if a SIGKILL's exit is not observed within about a second, the returned agent is `stopped` but keeps its `pid`.

#### `agents.restart`
- **Authorization**: the same bound agent id, an orchestrator for one of its own workers, or host-management authority.
- **Params**: `{ id: string }
- **Returns**: `ManagedAgent`
- A declined stop (see `agents.stop`) fails the call with that error; nothing is restarted.
- The start half fails exactly as `agents.start` does: `agent <id> not found` when a concurrent `agents.remove` dropped the agent (or it was re-added, even with an identical spec and token) after the stop, and `agent <id> changed while it was starting; nothing was started. Start it again to run its current spec` when an `agents.upsert` replaced its spec while the start was in flight. After the start half has installed its loop, a remove and re-add under the same id fails with `agent <id> not found` (even with an identical spec and token), and an in-place `agents.upsert` returns the agent with its current spec.

#### `agents.wait`
- **Params**: `{ id: string, targets?: (AgentStatus | "ended")[] = ["running"], timeout_secs?: number = 30, poll_ms?: number = 200 }`
- **Returns**: the matching `ManagedAgent` once its `status` is one of `targets`; an error if the timeout elapses first (`WaitTimeout`) or the agent isn't in the manifest (`NotFound`). A target that is neither a status nor `"ended"` is refused, naming the choices.
- Blocks until a supervised agent reaches a target state — the persistent-agent analogue of "wait until ready / wait until done". Pass `["running"]` to wait for an agent to come up, or `["ended"]` (`stopped` or `errored`) to wait for it to finish. It only observes the supervisor's status transitions; it never starts or stops the agent. `poll_ms` is clamped to ≥10ms. FFI: `agentsWait` (NAPI) / `agents_wait` (PyO3).
- **A worker's row** (`docs/websocket-protocol/workers.md`) also carries how it ended, so one reply answers "did it finish, and how" with no log read. End states are sticky: a wait started after the worker ended, or by a daemon started since, still gets them, until the worker is next started. For a worker, `"ended"` matches `stopped` only once its end is on record, so the stop half of an `agents.restart` is not an end.
  - `end_reason`: `finished` (it exited and its restart policy did not bring it back), `stopped_by`, `orchestrator_stopped`, `timed_out`, `kept_crashing`, `interrupted_by_restart`, `restart_refused` (a crash restart or a start at boot that the admission point refused) or `environment_failed` (its wall could not be applied, or a key it declares could not be handed to it); `null` while it has not ended. Every way a worker ends for good records one, so `"ended"` never returns a worker without it.
  - `end_message`: CAR's own sentence for it: `finished`, `stopped by <name>` (a person, the orchestrator's id or "the server owner"), `stopped: its orchestrator stopped`, `stopped: time limit reached`, `stopped: kept crashing`, `interrupted by restart`, `stopped: not started again: <refusal code>` (for example `worker_limit_reached` or `label_deleting`) or `stopped: the place it runs in could not be prepared`; `null` with no end.
  - `last_error`: `{ kind: "exit" | "signal" | "timed_out" | "kept_crashing" | "spawn_failed" | "environment_failed", exit_code?: number, signal?: number }`, or `null`. `exit` carries the non-zero code; `signal` the signal number; `kept_crashing` the last crash's code or signal; `spawn_failed` and `environment_failed` carry neither. A clean exit has none, and neither has `restart_refused`: the refusal is the cause, not the crash before it. `interrupted_by_restart` carries the exit its init saw, when it saw one.
  - `report`: the worker's last structured `workers.report` (`{ status, counters, run_ids }`), or `null`.
  - `end_record_error`: present only when the end could not be written to disk and is held in the daemon's memory: CAR's own error text for the failed write. The end itself is in the other fields.
  - None of these is text the worker wrote. Its stdout and stderr stay in its own logs, which only the server owner reads; no reply an orchestrator can get through `agents.wait`, `agents.list`, `agents.health` or `events.query` carries them.

#### `agents.tail_log`
- **Params**: `{ id: string, n?: number, stream?: "combined" | "stdout" | "stderr", offset?: number }`.
  - `n` — lines **per included stream** (default 100; `0` ⇒ whole file, still bounded by the tail byte ceiling below). Both `n` and the legacy alias `lines` are accepted (the CarHost UI historically sent `lines`).
  - `stream` — which captured stream(s) to return (default `combined`). Each stream is tailed **independently** to its own `n`-line budget, so a long stale `stderr` can no longer bury a healthy agent's live `stdout` (Parslee-ai/car#273).
  - `offset` — page back: skip this many lines from the end of each stream before taking the window (`offset = n` ⇒ previous page).
- **Returns**: `{ lines: [string], stdout: [string], stderr: [string], stdout_total: number, stderr_total: number, stdout_path: string, stderr_path: string, more: boolean }`.
  - `lines` — legacy combined view: stdout lines then stderr lines (each independently budgeted). Kept for back-compat.
  - `stdout` / `stderr` — the per-stream windows (empty when `stream` excluded that side), for separate-pane / stream-select viewers.
  - `stdout_total` / `stderr_total` — line count in the scanned tail before windowing (for "showing N of M" / scrollbar sizing). Exact for any log within the tail byte ceiling; for a multi-GB log it counts only the lines in the last ceiling bytes, and `more` is `true`.
  - `stdout_path` / `stderr_path` — absolute paths of each stream's newest finished run's redacted `.log` (for "reveal in Finder" / opening the full log), never a running run's raw file, which holds handed values unredacted; `<id>.stdout.log`/`<id>.stderr.log` when the agent has no finished run, only while nothing is at that name, or else the agent's log folder itself; never a log from before per-run files or a symbolic link. A running run's output is read through this method.
  - `more` — `true` when paging further back (larger `offset`) would surface older lines on at least one included stream, **or** when the tail read was truncated at the byte ceiling (older lines provably exist on disk).
- **Note**: the capture format is raw child output with no per-line timestamps, so a true cross-stream timestamp interleave isn't available; combined ordering is stdout-then-stderr with each side independently budgeted.
- **Bounded read**: each stream is read via a **bounded backward seek** (at most an 8 MiB tail, across its runs), not a whole-file slurp — keeping repeated polling (e.g. a live-follow viewer re-fetching every 2s) cheap regardless of how large the on-disk log has grown. A log larger than the ceiling is truncated to its last 8 MiB; the partial leading line is dropped and `more` is forced `true`. Combined-view paging (`stream: "combined"` + `offset`) is **not** order-preserving — a combined page is a stdout-block followed by a stderr-block, so prepending an older combined page scrambles that ordering; page within a single stream (`stdout`/`stderr`) to scroll back, or open the file directly.
- **Per-run log files** (car#3637): each start of an agent (a run) writes files of its own in the agent's log folder (`<CAR_HOME>/logs/`, or a worker's own): `<id>.<run>.stdout.raw` and `<id>.<run>.stderr.raw`, created new (never reused) and owner-only, where `<run>` is `<start ms>-<daemon nonce>-<n>` and so unique to the daemon instance that began it. Beside them, `<id>.<run>.run.json` records a salted SHA-256 fingerprint, never the value, of every secret value the run is handed: its declared `secrets` at the spawn, and each `secret.get` reply before it is answered. A stream reads as the agent's kept runs one after another, oldest first, and `n`, `offset`, `more`, the totals and the 8 MiB ceiling apply across them. The daemon keeps the last 20 finished runs per agent (the `CAR_AGENT_LOG_RUNS_KEPT` environment variable of `car-server` sets another number) and deletes older runs' redacted logs when a run ends. A run is kept or deleted whole: one with a withheld file or a raw file left is kept, and so is the newest run this daemon began, wherever a clock stepped back sorts it. Before deleting a run's files the daemon writes `<id>.<run>.pruning`; a run with that file is not served, and the next deletion finishes it, so a delete that fails partway never leaves half a run served as whole. A withheld file is never deleted.
- **Recorded before it is handed**: `secret.get` hands a supervised agent a value only after recording it, durably, in the record of every unfinished run of the agent this daemon holds; with no such run, no record, a record that cannot be read now, or a write that fails, it refuses with `log_record_error` (see `secret.get`). So a run's record never says it was handed less than it was.
- **Delivered secrets**: every value the daemon handed the agent (its declared `secrets`, and any value its `secret.get` returned) is replaced with `[redacted]` in every line this method returns, alongside the pattern redaction every tail gets; each line of a multi-line value (a PEM key) that is at least eight characters long is also redacted on its own. While a run's process is alive, its raw files are read and redacted in memory: each file's window is redacted whole before it is split into lines, so a value spanning lines is found; up to 64 KiB before a window that starts partway into the file is read too, so a value the window's start cuts is replaced before the partial first line is dropped; and a raw file that ends partway through a line has the longest end that begins a handed value replaced with `[redacted]`, since the rest of that value may not be written yet. A file at a log's name that is a symbolic link, or that has a second name, is not served. Once the process is gone (`agents.stop`, `agents.restart`, `agents.remove`, a crash or exit, daemon shutdown), the daemon ends the run before it spawns the next one or replies: for each stream it reads the raw file from its first byte, writes it with every handed value replaced to a temporary in the same folder, fsyncs it, renames it to `<id>.<run>.<stream>.log`, a name that does not exist yet, syncs the folder, and only then unlinks the raw file. That `.log` file, the run's redacted log, is what this method and feedback bundles read from then on. Nothing is truncated, and nothing is renamed over an existing file (the rename refuses an existing name), so the end works the same on a local disk and on an SMB/Azure Files state root. Where the file system has no rename that refuses an existing name, the daemon links the temporary to the new name and unlinks the temporary instead, never a plain rename; where it has hard links neither (an SMB mount on macOS), the end fails closed: the raw file stays, served redacted, and the failure is reported as below. The copy stops at the raw file's length when the run's end began, so a writer that never stops cannot hold it open. Because the whole raw file is read in one pass, a value is found however it was split across writes; a copy that ends partway through a line has the longest end that begins a handed value replaced too, since the process may have been stopped mid-write. A process that outlives the agent and still holds a raw file open (a descendant left running, or one that moved to its own process group) writes into a file that no longer has a name: **those late writes, through that open descriptor, are dropped**, and never reach any file this method, a feedback bundle or a later run reads (for a run that is withheld instead, below, they go to its withheld file, which nothing reads). This covers a process writing through a descriptor it already holds. Where agents are not walled into their own folder (Windows, and on macOS every agent but a worker or an orchestrator), a process of the same user that can open the log folder can do anything that user can, including reading a raw file while it runs or linking it to another name; the daemon does not trust a `.log` that is a symbolic link, has a second name or is the raw file itself, and replaces it with a redacted copy, but it does not defend against that user otherwise. A stream that wrote nothing leaves no file. If the redacted log cannot be written or the raw file cannot be unlinked, the raw file stays, this method keeps serving it redacted, the failure is reported in the agent's `status_reason` (`agents.list`) or as `log_scrub_error` in the `agents.remove` result, and the next stop, removal or shutdown tries again; shutdown retries once and waits for every run's end. The daemon keeps every value it delivered, older and rotated ones together, until the agent is removed (when a stopped agent holds more than 256 and no run of it is still open, it releases them all).
- **After a daemon restart**: values are never persisted, so a new daemon recovers the runs earlier daemons left before it spawns or adopts the agent, and at startup for every other registered agent. A stream whose `.log` exists, as a regular file with one name, has its raw file removed. Otherwise, when the agent's declared secrets as resolved now include every value the run's record names, the raw file is redacted into its `.log` as above. Otherwise (a value rotated or removed, a store that cannot answer, a record that is missing or unreadable) the raw file is **withheld**: renamed to `<id>.<run>.<stream>.withheld` (`-<n>` added if that name is taken), never returned here, never put in a feedback bundle, and never deleted automatically. Temporaries such a daemon left are removed. A daemon touches only the runs it began, the ones it recovers this way, and the run of a process it adopts. Recovery treats every run another daemon began as that daemon's leftover, which holds because one daemon at a time owns a state root; two daemons sharing an SMB/Azure Files state root, where that lock does not hold, is a known limit (car#3634). A value `secret.get` hands while a run's end has failed (a process left over from it may still ask) is recorded against that run until its `.log` is written. An adopted process (one still running from an earlier daemon) carries its run on the third line of its pid record. The daemon resolves the agent's declared secrets at adoption: when they include every value the run's record names, the run is its own, served redacted, and ends in its `.log` as above; otherwise nothing of that run is returned while it runs, and it is withheld when it ends.
- **Notes in the tail**: each stream's first page (`offset` 0) can end with lines starting `[car: ` that name what is not shown: the withheld files, a run an earlier daemon left that is not yet recovered, or an adopted run this daemon cannot vouch for. Those lines come on top of `n`, are not counted in `stdout_total`/`stderr_total`, end the stdout part of `lines` (so they can sit in the middle of the combined list), and are what any other reader of this method, such as self-healing detection, also sees.
- **Logs from before per-run files are never published**: the first time a daemon recovers an agent, its `<id>.stdout.log` and `<id>.stderr.log` are withheld, whatever the earlier release's scrub marker (`<CAR_HOME>/agent-log-scrubs/<id>.json`, or a worker's `log-scrub.json`) says and whatever the agent declares: renamed to `<id>.0000000000000-00000000-0.<stream>.withheld`, kept on disk for the operator, never returned here, never copied into a `.log`, never put in a feedback bundle (`car feedback` included). What that release's scrub missed (a value split across writes, a `secret.get` reply, a secret since rotated or no longer declared) cannot be told apart now, so no marker or declaration can vouch for them. So are the copies that release set aside beside them (`.withheld-*`, `.settle`, `.rewrite`); an empty one is removed. The marker is not read, and is removed once they are. A legacy log still held open by an adopted process becomes that run's raw file. At adoption that run is given a record naming one value nobody holds, so the values `secret.get` hands it are recorded (without a record they would be refused), and it is never returned and is withheld when the run ends. One-time effect of the upgrade: an agent's output from before it is not shown here or in feedback bundles; it stays on disk under those names.
- **What can still hold a value on disk**: a raw file while its run is live, the raw file of a run whose end failed, the raw files a daemon that died without a shutdown left until the next daemon recovers them, and withheld files. A value printed in a form a text match cannot find (encoded or transformed) is not redacted anywhere, nor is one the agent itself splits into pieces it prints apart, across lines too short to match alone (a multi-line value's lines are matched alone only from eight characters) or across runs. A symlink at a run's raw name is withheld, never followed.

#### `agents.chat`
- **Params**: `{ agent_id: string, prompt: string, session_id?: string, conversation_id?: string, stream?: boolean = true, voice_input?: boolean = false, shows_agent_drafts?: boolean = false, added_agents?: { id: string, name: string }[], model?: string, attachments?: ImageContentBlock[], goal?: { check: string, max_iterations?: number }, history?: { role: "user" | "assistant", content: string }[], history_omitted?: number, cwd?: string }`.
  - `agent_id` — the flagship assistant's canonical id is `parslee-core`; `car-assistant` (its pre-car#1107 id, still hardcoded by macOS) is accepted as a server-side alias. If the caller sends one spelling and the assistant is attached under the other, the daemon transparently resolves to whichever is actually attached — this only applies to the flagship assistant, not other supervised or declarative agents.
  - `session_id` — host-generated id threaded through every event so one CarHost window with multiple in-flight chats can demux. Auto-generated when omitted. Ids starting with `peer:` are reserved for the built-in assistant's peer conversations, and the built-in assistant refuses a turn under one.
  - `conversation_id` — optional stable id of the host's chat, 1–128 characters of `[A-Za-z0-9._-]` (from a host-management session anything else is refused; from any other caller the value is ignored). An approval for a web search answered **Allow for this conversation** is remembered under it, so it keeps applying when the host starts a fresh `session_id` for the same chat (after an error, a regenerate, a goal change) and across reconnects. Omitted, the session is its own conversation (scoped `session:<session_id>`). Honored only from a host-management session. The person's saved answers apply only to turns the person's host started: a turn another agent starts (or an A2A caller) consults no grant at all — not conversation, agent or all-agents — and its approvals offer plain approve/deny. A `session_id` whose turn another client still holds, or that has a running turn in a different conversation, is refused. The same client sending another turn in the same conversation while its earlier one is still routed replaces that route, which is ended (see `agents.chat.approve`). The daemon forwards the resolved value to the agent's `agent.chat` handler as `conversation_id`.
  - `shows_agent_drafts` — set by a host that shows the draft card a `propose_agent` call becomes (the macOS app). The daemon forwards it to the agent as `context.shows_agent_drafts`; the built-in assistant offers `propose_agent`, its prompt line and its turn-ending reply only on such turns, read turn by turn (the prompt line leaves the conversation's system prompt on a turn without it), and refuses a call to it on any other turn with a plain `ok: false` result that lets the turn go on. Absent or `false` is not forwarded.
  - `added_agents` — the agents the person added from this chat's draft cards, oldest first, each `{ id, name }` (the macOS app sends them on every turn to the built-in assistant). Honored only from a host-management session and only on a turn with `shows_agent_drafts: true`; from any other caller, or without the flag, it is ignored unread, never an error. The daemon forwards it to the agent as `context.added_agents`. It reads only the newest 64 entries, and keeps those whose `id` is one CAR can register (1–128 characters of `[A-Za-z0-9._-]`, not starting with `.` or `-`, without `..`) and whose `name` is 1–80 bytes, each id once (its latest entry), only the newest 20, and only agents its registry still holds, under the name each has there now. An agent removed since is never forwarded, and a registry that cannot be read forwards none. The built-in assistant names them, with their ids, in that turn's thread, so a request to change one is proposed as an edit of it (`propose_agent` with `existing_agent_id`); and a new-agent draft whose name (as CAR turns a name into an agent id) is one of theirs shows nothing and comes back with `ok: false`, the agent's id and a next step to propose the change as an edit, or to ask for a name of its own if the person wants a separate agent.
  - `model` — optional explicit CAR model ID for this turn. A non-empty value is a strict selection and reaches inference unchanged; CAR reports that model's failure rather than silently substituting another model. Omit it (or pass a blank string) to preserve the supervised agent's configured model and adaptive fallback policy.
  - `attachments` — optional array of image `ContentBlock`s the user attached: `{ "type": "image_base64", "data": "<b64>", "media_type": "image/png" }` or `{ "type": "image_url", "url": "https://…", "detail": "auto" }`. The daemon validates each entry's shape and content — `image_base64` must carry a string `data` and a `media_type` in `{image/png, image/jpeg, image/gif, image/webp}`; `image_url` must be http(s) — rejecting a malformed entry with a JSON-RPC error, then forwards the array verbatim to the agent's reverse-called `agent.chat` handler, which passes it to inference as `imagesJson`. Omitted when the turn has no images, so agents that don't read it see the legacy request shape. The daemon does **not** check provider vision capability; an agent or provider that can't accept images surfaces that error downstream.
  - `history` — optional earlier turns of the host's chat, oldest first, each `{ role: "user" | "assistant", content: string }`. Any host connection may send them (CarHost is the first to do so) with the first turn of a new `session_id` for a chat that already has turns, so the agent still has the conversation; the macOS app does after a Stop, an error, a Regenerate, an edit-and-resend, a goal change, or a turn to another agent, and a host that starts a new session for every turn may send them every turn. `history_omitted` is how many older messages the host left out before sending. An entry with any other role or without a string `content` is refused with a JSON-RPC error, and so is a `history_omitted` that is not a non-negative integer, with or without `history`; a valid `history_omitted` without `history` is ignored. Entries with blank content are skipped. Only the newest messages within 200 messages and 256 KiB of `content` are kept, and the daemon forwards them to the agent's `agent.chat` handler as `history`, with `history_omitted` the host's count plus the older ones the daemon left out (absent when both are zero). Both fields are honored only from a host-management session; from any other caller they are ignored without being read (never an error), since they would put words in the agent's mouth as its own earlier answers. The built-in assistant seeds a session that has no thread yet (no cached thread and no durable checkpoint) from them, as a thread that alternates and ends on an answer: consecutive messages of one role are joined, a leading answer whose question was left out is dropped, and a last question that got no answer is closed with the answer `(no answer was given)`. It says how many older messages the host and daemon left out, and fits the thread to the model's context window with the same compaction every turn gets; a session that already has a thread ignores them. Declarative agents run each turn on its own and ignore it.
  - `goal` — optional deterministic completion contract for this chat turn. `check` is a shell command the agent runtime runs after each assistant iteration; exit 0 means the condition is met. `max_iterations` defaults to 8 and is clamped to 1–50. Goal-driven agents stream `goal_evaluated { iteration, met, grounded, reason }` after each verifier pass and emit terminal `done` once the deterministic check passes (`met` with `grounded: true`). The flagship assistant still cross-checks conservative final-summary operational claims such as "tests passed" against same-run tool receipts, but once the deterministic check has itself passed an unmatched claim only **adds a non-authoritative warning** (a `[claim check]` note appended to the plain `done` message, or emitted as a separate Text event beside unchanged formatted JSON) — it no longer re-opens a deterministically-verified iteration on prose wording, and `grounded` stays `true`. A summary claim can still keep a completion ungrounded when the met verdict rested on a model judge rather than deterministic ground truth (it fails closed and keeps iterating). If the governor halts on a condition that actually ran and was not met (turn/cost/wall-clock budget, no-progress, cancel), the terminal event is `error`, naming the halt reason. If the check itself never got to run within its own bound — a stuck approval wait, a wedged subprocess — the loop fails open instead of hanging or discarding a working reply: it halts on the *first* such stall (it does not burn the rest of `max_iterations` retrying a check that structurally cannot be evaluated), and the terminal event is still `done`, with the reply text carrying a `[goal check] not verified — …` note (mirroring the `[claim check]` annotation convention above), `finish_reason` set to a short "unevaluated" string, and `goal_unevaluated: true` — a machine-readable marker `goal.status`'s persistence layer reads to record `status: "unevaluated"` rather than `"met"`, so a client polling `chatGoal.status`/`goal.status` cannot misread an unchecked condition as a verified pass. Currently mutually exclusive with `attachments`.
  - If no inline `goal` is passed, the daemon looks for a standing goal stored for the same `session_id` via `goal.set` and forwards that contract to the agent.
  - `cwd` — optional absolute path of the folder the host's conversation works in (same name as `agents.invoke_external`'s `cwd`). Honored only from a host-management session; from any other caller it is ignored unread, never an error. From the host, a relative path or a non-string is refused, and a blank one is no folder. The daemon forwards it to the agent's `agent.chat` handler as `cwd`. The built-in assistant runs that turn's relative paths in it on the local host: a relative `write_file`, `edit_file`, `read_file`, `list_dir`, `find_files` or `grep_files` path, the `shell` working directory, and the relative output or input path of `generate_image`, `generate_speech`, the Studio media tools, the image-reading tools and `browser_record_stop`. Those host-side writers then report the output by its absolute path (`image_path`, `audio_path`, `path`), as `write_file` does. The turn's thread carries one line telling the model this conversation's folder, in place of the working directory its instructions name. The folder is made the first time a write or `shell` needs it, so a turn that writes nothing creates nothing: before then `list_dir`, `find_files` and `grep_files` without a `path` return an empty result, and a `shell` whose folder cannot be made runs at the agent's root with a `working_folder_note` in its result saying so. It never widens what a tool may touch: an absolute path is checked exactly as before, a folder outside the agent's working root is not used, approvals are unchanged, and in a Docker sandbox it is ignored (the container holds no host folder). A turn without `cwd` resolves against the agent's own working directory, as before. CarHost sends it on every Parslee Core turn: the conversation's own folder, or else its default `~/Documents/Parslee/<conversation name>`, chosen at its first such turn and kept with the conversation.
- **Unknown agent.** An `agent_id` that is neither attached nor a declarative agent is refused with "`<id>` is not attached to this daemon and is not a declarative agent". When `declagents.json` exists but cannot be read, the declarative half cannot be checked, so the refusal is "agent `<id>` is not attached to this daemon — supervisor may have it stopped, or it hasn't called session.auth yet; declarative agents could not be checked: <registry error>".
- **Returns**: an ack `{ accepted: true, session_id: string, turn_id?: string }`. `turn_id` is the daemon's id for this turn, present for an attached supervised agent's turn; it is also sent to the agent with `agent.chat`, and the frames of an agent that echoes it carry it on every `agents.chat.event` of the turn, so a host can tell this turn's frames from a replaced turn's under the same `session_id`. The reply does **not** carry the answer — for attached supervised agents, the daemon reverse-calls the agent's `agent.chat` handler and fans the streamed reply back as `agents.chat.event` notifications (`kind: "inference_started" | "inference_retry" | "model_served" | "token" | "tool_call" | "tool_result" | "todos" | "approval_pending" | "approval_resolved" | "goal_evaluated" | "receipt_report" | "done" | "error" | "auth_required"`) keyed by `session_id`. `inference_started { model, attempt, turn, waiting_ms? }` is emitted before each model call is awaited, and repeated every 60 s while that call is still awaited, with `waiting_ms` (how long it has waited) present only on the repeats; `inference_retry { model, attempt, reason, backoff_ms }` is emitted before a transient remote retry's backoff, with a generic reason that never copies the provider body. `model_served` precedes each completed turn's content and carries `{ model_id, local_last_resort, substituted_from?, substitution_reason? }`, where the boolean is true only when the appended on-device last resort actually served; on such a turn `substituted_from` names the model the request named and `substitution_reason` (`credential_rejected` | `credential_absent` | `rate_limited` | `quota_exhausted` | `timed_out` | `failed`) says why it did not serve. Both are absent on an ordinary turn. The last resort is only ever a model installed through CAR. Each requested tool emits `tool_call { call_id, sequence, tool, params }` and exactly one matching `tool_result { call_id, sequence, tool, ok, excerpt, evidence }` before later assistant text; `call_id` is generated by CAR as `turn_<n>_call_<sequence>` because provider ids may repeat, and `sequence` is the call's one-based position in that turn. `n` counts every assistant turn the session has had, including turns history compaction has since removed, so an id is never reused within a session. A receipt merged up from a `delegate` child is namespaced `<parent call id>/<child call id>`: the child loop numbers its own turns from one and would otherwise collide with the parent's first call. A dispatch error or cancellation still closes the request with `ok: false`. `excerpt` is feedback-redaction-scrubbed and bounded to the first 2,048 UTF-8 bytes plus an explicit truncation marker; structured header maps drop every non-allowlisted header (including Authorization/Cookie), and URL userinfo plus credential query values are removed. Evidence is extracted from the complete observation before the model-facing cap can invalidate large JSON. It is a closed-world object containing only applicable identifiers/destinations/status/title/count fields (`requested_url`, `final_url`, `redirected`, `url`, `status`, `title`, `event_id`, `message_id`, `id`, `count`, `total`, `path`, `edited`, `image_path`, `audio_path`, `event_count`, `event_ids`, `message_count`, `message_ids`, `result_count`, `result_ids`); `redirected` is present when requested and final URLs are both known. Evidence strings are capped at 512 bytes and id lists at 20 items. `path` (written by `write_file`), `edited` (changed by `edit_file`), `image_path` and `audio_path` name what the tool produced, so a host can list a turn's outputs without parsing the excerpt. After a successful `todo_write`, the flagship assistant emits `todos { items: [{ id, text, status }] }` with the conversation's WHOLE task list (`status` is `"open" | "done" | "dropped"`; `dropped` means deliberately abandoned, never completed); the latest event is the state, so a host that missed one needs no replay. A rejected write emits nothing. Task lists are per conversation and persist in the conversation's durable checkpoint, and a conversation reopened after a daemon restart emits its restored list as the first event of its next turn. `receipt_report` is emitted immediately before the terminal frame and is capped at 64 KiB as a complete serialized frame. It carries the bounded software `completion` matrix, `desktop_actions: [{ action, target?, identifier?, verified, evidence }]` plus `desktop_actions_omitted`, and bounded `tool_receipts: [{ tool, call_id?, sequence?, ok, via?, excerpt, evidence }]` plus `tool_receipts_omitted`. Both lists and the `completion` matrix cover **only the turn that just ran** (on a goal turn, every iteration of the goal run, keeping the latest rows when a list is over its cap) — a continuity turn's earlier evidence still grounds the summary but is not republished as work the person just watched, and a stage recorded on an earlier turn is not reported again. A `completion` stage's evidence string carries the turn's `call_id` and the call's redacted excerpt, bounded to 2,048 bytes overall; a call whose output reports a non-null `error` records no stage. A read action is verified when it succeeded and produced evidence, judged from the tool's own result fields: a result reporting `"ok": false`, `"success": false`, a non-null `error`, `"met": false` (`browse_wait`), `"settled": false` (`browser_await_answer`) or `"timed_out": true` is never verified; a `web_search` is verified only when it returned results or an abstract; and an `http_request` GET is verified only when its final response was 2xx other than 204/205 with a non-empty body or with `binary: true` (binary content that was not inlined), never with `undecodable: true`. A write is verified only when a later verified read receipt contains the same object identifier (`event_id`, `message_id`, `id`, or one of the id lists), otherwise it remains attempted; an `http_request` never confirms a write by URL, so a `GET` of the URL a write targeted does not verify it, while a browser read whose page URL (`url`, `final_url` or `requested_url`) is the page a browser write (`browse_navigate`, `browser_await_signin`) targeted still does, ignoring a lone trailing `/` on the path that the browser adds or drops. Whether an action counts as a write is read from the advertised tool definition's own `mutating` flag, not from its name, so a tool added later is classified without a protocol change; `http_request` is declared mutating because it can send other methods, and only a GET (its default) is scored as a read. Hosts list the recorded software stages beside `desktop_actions` (a turn can carry both) and show `desktop_actions_omitted` as a count of actions the list leaves out, so its verified count covers only the listed rows; missing matrix evidence remains absent rather than inferred. `approval_pending { approval_id, call_id?, tool, params, session_id, deadline, action_id?, scope? }` parks the turn on the person. The built-in assistant's approvals carry `call_id`. For a gated tool call it is the id that call's `tool_call` carries, so a host can tie the approval to that call. A goal check's approval, and one for a call inside a delegated child, carry an id no `tool_call` event names. An answer can be remembered only for a web search (`web_search`) by the built-in assistant, and an approval for one carries, all together, `permission_kind` (always `browse_web`; set by the runtime, never by the model), `purpose` (one fixed sentence, "CAR needs to search the web to continue this task."; it takes nothing from the call) and `choices` (exactly `[{answer: "allow_conversation"}, {answer: "allow_agent"}, {answer: "allow_all_agents"}, {answer: "deny"}]` in that order, each with a `label`) — answer through `agents.chat.approve` — but only when nothing forces a plain card: a web search approval carries none of the three when an exact `require_approval` override is set on `web_search`, when `agent-permissions.json` is damaged or has gone missing under the running agent, in a governed run, and in a turn another agent or an A2A caller started. Every other approval carries none of the three, an `http_request` in any shape included, so hosts show plain approve/deny for it; the daemon removes the three fields from an `approval_pending` it forwards for any agent other than the built-in assistant. A web search a saved answer covers runs without any `approval_pending`, and a call a saved standing refusal covers is refused without asking. `approval_resolved { approval_id, resolution: "approve" | "deny" | "timeout" | "cancelled" }` (`"cancelled"` is what an agent emits after a Stop; the daemon closes the ledger row itself) is the authoritative terminal transition for an `approval_pending` gate: hosts clear the inline card and the mirrored ledger row on this frame rather than optimistically on their own request, so a resolve that never reached the parked turn cannot look successful. `auth_required { reason, message }` is a THIRD terminal frame alongside `done` and `error`: it arrives after `receipt_report`, is never followed by `done` or `error`, and means the turn could not reach Parslee inference because of the account — `reason` is `"signed_out" | "expired" | "no_workspace"` (branch on it; `message` is written for a person to read). The out-of-the-box agent runs on Parslee inference through a Parslee account, so a host should render this as a sign-in prompt rather than an error row; a turn that names an explicit `model` is unaffected and still reports that model's own failure. The built-in assistant's `error` terminal also carries `state: "not_done"` and a `cause` from `docs/contracts/ootb-turn-outcome.md`: `approval_denied` (a person, or a standing answer they saved, did not allow an action the turn tried), `needed_approval` (nobody could be asked, or the request timed out), `action_failed` (an action could not run, or another non-inference failure), or `unreachable` (inference retries ran out). Branch on `cause`, not `error`; for the first three, `error` is the assistant's answer followed by a plain line saying the request did not finish. A later successful call with the same arguments clears a refused action; any later successful call of the same tool clears a failed one. For in-daemon declarative agents, no child process or reverse call is needed: the daemon runs the declarative runner directly and emits the same event stream. `stream: false` still returns via the same event channel as a single terminal frame. Refused with `the turn was cancelled before it started` when this connection sent `agents.chat.cancel` for the same `session_id` within the previous 60 s and no turn was routed (see `agents.chat.cancel`).
- **Task scoping on authenticated A2A surfaces.** `tasks/list` returns only the caller's own tasks; `tasks/get` and `tasks/cancel` answer `TaskNotFound` for a task created by a different verified caller (rather than confirming it exists); and a `message/send` whose `taskId` names another caller's task is refused instead of appending to their history. Tasks created on a surface with no caller identity are un-owned and stay visible to everyone, so unauthenticated embedder deployments are unchanged.
- **Admission (agent callers only).** When the caller is an *agent* rather than
  the host, this method now passes the same admission `agents.message` applies:
  the per-recipient channel guard (identical-body dedupe inside 10s, 20 sends
  per sender per minute — one shared budget per recipient across both methods)
  and the `AgentPermissionPolicy` decision at the `read_only` tier. An agent set
  to `Deny` is refused; one set to `RequireApproval` is refused too, with a
  pointer to `agents.message`, because chat is request/response and has no hold
  queue. **The host is exempt** — it is the operator's own client, and the dedupe
  window would otherwise swallow a person retyping the same prompt. Before this,
  `agents.chat` was the way around `agents.message`'s admission: a denied agent
  could reach another agent by chatting at it, and two agents could answer each
  other with nothing to terminate the loop.

  Two failure modes follow from that and are worth anticipating: an `agent_id`
  outside `[A-Za-z0-9._-]` (or over 128 chars) is refused as an invalid peer
  name, and a refusal names the guard rule that stopped it. Admission runs
  *after* the target is confirmed to exist, so an unroutable id is refused for
  that reason and does not consume the caller's dedupe or rate budget. A
  synchronous turn does not occupy the in-flight `QUEUE_CAP` slot that
  `agents.message` takes, so the two methods cannot exhaust each other on that
  axis; they do share the dedupe window and the rate budget, which is the point.
  Every refusal is written to `~/.car/peer-messages.jsonl` with its outcome.
- Host-side method is WS-only (no FFI binding — a host like CarHost calls it directly). The **agent side** has FFI helpers (below). See [`docs/proposals/agent-chat-surface.md`](.././proposals/agent-chat-surface.md) for the full host↔daemon↔agent flow.

#### `goal.suggest`
- **Params**: `{ prompt?: string, objective?: string, working_dir?: string, cwd?: string, session_id?: string, set?: boolean }`.
  - Produces an explainable deterministic completion-check candidate for a vague goal. `prompt` and `objective` are aliases; one is required.
  - `working_dir`/`cwd` is optional. When it points at a project directory, the daemon checks for `Cargo.toml`, `package.json`, `pyproject.toml`/`setup.py`, `go.mod`, `Package.swift`, `CMakeLists.txt`, `build.gradle(.kts)`, `pom.xml`, `.sln`/`.csproj`, `composer.json`, `Gemfile`, `mix.exs`, or a `Makefile` `test` target. If a prompt names a relative file or directory path inside a recognized project, including a nested project below `working_dir`, it uses the nearest project verifier. For create/write prompts, it also combines file existence with that verifier (for example `test -f src/lib.rs && cargo test -q`) instead of treating file creation alone as success. Outside a recognized project, a named path can still produce a file-existence check.
  - The method is conservative: when no deterministic signal is present, it returns `suggested: false` rather than inventing a weak completion check.
  - With `set: true`, `session_id` is required and a successful suggestion is stored exactly like `goal.set`.
  - Foreground `car do "<objective>" --infer-until` uses the same synthesis logic, prints the selected check/rationale, then enters deterministic `--until` goal mode.
- **Returns**: `{ suggested: boolean, goal: { check, max_iterations } | null, confidence: "high" | "medium" | "none", rationale: string, signals: string[], warnings: string[], set?: true, session_id?: string, stored_goal?: ChatGoalState }`.

#### `goal.set`
- **Params**: `{ session_id: string, goal?: { check: string, max_iterations?: number }, check?: string, max_iterations?: number }`.
  - Stores a durable deterministic completion contract for a chat `session_id`. `goal` is the preferred shape; top-level `check` / `max_iterations` are accepted as a convenience.
  - `check` is trimmed and must be non-empty. `max_iterations` defaults to 8 and is clamped to 1–50.
  - The daemon atomically rewrites the registry at `~/.car/chat-goals.json`, derived as a sibling of the configured journal directory.
  - **Ownership.** Only *bound* connections are restricted: a supervised agent's connection, authenticated with an `agent_id` and without the host role. A goal such a connection stores — through `goal.set`, `goal.suggest { set: true }`, or an inline `agents.chat` `goal` — records that agent in `owner_agent`. It may create a goal on a session id that has none, and replace or clear only goals it stored itself; a goal stored by the host, by an unbound client, or by another agent is refused with ``"`<method>`: session `<session_id>` has a goal held by another owner (an agent or the host)"`` where `<method>` is `goal.set`, `goal.suggest`, `goal.clear` (with a `session_id`) or `agents.chat`. The host and every unbound connection (CLI, SDK and mobile clients on the daemon token), with or without a host token configured, may replace or clear any goal, and their replacement takes ownership. A goal an agent stored steers only that agent's own `agents.chat` turns: a turn from anyone else on the same `session_id` ignores it, `goal.status` for that session reports it to them as `null`, and an inline `goal` from the host replaces it. A turn's events (`goal_evaluated` and the terminal kinds) update a goal only when the turn's driver owns it — the host or an unbound client for a goal with no `owner_agent`, the agent itself for its own — so an agent's turn on a host-owned session with no inline `goal` runs the host's goal without recording against it, while the same turn with an inline `goal` is refused (it would replace the host's goal for that turn). The driver is fixed when the turn starts, so a late frame from a replaced turn is not credited to the turn that replaced it. Goals stored before this rule carry no `owner_agent` and belong to the host.
- **Returns**: `{ set: true, goal: ChatGoalState }`.

#### `goal.status`
- **Params**: `{ session_id?: string }`.
  - With `session_id`, returns `{ session_id, goal: ChatGoalState | null }`. The goal is the one that would steer the caller's own turn on that session, so a goal another agent stored there is reported as `null` (see `goal.set` ownership).
  - Without `session_id`, returns `{ goals: ChatGoalState[] }`: every goal for the host or an unbound client, including `owner_agent` when the goal is agent-owned (the field is omitted otherwise); only the goals it may use for a bound agent.
  - `ChatGoalState` carries `{ session_id, owner_agent?, check, max_iterations, status, last_iteration?, last_met?, last_grounded?, last_reason?, terminal_kind?, terminal_message?, updated_at }`. `status` is one of `"active"` (set, not yet run), `"running"`, `"met"`, `"unevaluated"` (a `done` whose goal check never got the chance to run — see the fail-open case under `agents.chat`'s `goal` param above; `terminal_message` carries `finish_reason` for human-readable detail), or `"error"` (a check that ran and genuinely failed, a governor halt, or a turn refused on the Parslee account). It is updated from forwarded `goal_evaluated` events and from the three TERMINAL chat kinds — `done`, `error` and `auth_required` — and persisted. `auth_required` records `terminal_kind: "auth_required"` and carries its `message` in `terminal_message`, and it maps to `status: "error"` exactly as an `error` terminal does: the condition was not met and the run is over, so a poller reads `terminal_kind` when it needs to tell an account problem from a failed check. Ordering is the same as for the other two — it arrives after `receipt_report` and nothing follows it — so a poller that sees it has the last word it is going to get. On daemon restart, a stale persisted `running` status is reloaded as `active` while verifier details are preserved.

#### `goal.clear`
- **Params**: `{ session_id?: string }`.
  - With `session_id`, removes one standing goal and returns `{ cleared: boolean, session_id }`.
  - Without `session_id`, removes all standing goals the caller may clear and returns `{ cleared: number }`: every goal for the host or an unbound client, only its own for a supervised agent. A supervised agent clearing another caller's goal by `session_id` is refused (see `goal.set` ownership).

#### `agent.chat` (daemon → agent reverse-call) + `agent.chat.event`
- For attached supervised agents, `agents.chat` reverse-calls **`agent.chat`** on the target agent's WS connection — resolved via `attached_agents`, so the agent must have `session.auth`'d **with its `agent_id`** (`{ session_id, prompt, turn_id, model?, attachments?, goal?, context?, cwd? }`). The optional `model` is forwarded unchanged from the host request. The agent **acks** `{ accepted: true }` immediately, then streams its reply as **`agent.chat.event`** notifications `{ session_id, turn_id?, kind, delta? }` (`kind: "inference_started" | "inference_retry" | "model_served" | "token" | "tool_call" | "tool_result" | "todos" | "approval_pending" | "approval_resolved" | "goal_evaluated" | "receipt_report" | "done" | "error" | "auth_required"`), which the daemon rewrites to `agents.chat.event` for the host. `turn_id` is the daemon's id for the turn; an agent that echoes it on every frame (`car do --serve` does) has its frames matched to that turn: a frame naming another turn's id (a turn the host's next `agents.chat` on the same `session_id` replaced, or one that has ended) is dropped, so a replaced turn's late terminal cannot end its successor. Its approval frames are the exception: the replaced turn keeps running, so a card it raises after it was replaced reaches the host, which can answer it, and the turn's `approval_resolved` for that card reaches the host too; a card it raised before was closed with its route, and its late `approval_resolved` is consumed against the carried card, as described under `agents.chat.approve`. A host may receive frames before the `agents.chat` reply that carries `turn_id`, so it should use `turn_id` to correlate frames with a turn, never as a gate. A frame without `turn_id` is matched by `session_id` alone, as before. `inference_started { model, attempt, turn, waiting_ms? }` arrives before CAR awaits a model call, and again every 60 s while the call is still awaited, with `waiting_ms` saying how long, so a host's idle watchdog keeps seeing a slow call; and `inference_retry { model, attempt, reason, backoff_ms }` arrives before remote retry backoff. `model_served` carries `{ model_id, local_last_resort, substituted_from?, substitution_reason? }` before each completed turn's content, so a host can identify the actual serving model, mark an on-device last-resort turn, and say which model it replaced and why. `tool_result` carries the bounded/redacted observation shape documented above. `goal_evaluated` is emitted by goal-driven agents after each verifier pass as `{ iteration, met, grounded, reason }`; `receipt_report` carries bounded per-tool receipts, desktop actions when present, and the software completion matrix. `auth_required { reason, message }` replaces the `done`/`error` frame when the turn could not reach Parslee inference because of the account: it follows `receipt_report`, nothing follows it, and on the goal path the loop returns before the verifier runs, so no `goal_evaluated` is emitted for that iteration. `agents.chat.cancel` proxies to `agent.chat.cancel` (a request to the bundled assistant, whose `dispatched` answer it relays; a notification to any other agent), with params `{ session_id, turn_id? }`: `turn_id` names the daemon's id for the turn being stopped whenever its route had one. An agent that retains its ordering entry stops that turn and every older turn of the session, never a newer one the host started after it; with no `turn_id` it stops every turn of the session. An agent says it does so by acknowledging `agent.chat` with `{ accepted: true, stops_by_turn_id: true }`, recorded for its connection from that first acknowledgement; `car do --serve` and the Python chat bridge declare it (the Node bridge does not: a JavaScript handler may still be running an older turn when a newer one starts, and its Stop would reach both); `agents.chat.approve` reverse-*requests* `agent.chat.approve` (resolving an `approval_pending` gate so the turn resumes). In-daemon declarative agents skip the reverse call and stream `token`/`goal_evaluated`/terminal frames directly; cancel flips a local run flag and halts at the next model/tool/goal-check boundary; inline `agents.chat.goal` and image attachments are rejected for them because their own manifest `goal` and scratch-worktree runner own completion.
- **Bounded Stop history:** Bundled receivers retain up to 1,024 named ordering entries across sessions: per built-in assistant service, per Node process-wide chat queue, and per Python client queue. An absent, unseen or evicted identity uses the legacy session-wide Stop and can affect newer current turns. A bridge drops only that runtime owner's queued session turns and permits its own cancellation handler to receive that Stop; it does not itself terminate arbitrary handler code. See `agent.chat.cancel` in `docs/host-protocol.md`.
- **FFI (agent side):** `registerChatHandler(handlerFn)` / `register_chat_handler(handler)` installs the handler (stored-callback pattern; the per-`CarRuntime` bridge acks and fires it with the params JSON). `CarRuntime.chatEvent(sessionId, kind, delta?)` / `chat_event(...)` emits each `agent.chat.event`; `chatTurnEvent(sessionId, turnId, kind, delta?)` / `chat_turn_event(session_id, turn_id, kind, delta=None)` emits it naming the turn. The params JSON the handler receives carries the turn's `turn_id`; pass it to `chatTurnEvent` / `chat_turn_event` so the frames are matched to that turn. **The handler may call any runtime method and should run the turn inline** — in Python it is dispatched on a dedicated CAR-owned OS thread, never a tokio worker, so `infer_tracked`, `submit_proposal`, `state_set`, and `chat_event` all work from inside it. Before car#905 the Python bridge dispatched on a runtime worker and every one of those raised `PanicException: Cannot start a runtime from within a runtime`; because that is a `BaseException` and `chat_event` hit the same wall, the accepted turn was stranded with the host receiving zero frames. Any `threading.Thread` offload written to work around that is now unnecessary. NAPI was never affected (async `ThreadsafeFunction` dispatch). The same contract covers the `tools.execute`, `tools.cancel`, and `voice.event` callbacks. A `--serve` agent **attaches automatically**: the binding sends `agent_id` on `session.auth` when `CAR_AGENT_ID` + `CAR_AGENT_TOKEN` are set (the supervisor injects them). The bundled `create-car-agent` harness wires all of this in `--serve`, keeping an ephemeral per-`session_id` message thread and running the standard propose→verify→execute loop per turn.
- Bundled `car do` / `car do --serve` assistant loops run proactive memory before every model turn. The hidden pass maintains compact execution-state memory from the runtime event log, selects at most one relevant remembered fact/procedural warning, and injects it as a `## Proactive Memory` context block. This uses the same assistant memory bank as `remember` / `recall`, but does not require the model to call `recall`; maintenance/intervention decisions are journaled as `proactive_memory_maintained` and `proactive_memory_intervention`. Memory derived from a chat's own runtime events (a failed tool call, a retry, a capped turn) is kept to that chat: it is never injected into another chat, and within its chat it is injected at most once per turn (a goal turn's iterations and a delegated sub-task included) rather than on every model call of the turn. The assistant's `recall` answers only from remembered facts, never from this derived memory.
- Native coder loops also run proactive memory over the shared repair memgine when learning is enabled. The pass mines the coder session journal into procedural/open-subgoal facts, injects at most one `## Proactive Memory` context block before the next coding turn, and journals the same proactive-memory events into the coder session event log. Memory mined from one coder session's journal is injected only into that session, at most once per run, although the repair memgine is shared and saved across restarts.

#### `agents.peers`
- **Params**: `{ organization_directory?: boolean }`.
- With `organization_directory: true`, the reply also carries `organization_directory`: the colleague directory of the organization this connection is bound to, in the single-org `lattice.directory` shape (`{ org, count, members, org_stream, relay }`) with each device's `connection` left out, since those are the operator's own Lattice connection ids and labels. The org always comes from the connection's own binding; nothing names one. It is read only from what this CAR already holds and never fetches the relay directory (the relay's six-a-minute directory budget is the operator's), so before the operator's first directory read `relay` is `{ error, dormant: true }`. A connection with no organization, or an org this CAR holds no directory for, gets `{ error }` (with `org` in the second case) in that field instead of a failed call.
- Lists the peers visible to this caller. Use each row's `reachable` field before offering a send.
- **Returns**: `{ self: string | null, peers: [{ name, address, reference, kind, source, can_receive, reachable, display_name, capability, last_seen_ms }], count: number }`.
  - `self` is the caller's own name — the address other agents use to reach it. The caller is **never** among `peers`; addressing yourself is an error, not a loopback.
  - `address` is the form to pass as `agents.message`'s `to`. It is the bare `name` unless two live peers share that name, in which case it is `name [reference]`. References are assigned only where a name is genuinely ambiguous, so ordinary addresses stay readable.
  - `kind` is `car_agent`, `external_cli`, or `remote_car`; `can_receive` is the stable capability of that kind and is false for `external_cli`. CAR runs external CLIs as batch processes (the task goes in on stdin, which is closed immediately so the child sees EOF), so they can message CAR while running but have no inbox to deliver into.
  - `reachable` is the daemon's point-in-time delivery preflight over the same two descriptor guards `agents.message` applies: the kind must have an inbox (`can_receive`) and the emitted `source` must be trusted by default. It is false for an unpromoted `lan` peer even though that remote-CAR kind has `can_receive: true`. It is a snapshot, not a delivery guarantee: the send remains authoritative because sender policy, standing, message limits, recipient attachment, and remote liveness are evaluated later.
  - `source` is `attached`, `invocation`, `parslee`, or `lan`. Local peers come from the daemon's **live connection table**, not the on-disk agent registry — the registry is observe-only self-report whose reap sweep tolerates a 900s stale window, so a listing built from it would offer agents that exited a quarter of an hour ago.
  - **Cross-host discovery** has two independent routes, complementary rather than redundant:
    - `parslee` — this user's other machines, each announcing its A2A endpoint on the **synced oplog** (`Registry { kind: "host_endpoint" }`, folding LWW per device id so a machine that moves overwrites its own entry). The oplog is end-to-end encrypted, so Parslee relays the bytes without being able to read the endpoints. This is why discovery rides the oplog instead of an address field on the sync roster: the roster would publish a per-device address to the service. Covers every signed-in login, not only the one present at daemon start: each other login's endpoints ride its own personal oplog (opened on `sync.pump`; daemon boot stays credential-free, so this host's announcement is remembered at boot and published as each subsystem opens), and a machine signed in to several of your logins is listed once. Devices under any held login are trusted too: trust rests on a login signed in here plus the shared sync passphrase, so signing in a login that is not yours extends trust to its devices. Removing a login (`auth.remove_account`) or signing out (`auth.logout`) through the daemon withdraws its devices' trust immediately, the boot login's included; a change made through the in-process CLI is noticed within 30 s from the non-secret credential-authority hint and drops other logins' trust until the next `sync.pump`. If the hint's generation could not be published, the change is picked up by the five-minute fallback listing on `sync.pump`, provided that listing succeeds. Requires a login; empty without one.
    - `lan` — CAR daemons advertising `_car-a2a._tcp.local.` over mDNS. Needs no login but reaches only one broadcast domain; point-to-point tunnel interfaces (macOS `utun*`, Linux `tun*`/`wg*`, and the like) are skipped, since a tunnel cannot deliver link-local mDNS to peers on the local network. The peer-reachable URL travels in a TXT record rather than being rebuilt from the resolved IP and port, because an operator can pass `--a2a-public-url` to declare a URL that differs from the bound socket.
  - **A `lan` peer is listed with `can_receive: true` and `reachable: false`.** Anyone on a network can advertise any name, so discovery makes a peer *visible*, not reachable; `agents.message` refuses it with an error naming the remedy until an operator promotes it via `a2a.peers.add`. A promoted peer is reported under its trusted source instead, so it is not double-listed. Name collisions resolve toward the more *trusted* source, not the nearest one — a `parslee` device outranks a `lan` advertisement even though the LAN is the shorter path.
  - Cross-host delivery addresses the remote **daemon's** A2A surface, never one of its agents. That daemon applies its own guard and policy before reverse-calling a local agent, so a cross-host message passes two admissions — the sender's and the recipient's — and neither can be skipped. `PeerAddress` deliberately has no variant naming a remote agent.

#### `agents.message`
- **Params**: `{ to: string, body: string, summary?: string, kind?: string, in_reply_to?: string, on_behalf_of?: string }`.
  - `to` is an `address` from `agents.peers`, or `human:<name>` for a human Lattice node. An attached agent's principal form `agent:<id>` — what its messages carry in `from` — resolves to that agent, so a reply can copy `from` verbatim. `body` is plain text.
  - `kind` says what the sender is asking for: `message` (default), `question`, `answer`, `review_request`, or `handoff`. It is a field rather than a body convention so a recipient can sort its inbox without parsing prose. It is advisory: every kind passes the same guard, policy, and audit, and a `review_request` or `handoff` grants the recipient nothing. A plain message omits `kind` from the stored envelope, so recipients that predate the field see the same envelope as before.
  - `in_reply_to` is the `id` of the message being answered, so an asker can match an answer to its question. The daemon checks its shape only — it is a correlation hint, not proof that a conversation happened. The reply path for a question is an `agents.message` back to the received `from` with `kind: "answer"` and `in_reply_to` set to the question's `id`.
  - `summary` is a label for the **sender's** own transcript; it is not transmitted.
  - `on_behalf_of` is for a **human delegate** (`delegate_for`, car-releases#109) forwarding a question to the person it fronts: the `id` of a message the daemon delivered to the delegate, with `to: "human:<name>"`. The request is recorded as asked by that message's sender, over the connection it arrived on, with that message's own body, kind and `in_reply_to` (the forward's `kind` and `in_reply_to` are not used), `forwarded_by: "delegate:<agent id>"`, `forwarded_from: <that id>`, and the forward's `body` as `forward_note`; the 10-pending cap is the asker's, and the answer goes to the asker directly with `in_reply_to` set to the asker's own message id, so the delegate does not relay it and the asker waits on the id it already has. The result is `{ id, to, outcome: "awaiting_human", request_id, on_behalf_of: <asker>, forwarded_from }` without an `answer_token`, which stays the asker's. Each delivered message can be forwarded once, and the daemon remembers the latest 256 per delegate. Refusals carry `-32020` with `error.data.reason` `not_a_delegate`, `not_delegate_for_human`, `forward_not_found` or `forward_not_a_question` (an answer, or a message from a person on this CAR); a forward the delegate's posture would hold is refused rather than held.
  - There is no `from`. The daemon derives the sender from the connection's bound `agent_id` (the same server-side principal stamped into approval audit records), so a caller cannot attribute a message to another agent and the audit trail cannot be forged.
- **Authorization**: the caller must be a bound agent or a host session; an unauthenticated connection is refused. A bound agent is then resolved against `AgentPermissionPolicy` at the **`read_only`** tier — honestly what a peer message is, since it mutates nothing on the recipient, reaches no executor, and grants no authority. The tier is resolved for the *sender*: the question is whether this agent may talk to other agents. Under the Balanced preset `read_only` is `always_allow`, so the default is permissive; the value is that setting a specific agent's `read_only` posture to `deny` actually stops its peer messages (`require_approval` holds them instead of dropping them), rather than the rule living only in a system prompt the agent may or may not follow.
- **Semantics**: a peer message is **inert data**. It is not a `proposal.submit` and cannot reach the executor; whatever the receiving agent decides to do about it passes through that agent's own gates unchanged. It cannot answer a pending permission prompt, and a slash command in the body arrives as text.
- **Delivery**: the daemon reverse-calls **`agent.peer_message`** `{ id, from, body, sent_at_ms, no_reply, kind, in_reply_to, answered_by, cross_owner, connection, verified_by, verified_org, verified_account, same_org, sender_work_context, work_context }` on the recipient's attached connection (`kind` is always present, `"message"` when unset; `in_reply_to` is `null` when unset; `answered_by` is set only on an answer from a person's node and says who recorded it — `host`, `delegate:<agent id>` for an agent the operator made the person's delegate, or `approval` — so a delegate's words never pass as the person's own; `cross_owner` is true when the message came from another owner's CAR over a Lattice connection, recorded from the key that signed it — untrusted data from outside this owner's trust domain. `peer_inbox` rows carry the same `cross_owner`) — the same mechanism `agents.chat` uses.
  - **Provenance** (car-releases#109), so an agent can tier its trust in a peer without the host-only `lattice.connections` and without matching connections by label: `connection` is the stable id of the Lattice connection the message arrived over (`null` for this owner's own nodes and devices); `verified_by` is how that CAR's identity was established — `fingerprint` (both owners compared fingerprints), `tofu` (a LAN knock: pinned when accepted, not verified), `org:<org>` (an org granter's attestation) or `cert:<org>:<account>` (a Parslee device certificate); `verified_org` and `verified_account` are the certifying org and the other owner's account when an org verified it; `same_org` is whether `verified_org` is an organization this CAR's owner belongs to (`false` when no org verified it). All four are `null` when `cross_owner` is false. `from` is `<node>@<label>`, where `label` is the operator's own name for the connection — a display name, not an identity.
  - **Acknowledging.** The daemon waits 5 s for the JSON-RPC response to the reverse call; that response is the acknowledgement. Send it as soon as the message is received — before doing the work it asks for — and do the work afterwards. In Node, the value a `registerDaemonHandler("agent.peer_message", …)` handler resolves is the response, and the handler runs on the JS event loop: resolve it at once and continue without awaiting the work, and keep long synchronous calls (a blocking FFI call) off the loop, or the acknowledgement misses 5 s even though the message is then handled. (`registerChatHandler` acknowledges `agent.chat` natively; `agent.peer_message` has no such handler.)
  - **What `unacknowledged` means.** The frame was written to the recipient's connection and the daemon stopped waiting; it does not mean the message was lost, and the recipient may still handle it. The daemon never retries or redelivers it, and the sender should not resend it by reflex: a resent body inside 10 s is dropped as a repeat, and a resent body later arrives as a second message with a new `id`. A recipient that may see the same request twice (because a sender resent it after `unacknowledged`) deduplicates by its own reading of the content; the `id` is unique per send. A reply, if one comes, still reaches a sender waiting with `lattice.wait`. There is deliberately no per-agent socket: a path that reached an agent without passing through the daemon would make admission advisory, since nothing would sit between sender and recipient.
- **Channel limits** (these bound the channel, not the sender's authority — two agents answering each other form a loop that no policy rule catches because neither is misbehaving):
  - Body cap ~1 MB serialized. Over it, send a path or a state handle instead.
  - Identical body from the same sender inside 10s is dropped as a repeat.
  - 20 messages per sender per recipient per 60s, and 40 per recipient from all senders behind one Lattice connection together (a remote sender `node@label` names its own node, so only the connection label bounds it).
  - 50 undelivered messages queued per recipient.
  - Each limit returns a distinct error naming the remedy: batch for a rate limit, wait for a full queue.
- **Returns**: `{ id, to, outcome }` where `outcome` is:
  - `delivered` — the recipient acknowledged.
  - `unacknowledged` — the frame was written but no ack arrived within 5s. Recorded as its own audit outcome rather than folded into `delivered` or `refused`: the frame demonstrably was written, so calling it a drop is as wrong as calling it a delivery. Reported honestly rather than as failure: an agent that does not implement `agent.peer_message` simply never answers, and the write did happen.
  - `stored` — the recipient is an organization inbox (`inbox:<org>`, or a session of that org that had exited): the message was fsynced on the recipient's CAR, and the org's next session reads it with `lattice.inbox`.
  - `awaiting_human` — the recipient is a human Lattice node (`to: "human:<name>"`): the message was recorded as a durable request for a person, and the answer arrives later as a reply (see `lattice.wait`). The result also carries `answer_token`, which only the asker receives.
  - `held` — the recipient's configured posture stopped it, or it is the first message this owner sends over a Lattice connection to another owner's CAR (below); carries `reason`, `retained: true`, `cross_owner`, and `awaiting_notice`. The message is kept for an operator decision — see `agents.message.pending` / `agents.message.approve` below.
- **The first message to another owner's CAR waits for its owner.** Except on a connection an organization verified (`verified_by` `org:<org>` or `cert:<org>:<account>`): there, offering or accepting the colleague's connection was that agreement, and nothing is held. Otherwise a message to `<node>@<label>` over a Lattice connection (never one of this owner's own devices) is held, with `cross_owner: true`, until the operator agrees to what may happen to it there. The `reason` is the notice: where it goes, the connection's purpose, and that what processes it on the other CAR — a cloud model included — is outside this owner's control. Nothing CAR can check rules a cloud model out on the far side, so every cross-owner target is in that one class today. Approving the message records the agreement on the connection (`lattice.connections` `acknowledged`), and later messages on it go without asking, from any of this owner's nodes. Declining shares nothing, records nothing (the next message waits again), and is not charged against the sender's standing: the owner declining to share is no fault of their node. The same applies to the MCP `peer_message` tool, which returns `outcome: "held"` instead of sending, and to a person's answer through `lattice.respond`. The operator decides in CarHost or with `car lattice held` / `car lattice release <id> [--decline | --acknowledge-processing]`. This is a consent step for the owner, not a barrier against software running as that same user: the host credential is a file in the user's own account, so a coding agent with a shell and that user's permissions can reach it, as it could reach CarHost's. Each held cross-owner message raises a `lattice.outgoing_held` host event `{ id, from, to, connection }` (no body). A message the credential heuristic flags is still refused when the operator approves it. When posture also holds the message, one record carries both reasons.
  - A refusal is an error, not an outcome.
- **Cross-host delivery passes two admissions when the far side is a
  peer-authenticated CAR listener** — the one `car-server` runs by default. That
  qualifier matters: a `remote_car` peer whose URL points at an `a2a.start`
  listener reaches a surface with no signature check and no broker, and the
  outcome reported there is `accepted`, not `delivered`. A message addressed to
  a peer-authenticated daemon lands on its **receiving-side broker**, which
  decides it
  before it reaches anyone: the sender is rebuilt from the *verified* signing
  key rather than the name the caller supplied, the recipient must be an agent
  attached to that host (a peer message is **never relayed** onward — that would
  make the host an open relay forwarding under its own signature to hosts that
  never trusted the origin), and the recipient's own channel guard applies. So
  `delivered` means the far side admitted it and reverse-called its agent, and
  the far side *said so* — the sender reads the broker's verdict out of the
  reply rather than assuming it, so a message whose recipient never acknowledged
  comes back `unacknowledged` on both hosts instead of being recorded as
  delivered on either. A peer with no broker reports `accepted`, which claims
  only what it can: the bytes were taken. A refusal returns as an error carrying
  the remote broker's reason. Peer messages are delivered over
  `message/send`; the streaming twin refuses them rather than compiling them
  into a proposal. What the far side does **not** do is grade the sender against
  a per-peer policy row: there is no local sender to resolve inbound, and a
  remote-supplied name must never select which local posture governs it.
- **Earned standing.** A sending principal — a verified peer key inbound, a
  local agent id outbound — accumulates a record from *this daemon's own
  observed outcomes*, never from message content (a body that could move a
  sender's standing would make the envelope an authority channel). A record
  degrades on the same rule that degrades a skill, `fail > success + 2`, now a
  single shared definition rather than three copies. What counts as a failure is
  narrow and deliberate: a chain over the hop cap, an oversized body, an illegal
  name or malformed lineage, an unresolvable recipient, and an operator's
  explicit denial through `agents.message.approve` — which is the only ground
  truth among them. What does **not** count: a rate limit or an in-window
  duplicate (the channel guard exists precisely because in a mutual loop neither
  party is misbehaving, so charging them would price correct behaviour as
  misconduct), a refusal by this host's own policy (our posture, not their
  conduct), and an unacknowledged delivery (the recipient's agent did not
  answer). The consequence is a **throttle, not a severance**: a degraded sender
  is limited to 2 messages per minute, host-scoped and checked *before* the
  per-recipient guard, so renaming agents or switching recipients does not buy a
  fresh budget. Successes saturate, so headroom never grows without bound, and
  both counters halve weekly, so a degraded peer recovers on its own without
  anyone remembering to forgive it. `agents.peers` renders a record where one
  exists — absent means nothing has been observed yet, which is not the same as
  a clean record. Counters are in-memory: only an operator's ledger decision is
  durable, by design.
- **Lineage.** A peer message carries `trace` (the id of the message that began
  the chain) and `via` (the ordered principals it passed through, origin first).
  Segments are `agent:<id>`, `conn:<id>`, `mcp:<peer-id>`, or
  `peer:<key>` — and a `peer:` segment is a **host-boundary marker stamped by
  the receiving daemon from the key it verified, never by the sender**. So
  everything before the last `peer:` marker is that key's *attestation*, and
  everything after was observed by the daemon holding the message. The list
  carries its own trust model; nothing downstream has to remember which half was
  witnessed. Lineage crosses the hop inside the signed request body, so it
  cannot be altered in flight — though the signer can still lie about its own
  prefix, which is what the hop cap bounds and what earned peer standing is
  meant to make expensive. A chain deeper than 8 **agent** hops is refused
  (boundary markers do not count: crossing a host changes who attests, not how
  far the work has travelled). This is the one hazard the dedupe and rate limits
  structurally cannot see — eight agents each forwarding a different body are
  eight legitimate sends by every per-pair rule, and still a runaway. Inbound
  `via` is validated for shape before an agent is shown it; both fields default,
  so a sender that predates lineage produces a root rather than an error.
- **Audit**: every attempted delivery, refusals included, appends to the `ServerState`'s configured peer audit journal (`~/.car/peer-messages.jsonl` for the standalone daemon). The journal holds metadata (sender, recipient, outcome, size, lineage), never the message body. The default journal (and one derived from a custom journal directory) is written owner-only (`0600`): a looser file is tightened in place at daemon startup and on each write, never deleted, and a symlink at the path is refused. The first write also makes its directory (the state root, by default) `0700`, and a state root reached through a symlink (a symlinked `CAR_HOME`) is refused for this file, as it already is for session journals. A path an embedder sets with `ServerStateConfig::with_peer_audit_journal` is written the plain way, as before. Either way a refused or failed write is logged at warn level with its reason rather than silently dropped. `agents.chat` rows go through the same writer. The path is resolved once at state construction; a test or embedder with a custom state directory never re-resolves process-global `CAR_HOME` while writing. Rows carry `dir` (`out` / `in`), `trace`, and `via`, plus `message_kind` when the message is not a plain `message` and `in_reply_to` when it answers one (the row's `kind` column is the recipient's peer kind, which predates message kinds); inbound rows also carry `attested_by` — the verified key the sender was derived from. The last `via` segment on an inbound row is therefore the receiver-appended `peer:<verified-key>` boundary, so an operator can distinguish what the remote key attested from what this daemon observed. Inbound rows are new: before the receiving broker existed there was no inbound admission to record. `agents.chat` writes to the same configured journal — it has driven another agent's turn since it shipped with no audit record of any kind, and adding a governed sibling beside an unrecorded surface would only have moved well-behaved callers onto the audited path.

#### `agents.message.pending`
- **Params**: none (`{}`).
- **Authorization**: **host-only.** An agent must not be able to read, or later approve, the queue that exists to gate it.
- Lists peer messages held awaiting an operator decision, oldest first.
- **Returns**: `{ held: [{ id, from, from_name, to, body, held_at_ms, reason, cross_owner, connection, awaiting_notice, notice_only, processing }], count, cap }`. `from_name` is the sender's Lattice display name when it has one (`null` otherwise). `cross_owner` is true when the recipient is a node on another owner's CAR, and `connection` is that Lattice connection's id (`null` otherwise). `awaiting_notice` is true while the message still waits on the processing notice (false once its connection has been agreed), with `processing` the class it was held for (`"may_use_cloud_model"`, else `null`). `notice_only` is true when the notice alone held it, so allowing the connection sends it; false when posture held it too, which still needs its own decision. A message posture held to another owner's node after the agreement has `cross_owner: true, awaiting_notice: false`.
- **Authorization**: also accepts the host-management credential, so `car lattice held` / `car lattice release` reach it from the CLI.
  - The queue is bounded at 100 undecided messages; past that the oldest is dropped, logged, and written to the audit journal as a refusal — a message the operator never saw must not vanish silently after the sender was told it was retained.
  - Held in memory only. A held message is a live decision awaiting a human, and one that outlived a daemon restart would be delivered into a world that had moved on.

#### `agents.message.approve`
- **Params**: `{ id: string, decision: boolean | string, acknowledge_processing?: boolean }`.
  - `acknowledge_processing` must be `true` to send a message still `awaiting_notice`, because sending it agrees for its whole connection; once the connection is agreed it is not needed. Without it the call fails with the notice, and the message stays held where it was. Declining needs no flag.
  - `decision` accepts a bool or a string (`"approve"`/`"approved"`/`"yes"` → approved; anything else, or omitted → denied). Same convention as `agents.chat.approve`, so an operator does not have to remember two.
- **Authorization**: **host-only**, as above.
- On approval the message is **re-admitted through the channel guard** before delivery. It passed the guard when it was sent, but time has moved and the recipient may since have been flooded; an approval authorizes the sender, it is not a licence to bypass the channel's limits. The message's own identical-repeat record is forgotten first, so an operator approving within 10 s is not told it "was already delivered". A message the guard refuses at this point (a rate limit after a burst of approvals) stays held and the call fails saying so.
- **Returns**: `{ id, outcome }` — `denied`, or the same `{ id, to, outcome }` shape `agents.message` returns on delivery. Both paths append to `~/.car/peer-messages.jsonl`.
- Approving an `awaiting_notice` message first records the agreement on its connection, which must still be active, then sends the other messages held only for that notice on the connection. They are taken off the queue one at a time, just before each is sent, so a decline made meanwhile still finds its message and wins. The agreement stands if the delivery itself then fails (a credential refused, the other CAR unreachable): the owner did see the notice. Declining a message posture held too is charged to the sender as any posture denial. Ending a connection drops its held messages, each journalled as refused. The journal records an approved message's actual delivery outcome, never `delivered` ahead of the attempt.
- The queue slot a held message occupied is released when it is held, not when it is decided: `QUEUE_CAP` bounds what a recipient has yet to read, `HOLD_CAP` bounds what an operator has yet to decide. Charging a held message against the delivery queue would let a slow human block a healthy channel.

#### `agents.chat.cancel`
- **Params**: `{ session_id: string }`.
- Best-effort cancellation. Attached supervised agents receive `agent.chat.cancel` (a notification) so they can short-circuit their inference stream; the bundled assistant (`parslee-core`, or its legacy id `car-assistant`) is sent it as a request instead, and its answer is relayed in `dispatched` below. In-daemon declarative agent sessions set a local cancellation flag and drop routing immediately; the runner stops at the next model/tool/goal-check boundary. Cancel also stops every streaming `agents.invoke_external` run handed off into the cancelled turn, and a host's own streaming run registered under that `session_id` (see **Authorization** under `agents.invoke_external`). The bundled `car do --serve` assistant stops the same way: a Stop ends the turn at once, as stopped, even while a model call is in flight, and no further reply text is shown or acted on (nor a reply that returns together with the Stop), a goal turn stopped during its final reply ends as stopped without running its goal check (a check that already finished is still graded), and for an approval card still waiting (a tool call's or the goal check's) the daemon closes the mirrored approval as `cancelled`, and the assistant refuses the parked call at once instead of waiting out its timeout; no new card is shown, because the daemon has already dropped the route an answer would travel. An approval that lands together with the Stop is refused the same way, and a call approved just before the Stop is refused at dispatch. The stopped turn stays in the session's thread: a call it never ran reads as stopped to the model, and the next turn on the same `session_id` numbers its call ids on from it, so a repeated approval-gated call shows a new card. A turn sent while another turn of the session is still running waits for it to finish. The Stop reaches every turn in flight on the `session_id`, including one waiting to start. Terminal for the routed turn; a later `agents.chat` under the same `session_id` starts a new turn.
- **A route the daemon ends without a Stop is stopped the same way.** When the host that started a turn disconnects, or the agent does not acknowledge `agent.chat` within the acknowledgement timeout (5 s), nobody can answer the turn's approvals or read its reply any more, so the daemon sends the attached agent the `agent.chat.cancel` notification. The bundled assistant then closes its waiting cards (a tool call's or the goal check's) at once instead of waiting out their timeout, and runs no goal check. When the agent's own connection ends (the agent disconnects or the daemon restarts) no notification can reach it; the bundled assistant stops every turn it accepted on that connection as the connection drops. A host disconnect still does not stop a daemon-owned run (an in-daemon declarative agent's turn, or a streaming `agents.invoke_external` run started with no chat routed under its `session_id`). A host should not reuse a `session_id` after a Stop or a disconnect while the stopped turn may still send its terminal frame: unless the agent echoes `turn_id` (see `agents.chat`), that frame ends the new turn's route. CarHost starts a new `session_id` after a Stop.
- **Returns**: `{ cancelled: true, session_id, dispatched?: boolean }`, or `{ cancelled: false, reason: "unknown session_id" }` when no turn is routed under `session_id` (a cancel kept for a turn not routed yet, below, answers this too, with no `dispatched`). `dispatched` says whether any call of the turn — a tool call (approved or not gated), a `delegate` child's call, or a goal check — passed the point where it runs. With more than one turn in flight on the session it is `true` if any of them dispatched. A turn still waiting on the session's turn lock registers its Stop flag and dispatch mark before it waits, so it counts as in flight and contributes `false`. It comes from the bundled assistant, which sets the turn's stop flag before reading its dispatch mark and marks each call before that call's last stop check, so `dispatched: false` means nothing of the turn ran and nothing will. It is **left out** whenever the daemon cannot say: any other agent, an in-daemon declarative or `agents.invoke_external` run, an older assistant, no answer within the acknowledgement timeout (5 s), or no turn of the session still in flight on the agent. Read its absence as unknown, never as `false`. The Stop itself takes effect before any wait: the daemon sets an in-daemon turn's stop flag, removes the route and closes the turn's approvals first, and only then asks the assistant, so the reply can take up to that timeout to arrive while the turn is already stopped. An older `car do --serve` answers the request without `dispatched`, which leaves it out here too. CarHost marks a stopped turn's Work item **Stopped** only on `cancelled: true` with `dispatched: false`, and **Outcome unknown** otherwise.
- A cancel can be handled before the turn it names is routed, because the daemon handles each frame on its own task: a host may send `agents.chat` and then, at once, `agents.chat.cancel`. So a cancel for a `session_id` with no route is kept for 60 seconds (at most 256 are kept). The calling connection's next `agents.chat` or `agents.invoke_external` under that `session_id` in that time is refused with `the turn was cancelled before it started` and never reaches the agent; that uses the cancel up, so the turn after it runs. A cancel for a turn that already ended is kept the same way, so use a new `session_id` after a Stop. A cancel that lands after the turn is routed but before the agent has acknowledged it may reach the agent ahead of `agent.chat`; once the agent acknowledges, the daemon sends `agent.chat.cancel` again, naming the turn's `turn_id`, when that turn's route is gone. If a newer turn already holds the `session_id` by then, it is sent only to an agent that declared `stops_by_turn_id` (echoing turn ids on frames is not that promise; ordering is conditional on the retained identity, with the bounded-history fallback above), since an agent that stops by `session_id` alone would end the newer turn; any other agent gets it only while no route holds the `session_id`.
- **Requires the originating host session or the host-management role**, the same check `agents.chat.approve` applies. Being authenticated to the daemon is not sufficient: without this, any session could abort any live turn by observing a `session_id`. A refused cancel leaves the chat session routing untouched.

#### `agents.chat.approve`
- **Params**: `{ session_id: string, approval_id: string, decision?: boolean | string, answer?: "allow_conversation" | "allow_agent" | "allow_all_agents" | "deny", permission_kind?: string }`.
  - Resolves an inline human-in-the-loop approval an agent raised via an `approval_pending` event (carrying `approval_id`). `session_id` selects the agent connection (same routing as `agents.chat`); the session is **kept** so the turn resumes after the decision. The `approval_id` is the one the daemon showed the host for that event, never the agent's own id; see **Only an outstanding id is forwarded** below.
  - `decision` is the legacy answer — a bool, or a string the agent accepts (`"approve"`/`"approved"`/`"yes"` → approved; anything else → denied). Omitted (with no `answer`) ⇒ denied. It approves or declines this one call and remembers nothing.
  - `answer` is one of the four choices an `approval_pending` event offered; send it with the event's `permission_kind` echoed back (and `decision` too, so an older daemon still resolves). The choices are offered only for a web search, and the kind is always `browse_web`. An allow answer approves the call **and** is remembered (the agent stages the grant as an inert pending record, resumes the call, and activates the grant only after the parked gate has durably recorded the approval, all inside the acknowledgement window; if any step fails or runs late the call still goes as the gate decides and the next one asks, and `resolved: false` means the call had already given up and nothing was remembered): `allow_conversation` for this chat's `conversation_id` (see `agents.chat`), `allow_agent` for this agent in every chat, `allow_all_agents` for every agent. Once the grant is active, the next web search in that scope runs without asking; nothing else ever runs on it, and each use reads the file again, so a revoked answer, an exact `require_approval` override or a refusal applies to the very next search. The reply does not say whether the answer was remembered; `agent_permissions.list_grants` shows what is. It remembers nothing when the event offered no choices, or when `permission_kind` is missing or is not `browse_web` — then the answer approves this call only. `deny` declines this call only and creates no refusal.
  - The four-choice `answer` is forwarded only from a host-management session. The other caller allowed to approve — the client session that started the chat turn (for example another agent that called `agents.chat`) — is reduced to the legacy `decision`: it may approve one parked call, never create standing authority. While the person's host holds a turn's route, an agent connection cannot answer an approval in it. An agent that starts a chat itself is that chat's starting session, so it can approve one parked call there, never with a remembered answer; the same is true of a client that starts a turn on a session id whose earlier host has disconnected. A host built from an older release sends a plain `decision` and so remembers nothing, and this agent behind an older daemon may be told `resolved: true` for an allow answer that was not remembered (that daemon does not forward the kind).
- **Authorization**: the caller must be the host session that started the chat turn, or a host-management session authenticated with `session.auth { host_token }`. A supervised agent connection can approve a parked action only in a turn it started itself, and never with a remembered answer.
- **Returns**: `{ resolved: boolean, session_id: string }` — the daemon reverse-*requests* the agent's `agent.chat.approve` handler and relays its `{ resolved }` reply (bounded ack timeout), so the host gets a definitive answer rather than inferring from the stream.
- The daemon mirrors the chat gate into the host `ApprovalLedger` under the same `approval_id`. A host may call this method directly or call `host.resolve_approval`; the latter recognizes `source: "chat"` and routes to the same parked turn. The ledger row remains pending until the agent emits authoritative `approval_resolved`, the routed resolve succeeds, or the agent refuses the decision (see below), so every host surface converges on the same decision.
- **A card is scoped by its turn.** An agent's approval id need only be unique within a turn: when its `approval_pending` names the turn's `turn_id` (see `agents.chat`), another turn's card under the same id is a different card with its own daemon id, an `approval_resolved` naming a turn closes only that turn's card, and the decision forwarded in `agent.chat.approve` carries that `turn_id`.
- **Only an outstanding id is forwarded.** Approval frames reach a host only under a daemon-minted `approval_id` (the inline card and the mirrored ledger row share it); an approval frame the daemon cannot map is dropped, not forwarded with the agent's id. Each approval the agent parks gets its own id, a repeated announcement of one still open keeps the id it has, and the daemon keeps the mapping back to the agent's id on the chat turn's route. This method forwards a decision only for an id outstanding on the session's current route, sending the agent its own id. Each id carries one decision: the first call claims it, and a second call, or one whose turn ended before the decision was sent, fails. A failed delivery is not retried; the parked call then times out as declined. When the agent refuses the decision (`resolved: false`, meaning the call had already given up, or an error reply), the daemon closes the mirrored ledger row itself, with `timeout` or `interrupted` respectively, since no `approval_resolved` will follow. Any other id (already answered, expired, from an earlier turn, another session's, or the agent's raw id) fails with an error naming it as not pending, and nothing reaches the agent. A route ends with its turn (or when another `agents.chat` replaces it under the same `session_id`), so a cancelled, failed or replaced turn's approvals cannot be answered under the next turn. The agent's `approval_resolved` is forwarded under the same daemon id. When an older agent reuses its id, the daemon matches the frame by what it says: `approve` or `deny` closes the oldest approval with that id that was answered, anything else (`timeout`) the oldest one that was not; a turn's approvals outlive its route: a replaced turn's are carried onto its successor, and a turn that ends with nothing replacing it (cancelled, a failed send, or its host disconnected) keeps its for the session's next turn from the same agent while that agent stays attached (at most 64 per session and 256 sessions, the least recently held dropped first, and all of them when that agent disconnects; a declarative agent's run sends nothing after it ends and keeps none), so the ended turn's late frames are consumed against them and never close the newer turn's approval. Treat ids as opaque. This keeps an agent built before approval ids carried a turn token, which reused `<session_id>-appr-<n>` from zero each turn, from ever having a stale decision reach a newer call; a host should still disable a turn's unanswered cards when the turn ends.

#### `agents.list_external`
- **Params**: `{ include_health?: boolean }` — when `true`, also populates each spec's `health` field via the tool's auth-status command (slower; one subprocess per detected adapter). Default `false`.
- Hosts may ask for health when a screen appears (CarHost's Assistants list and its AI accounts section both do). The status commands are each tool's own (`claude auth status`, `codex login status`): they read that tool's login, never CAR's secret store, so this is not a CAR credential read under [demand-driven Keychain access](../solutions/demand-driven-keychain-access.md). Each probe is bounded and its result cached for 30 seconds.
- **Returns**: `[ExternalAgentSpec]` — cached snapshot of installed agentic CLIs (Claude Code, Codex, Gemini). Each entry carries `{id, display_name, binary_path, version?, auth_kind, capabilities, detected_at, health?, execution}`. `auth_kind` is **deprecated** (Phase 2 stage 1) — prefer `health` for ground-truth readiness.
- `execution` (car#746) answers a **different question** from `health`: *can this binary be executed at all*. `{"state":"runnable"}` or `{"state":"unusable","reason":"<names the path>","checked_at":<unix>}`. It is written by detection and **never revised by a health refresh**, whereas `health` is owned by refreshers that are free to rewrite it — which is why the executability verdict moved off `health.status`. Prefer it over `health.status == "not_executable"`, which is still emitted for one compatibility window. An absent `execution` (a pre-split daemon) reads as `runnable`. **Callers must not invoke a spec whose `execution.state` is `unusable`.**
- This is the discovery surface for the third kind of agent in CAR's taxonomy (sibling to lifecycle agents and in-process runners). See `docs/proposals/external-agent-detection.md`.

##### How `binary_path` is resolved

Resolution is executability-verified, not existence-based. In precedence order:

1. **Explicit pin** — `$CAR_<ADAPTER>_BIN` (`CAR_CODEX_BIN`, `CAR_CLAUDE_CODE_BIN`, `CAR_GEMINI_BIN`). When set, `$PATH` is not consulted. Use this for a CLI that ships inside an app bundle and was never on `$PATH` (ChatGPT.app vendors its own `codex`). A pin that doesn't resolve is reported as `not_executable` rather than silently falling back to `$PATH` — falling back would reintroduce exactly the ambiguity the pin removes. **The pin is process-local**: the daemon is launched by the GUI and inherits launchd's environment, so a `export` in a shell rc file is visible to `car` but *not* to the daemon that runs coder sessions.
2. **`$PATH` scan** — **every** match is collected in `$PATH` order (duplicate `$PATH` entries collapse), then each is probed with `--version` until one actually runs. A binary that resolves but cannot execute therefore **cannot shadow** a working one later on `$PATH`.

If no candidate runs, the adapter is still returned — omitting it would leave the user unable to find the broken install — but with `execution: {"state":"unusable", reason}` naming the path (and, for the compatibility window, `health.status: "not_executable"`). **Callers must not invoke a spec in that state.** The world-writable scratch-directory denylist (`/tmp`, `%TEMP%`, …) applies to the `$PATH` scan; an explicit pin bypasses it, since naming a path outright already requires a privilege that setting `PATH` itself would grant.

#### `agents.detect_external`
- **Params**: `{ include_health?: boolean }` — same as `agents.list_external` but always force-refreshes the presence cache (and the health-check TTL cache, when `include_health: true`).
- **Returns**: `[ExternalAgentSpec]` — same shape as `agents.list_external`. Use after the user installs / authenticates a new tool, or to refresh `health` after a login.

#### `agents.health_external`
- **Params**: `{ id?: string, force?: boolean }`
  - `id` selects a single adapter (`"claude-code"`, `"codex"`, `"gemini"`, `"mini-swe-agent"`). Omit to check every detected adapter.
  - `force` bypasses the 30s per-tool TTL cache. Default `false`.
- **Returns**: `[ExternalAgentHealth]` (when `id` omitted) or `ExternalAgentHealth` (when `id` supplied). Each entry: `{id, status, details, reason?, checked_at}` where `status` is one of `ready | not_configured | expired | network_error | not_executable | unknown` and `details` is tool-specific structured JSON parsed from the auth-status output.
- `not_executable` is set by **detection**, not by an auth-status command — a binary the OS refuses to run cannot report its own auth state, so the status probe is skipped entirely rather than spawning a second doomed process whose `unknown` would overwrite the diagnosis. It means the *install* is broken (macOS Gatekeeper quarantine, architecture mismatch, dangling symlink into a relocated app bundle), not that the user is signed out: hosts should surface the `reason` and **not** offer a login flow. On macOS, `xattr -l <binary_path>` showing `com.apple.quarantine` confirms the common case.
- **Ground truth**, not heuristic: delegates to each tool's own status command (`claude auth status` returning structured JSON, `codex login status` returning a single status line, etc.). Two adapters have no such command and say so in `reason`: Gemini (running it without args triggers a browser OAuth flow) falls back to credential-file shape inspection, and `mini-swe-agent` (which has no status command at all) reports `ready` when a provider API key **name** resolves from the daemon environment or from its own global `.env`. Neither is verified against the provider; a key that doesn't match the pinned model surfaces at invocation.
- **Replaces the Phase 1 `auth_kind` heuristic** as the primary signal for "is this tool ready to invoke." Existing callers reading `auth_kind` keep working; new callers should prefer `agents.health_external`. Phase 2 will demote `auth_kind` to optional and add a `health` field to `ExternalAgentSpec` carrying ground-truth status.

#### `agents.invoke_external`
- **Authorization**: a host may call it with or without a chat. An unbound non-host caller holding only the daemon-wide token is refused with `this operation requires the host-management role`, the same authority boundary `agents.upsert` uses, on every daemon, including one with no host token. A connection bound to a supervised agent (`session.auth { token, agent_id }`) may call it only while it is answering an `agents.chat` turn a host started with it: the connection must be the agent's current one (an older connection a reconnect superseded is refused), and `session_id` must name that turn while it is still running. A later turn under the same `session_id` is a different turn. A host here is a connection with host-management authority; on a daemon with no host token (development mode), any connection that is neither bound to an agent nor authenticated as an inference consumer counts, the same exception the lifecycle methods make. An inference consumer socket (`session.auth { consumer_id, token }`) is refused outright with "An inference consumer socket cannot call `agents.invoke_external`; its scope is inference only." An agent's call is refused with "An agent can ask an outside agent only while answering a chat you started." when it names no `session_id`, a chat sent to another agent, a chat another agent, an inference consumer, or a connection without host authority started, or a chat that has ended or been replaced by a new turn. The check is made when the call arrives and again, on both the one-shot and the streaming path, just before the call is handed to the CLI runner; the second check covers both the connection and the turn, and no reconnect can land between them. The runner then probes the installed tools before the CLI starts: about two seconds at most per installed binary of an adapter, with an adapter's binaries probed one after another and the adapters side by side. A streaming run that has been handed off belongs to the turn it was allowed under. It keeps running if the agent reconnects, and it is stopped when that turn ends, however it ends: the agent finishes or fails it, a host cancels it with `agents.chat.cancel`, the host sends the session's next turn, or the host or the agent disconnects. Its events reach only that turn: once the turn has ended, any event the run still emits, its final `done` or `error` included, is dropped rather than delivered to a later turn under the same `session_id`, and it does not update that session's goal. A one-shot run is part of the calling connection's request, so it stops if that connection closes. The check reads the daemon's own record of the turn (who started it and which agent it was sent to), never the caller's params. It binds the connection, not the process: reconnecting without `agent_id` does not bypass the host-token authority gate (car#2456). This limits what CAR hands to that connection; it is not process confinement, because software running as the same user can launch the external CLI itself.
- **Discovery**: the method's derived role is `agent`, so `capabilities.list` lists it for agent sessions only. Hosts do not see it there and call it directly.
- **Params**: `{ id: string, task: string, stream?: boolean, session_id?: string, cwd?: string, allowed_tools?: [string], max_turns?: number, timeout_secs?: number, mcp_endpoint?: string, mcp_bearer?: string, isolate_network?: boolean, isolate_config?: boolean, attachments?: [{ path: string, media_type?: string }] }`
  - `id` selects the adapter (`"claude-code"`, `"codex"`, `"gemini"`, `"mini-swe-agent"`).
  - `"mini-swe-agent"` is a **measurement baseline**, not a production engine — it is the control arm for `car coder-ab` (see `docs/coder-ab-guide.md`). It must be named explicitly: unnamed engine resolution (`coder.start` with `engine: "auto"` or a bare `"external"`) never selects it. It also has no default backbone of its own, so an invocation without `model` (and without `$MSWEA_MODEL_NAME` in the daemon environment) is refused up front rather than spawned; its model ids are **litellm** ids and need the provider prefix (`openai/gpt-5.5`, not `gpt-5.5`).
  - `task` is the prompt the agent runs to completion.
  - `stream` opts into per-event streaming over the existing `agents.chat.event` channel (default `false`). When `true`, the method returns an ack (`{accepted, session_id}`) and the runner fans `agents.chat.event` notifications to the originating host as the child emits stream-json events — `kind: "token"` per text content block, `kind: "tool_call"` per `tool_use` block, terminal `kind: "done"` with metadata folded into `finish_reason` (or `kind: "error"`). Every adapter emits events (car#213), but only two stream: `claude-code` forwards native stream-json events; `codex` synthesizes an Anthropic-Messages-shaped `Assistant` event per `item.completed` line (incremental `kind: "token"` / `"tool_call"` frames); `gemini` is text-only in 0.1.x (no event stream) and `mini-swe-agent` has none either (its trajectory JSON is read once after exit), so each emits one `Assistant` text event with the full reply on completion — a single-pop `kind: "token"` then the terminal `done`, not a token stream. `capabilities.streaming` (`agents.list_external`) says which is which. Each `tool_call` frame carries the `tool` name + `params` (the `tool_use` input) per the shape pinned in `docs/host-protocol.md` (plus a legacy `detail` = name alias).
  - `session_id` is the host-generated id threaded through every event. Auto-generated when omitted; an agent must name the chat it is answering (see **Authorization**), and its CLI's events then stream to the host that started that chat, for as long as that turn runs. Reuses the same routing infrastructure as `agents.chat`; when `stream: true`, `agents.chat.cancel { session_id }` flips the runner's local cancel flag and drops the child-process future (`kill_on_drop` reaps the CLI). A streaming run started with no chat routed under its `session_id` also stops when the same connection's next `agents.chat` under that `session_id` replaces the route (from a host, only a declarative agent's turn can), and keeps running if the host disconnects; its events reach only its own route. A call that would route a new turn (no `agents.chat` turn already routed under `session_id`) is refused with `the turn was cancelled before it started` when this connection sent `agents.chat.cancel` for the same `session_id` within the previous 60 s (see `agents.chat.cancel`).
  - `cwd` defaults to the daemon's working directory.
  - `allowed_tools` is passed through as `--allowed-tools "<list>"`. `[]` denies every tool (text-only response). Omit to use the binary's default policy.
  - `max_turns` caps model turns. Cost-control guard for runaway loops.
  - `isolate_network` (default `false`) runs the CLI with no route off the machine: Codex gets `--ignore-user-config`, `web_search="disabled"`, the personal features off (as listed under `isolate_config`), a `workspace-write` sandbox without network, and a fresh temporary `CODEX_HOME` (none of the user's memories, past sessions or global `AGENTS.md`, which `--ignore-user-config` alone left readable). Only the login is carried into it: with `CODEX_API_KEY` set nothing is, otherwise the user's `auth.json` (from `CODEX_HOME`, else `~/.codex`) is linked in, and a login Codex refreshed into its own copy is written back while the user's file is unchanged since the run started. With neither, as with a login kept in the OS keyring, the call fails as a setup error; Claude Code runs with an empty temporary `CLAUDE_CONFIG_DIR` (none of the user's plugins, hooks, agents, skills, auto-memory or `~/.claude/CLAUDE.md`; its stock tools are unchanged; with no config it cannot use a claude.ai login or an `apiKeyHelper`, so it authenticates from the environment — `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, or a Bedrock/Vertex/Foundry provider selected with `CLAUDE_CODE_USE_*` — and without one the call fails as a setup error) and `--setting-sources project,local` (the user's own settings are left out), `--strict-mcp-config` with no MCP config, WebFetch/WebSearch removed, `acceptEdits`, and an OS sandbox with no allowed network domain and no unsandboxed retry (on Linux the sandbox needs bubblewrap; without `bwrap` on PATH the call fails as a setup error). The MCP endpoint is not injected. `gemini` and `mini-swe-agent` refuse (a setup failure) because CAR has no verified way to cut their web access. Ignoring the user's Codex config also drops its personal defaults, such as reasoning effort.
  - `isolate_config` (default `false`) runs the CLI without its user's own configuration while keeping the web: Codex gets `--ignore-user-config`, `web_search="live"` (the default would otherwise come from the ignored user config), the personal features off (`apps`, `plugins`, `plugin_sharing`, `remote_plugin`, `browser_use`, `browser_use_external`, `browser_use_full_cdp_access`, `in_app_browser`, `computer_use`, `memories`, `multi_agent`, `image_generation` — on by default and not user config, so `--ignore-user-config` leaves them on; `isolate_network` turns them off too) and the same fresh temporary `CODEX_HOME` with only its login carried in, but keeps its own sandbox's network posture and its web search. The CAR MCP endpoint is not injected. Verified on codex-cli 0.160.1: it searched the web, listed no browser, computer-use, app or plugin tool, and reported no MCP servers. Claude Code, `gemini` and `mini-swe-agent` refuse as a setup failure: Claude Code keeps its claude.ai login in the configuration this leaves out. `isolate_network` implies it.
  - `timeout_secs` is the public invocation deadline. It defaults to 300s and
    is clamped to [1, 3600]. Only coder sessions bypass this public policy and
    pass no runner wall timeout, because their silence watchdog and no-progress
    rule provide the bound.
  - `mcp_endpoint` is the MCP server URL the agent should load via `--mcp-config`. **Auto-filled from the daemon's bound `/mcp` URL when omitted** — so external agents transparently pick up CAR's tools (`memory_*`, `verify`, `skill_*`) routed through the daemon's policy + shared memgine. Pass `""` (empty string) to opt out (no `--mcp-config` injected; agent runs without CAR's MCP namespace). When the endpoint is the daemon's own (any loopback spelling of it), the daemon mints a run credential for this invocation and revokes it when the run ends (car#3185): a host or other operator caller's CLI is served the daemon's shared memory, as before, and a supervised agent's CLI is served that agent's own memory. Claude Code gets it as request headers in its owner-only MCP config file; Codex gets `bearer_token_env_var="CAR_MCP_RUN_TOKEN"`; both get `CAR_MCP_RUN_TOKEN`/`CAR_MCP_RUN_AGENT_ID` in their environment, never on the command line. A loopback spelling of the endpoint other than the daemon's own is rewritten to the daemon's own address first. The daemon's own token is never written into the CLI's config or command line, and a CLI launched for a supervised agent has the daemon-wide credential environment (`CAR_AUTH_TOKEN`, `CAR_AUTH_TOKEN_FILE`, `CAR_HOST_TOKEN`) removed and carries `CAR_AGENT_ID` as a spawner marker.
  - `mcp_bearer` is your own bearer token for an `mcp_endpoint` you hold a credential to, passed to the CLI by the same route (header for Claude Code, `CAR_MCP_BEARER` for Codex). It is never written to the audit record or echoed back, and a minted run credential takes its place when the endpoint is the daemon's own. CAR never fills it in.
  - `attachments` are images attached to the prompt, each `{ path, media_type? }` where `path` is an **absolute path on the daemon's filesystem** (external CLIs are local subprocesses, so images are passed by path, not base64). The runner hands each to the CLI in its native form: `claude-code` reads the bytes and inlines a base64 image block on stdin, `codex` passes each via `--image`, `gemini` references it with `@path` (staged into a temp dir first). The runner validates every path it reads/stages: files over 32 MB are skipped, and the `claude-code`/`gemini` paths verify the bytes are a real image by magic signature (PNG/JPEG/GIF/WebP) and derive `media_type` from the **content** — the supplied `media_type` is advisory, so a non-image file (e.g. a secret the path points at) is never inlined. Adapters advertise support via `capabilities.images` (`agents.list_external`); a CLI without image input ignores them (`mini-swe-agent` has none, and reports every supplied image in `dropped_attachments`). Unreadable / oversized / non-image paths are skipped.
- **Returns** (non-streaming): `InvokeResult { answer, session_id?, turns, tool_calls, duration_ms, total_cost_usd?, dropped_attachments?, is_error, error? }`. `total_cost_usd` is the would-be API cost — subscription users don't pay this; reported for transparency. `tool_calls` counts `tool_use` blocks the assistant emitted across all turns. `dropped_attachments` (omitted when 0) is the number of supplied images the runner couldn't send (unreadable / oversized / not a recognized image).
- **Returns** (streaming, `stream: true`): `{ accepted: true, session_id: string }`. The full InvokeResult is *not* in the reply — the daemon emits `agents.chat.event` notifications on the originating host's channel and writes the same `~/.car/external-agents.jsonl` audit record when the invocation completes. The terminal `kind: "done"` event carries `dropped_attachments` (and folds an "N image(s) skipped" note into `finish_reason`) when any attachment was dropped, so a streaming host can warn the user.
- **Cost note**: each invocation burns subscription quota. The runner doesn't gate cost; hosts should rate-limit.
- **Audit trail (stage 4a)**: every invocation appends one JSONL record to `~/.car/external-agents.jsonl` with `{ts, adapter_id, task, options, result}`. The `result` includes the `tool_uses` list — every `tool_use` block the assistant emitted, in stream order, with id/name/input. Built-in tools execute in-process and aren't policy-gated through CAR yet; this record is the after-the-fact trail of what ran, redacted and capped as below.
  - **Redacted.** `task`, `options` and `result` pass through the same redactor as feedback bundles before they are written: common token shapes (bearer tokens, JWTs, GitHub, OpenAI, Slack, Stripe and Google keys, AWS access key IDs, Azure SAS signatures), PEM private-key blocks (BEGIN line through END line, any key type; a block cut off before its END goes through its base64 body), AWS secret access keys named as one (`aws_secret_access_key = …` in any case with a key-shaped value, or a JSON field of that name), credential query parameters, `NAME=value` secret assignments, the opaque part of standard base64 runs of 40+ characters that do not read as words (Ed25519, RSA and ECDSA OpenSSH public keys and integrity hashes excepted), and other long high-entropy runs become `[REDACTED]`, and home-directory paths become `~`. It catches common shapes, not every secret: a value with no name the redactor recognises, shorter than 40 characters or reading as words, is kept. `options` never carries `mcp_bearer`. Records written before this version are left as they were written, not redacted retroactively.
  - **File mode.** The file is `0600`. The first write also makes the state root `0700` if it was looser, and a state root reached through a symlink (a symlinked `CAR_HOME`) is refused for this file, as it already is for session journals. A file left looser by an older daemon is tightened in place at daemon startup (for the default state root; a daemon started with a custom `--journal-dir` tightens it on the next write instead) and on each write, never deleted, and a symlink at the path is refused rather than followed.
  - **Retention.** The same limits as finished session journals, applied with slack so an append does not rewrite the file each time: at daemon startup (default state root) the file is cut to the newest 1,024 records from the last 30 days, and an append rewrites it the same way only once it holds more than 1,152 records (1,024 plus an eighth) or its oldest dated record is more than 31 days old. A record with no readable timestamp, a torn non-UTF-8 line included, is kept byte for byte and counted; a journal the daemon cannot read still takes new records, and only the trim is skipped, with a warning.
  - **Failures.** Writing the record never fails or delays the invocation (it runs on a blocking thread after the reply is ready). A failed write, a refused symlink included, is logged at warn level with its reason.
- **Policy gating (stage 4b, future)**: full pre-execution gating of each `tool_use` requires invoking the agent through a CAR-managed MCP server, not the default stream-json route. That's deliberately deferred — observability + audit ship first.
- See `docs/proposals/external-agent-detection.md` for the full architecture and Phase 2 design notes.


#### `agents.session_brief`

- **Params:** `{ id: string }` — enrolled session agent id.
- **Returns:** for a mind with a recipe,
  `{agent_id, brief_id, instructions, board, source:"car_compiler", compiled:true}`;
  for a session or service agent without a recipe,
  `{agent_id, instructions, board, source:"agent_instructions", compiled:false}`.
  `board: string | null` is the work-board briefing for the agent's own work
  context: at most 30 lines, with the items on its checkout's branch first and
  its own items marked. It is the same text Claude Code's SessionStart hook
  injects, and `null` when the board can't be read.
- **Authority:** host management. Unknown agents, absent compiled mind briefs,
  recipe changes and changed bead ownership are refused.

Minds receive the selected CAR-compiled brief described in [brief](brief.md#brief).
Recipe-less session and service agents receive their existing directory
instructions unchanged (empty when none exist). `car codex` accepts that session
response; supervised bead minds still require compiler output before spawning.
